START HERE · HOW TO USE THIS ROADMAP

This is a guided engineering curriculum — not a topic checklist.

This roadmap is designed to take a learner from GPU programming foundations to advanced kernel, inference, systems, compiler and research capability. Do not treat the phases as a list of technologies to skim. Each phase is a dependency chain: you learn the mental model, implement it, measure it, profile it, diagnose failure, produce evidence, and only then unlock the next layer.

THE LEARNING CONTRACT · USE THIS FOR EVERY IMPORTANT CONCEPT

Never meet a technical term without learning the thing behind it.

Every major concept in this curriculum — from a CUDA thread index to TMA, WGMMA, Triton program IDs, KV-cache paging, NCCL collectives, PTX, compiler passes or an optimization technique — should be learned through the same progressive sequence. The roadmap may introduce the concept at different depths, but the learner should never be expected to jump from a name directly to implementation.

Phase 04 · Hopper matrix execution

WGMMA

What is it? A Hopper-era asynchronous warp-group matrix-multiply mechanism: four warps cooperate on matrix work.

Why care? Modern Hopper Tensor Core workloads can expose more matrix throughput than a simple single-warp MMA mental model captures.

Problem + before: Earlier paths used warp-level MMA/WMMA-style execution. Hopper adds a larger cooperative, asynchronous execution model.

Simplest example: Compare one tiled GEMM using a conventional MMA path with a Hopper WGMMA path. First make both correct; only then chase throughput.

Modify / break / debug: Change tile shapes, warp participation and synchronization ordering. Look for incorrect barriers, invalid shared-memory state and under-filled work.

Benchmark: Sweep M/N/K and measure Tensor Core utilization, latency, registers, shared memory and achieved throughput.

Unseen problem: Choose a different GEMM shape and predict whether WGMMA will win before testing.

Mastery: Explain the four-warp mental model, asynchronous sequencing, resource costs and when the simpler path is actually better.

Next abstraction → WGMMA → producer/consumer pipelines → TMA → warp specialization → architecture-aware dispatch.
Phase 04 · Asynchronous data movement

TMA

What is it? Tensor Memory Accelerator support for moving multidimensional tensor regions between memory levels with hardware-assisted address generation and asynchronous execution.

Why care? The old staging path can consume instructions, registers and threads just to move data. TMA can move more of that work into a specialized mechanism.

Problem + before: Start with ordinary global loads, then cp.async-style staging where appropriate. Observe how much code and scheduling work is spent on movement.

Simplest example: A tiled GEMM where a producer loads the next tile while consumers compute the current tile.

Modify / break / debug: Change tensor shapes, strides, descriptor assumptions and barrier ordering. Deliberately create a producer/consumer synchronization error and diagnose it.

Benchmark: Compare transfer/compute overlap, instruction pressure, registers, occupancy and end-to-end kernel time.

Unseen problem: Decide whether a small workload amortizes TMA setup cost.

Mastery: Explain what TMA removes, what it does not remove, and when its setup/synchronization cost makes it a bad choice.

Next abstraction → TMA → pipelining → warp specialization → WGMMA/tcgen05 integration.
Phase 04 · Scheduling and pipeline design

Warp specialization

What is it? Deliberately assigning different warps distinct roles, such as data movement and compute, instead of having every warp perform the same work.

Why care? Asynchronous pipelines can benefit when producer and consumer responsibilities are made explicit.

Problem + before: Begin with all warps doing the same tiled loop. Then separate producer and consumer roles and compare the schedule.

Simplest example: One producer group loads the next tile; consumer warps perform matrix math on the current tile.

Modify / break / debug: Change producer count, tile size and synchronization. Break the handoff deliberately and trace which stage consumed invalid data.

Benchmark: Measure overlap, idle time, occupancy, registers and achieved compute/memory utilization.

Unseen problem: Given a pipeline with three stages, decide whether specialization is justified.

Mastery: Explain both the performance opportunity and the scheduling/complexity cost.

Next abstraction → specialization → clusters → persistent execution → architecture-specific scheduling.
Phase 03–04 · Resource management

Register allocation

What is it? The compiler/hardware-managed assignment of frequently used values to the fastest per-thread register storage, subject to a finite register budget.

Why care? Registers are extremely fast, but using too many can reduce resident warps or cause spills to slower memory.

Problem + before: Start from a correct kernel, then increase unrolling, accumulators or tile size until register demand changes the result.

Simplest example: Compare one accumulator with multiple accumulators in a tiled loop.

Modify / break / debug: Increase live values until performance regresses. Use compiler reports and Nsight evidence to distinguish healthy reuse from spilling.

Benchmark: Record registers/thread, occupancy, spills and kernel time together. Never treat register count as a score by itself.

Unseen problem: Given two kernels, predict which resource tradeoff is likely to dominate.

Mastery: Explain why fewer registers can be slower and more registers can also be slower.

Next abstraction → register allocation → occupancy tradeoff → launch configuration → architecture-specific scheduling.
Phase 03 · Residency, not speed

Occupancy

What is it? The relationship between active warps/threads resident on an SM and the hardware's maximum possible residency.

Why care? Residency can help hide latency, but maximizing occupancy is not the same as maximizing performance.

Problem + before: Start with a kernel whose performance is known. Change registers, shared memory or block size and observe how residency changes.

Simplest example: Compare two launch configurations that achieve different occupancy but perform differently.

Modify / break / debug: Force register pressure or shared-memory pressure and determine which resource limits residency.

Benchmark: Pair occupancy with stall reasons, memory behavior, instruction throughput and runtime.

Unseen problem: Given a low-occupancy kernel with high cache reuse, decide whether to increase occupancy at all.

Mastery: Treat occupancy as diagnostic context rather than an optimization target.

Next abstraction → occupancy → latency hiding → register/shared-memory tradeoffs → scheduler behavior.
Phase 09 · Compiler and machine-code literacy

PTX → SASS

What is it? PTX is NVIDIA's virtual assembly/intermediate representation; SASS is the architecture-specific machine instruction layer executed by the GPU.

Why care? Source code can hide what the compiler actually generated. Low-level inspection lets you connect a performance hypothesis to generated instructions.

Problem + before: Start from CUDA source and profiler results. Ask what instruction sequence could explain the behavior before inspecting generated code.

Simplest example: Compile a tiny arithmetic kernel and map a few source operations to PTX and then architecture-specific instructions.

Modify / break / debug: Change types, unrolling or math expressions and compare generated code. Look for extra conversions, loads, spills or unexpected paths.

Benchmark: Correlate code-generation changes with measured performance; never optimize assembly that has no measurable workload impact.

Unseen problem: Inspect two generated versions and hypothesize why one is faster before benchmarking.

Mastery: Move confidently between source, PTX/SASS evidence and profiler behavior without confusing an intermediate representation with the hardware ISA.

Next abstraction → source → compiler → IR/PTX → SASS → hardware counters → optimization hypothesis.
Phase 05 · Composable kernel abstractions

CuTe layouts

What is it? A compositional way to describe how logical tensor coordinates map onto physical storage, threads, warps and hardware operations.

Why care? High-performance kernels often fail because the data layout and computation layout do not line up efficiently.

Problem + before: Start with manual indexing and a simple tiled kernel. Then express the same mapping explicitly as a layout.

Simplest example: Map a 2D matrix tile onto threads and show the coordinate transformation before writing a full GEMM.

Modify / break / debug: Change the layout, tile shape or partitioning and inspect which threads own which values.

Benchmark: Compare layouts on coalescing, shared-memory access, register movement and Tensor Core utilization.

Unseen problem: Design a layout for a new matrix shape and explain the mapping before compiling.

Mastery: Explain layouts as a language for data movement and execution mapping, not as mysterious template syntax.

Next abstraction → layouts → tensor partitions → copy/MMA atoms → CuTe DSL → reusable kernel composition.
Phase 03–06 · Work assignment

Persistent kernels

What is it? A kernel design where a fixed set of resident program instances/blocks performs multiple units of work instead of launching a fresh unit for every piece.

Why care? It can reduce launch/scheduling overhead and improve data reuse or work coordination for the right workload.

Problem + before: Compare a conventional launch-per-work-unit design against a persistent design.

Simplest example: Keep a block resident and iterate over multiple tiles from a work queue or deterministic tile sequence.

Modify / break / debug: Change workload size and scheduling policy; deliberately create imbalance and inspect idle workers.

Benchmark: Sweep tiny, medium and large workloads. Measure launch overhead, utilization, tail behavior and work imbalance.

Unseen problem: Decide whether persistence helps a small fixed workload or merely adds complexity.

Mastery: Explain when persistence is an amortization strategy and when ordinary execution is simpler and faster.

Next abstraction → persistent execution → work queues → fused/streaming workloads → inference scheduling.
Phase 03–05 · Controlled search

Autotuning

What is it? Systematically testing a controlled set of kernel configurations and selecting the best configuration for a workload or shape class.

Why care? Tile sizes, warps, stages, layouts and pipeline depths interact too strongly to guess reliably across all shapes.

Problem + before: Start with one hand-picked configuration. Then expose a small design space and measure it.

Simplest example: Sweep tile size × warp count for one GEMM shape.

Modify / break / debug: Add invalid configurations, noisy measurements or an over-large search space and learn why tuning needs constraints and repeatability.

Benchmark: Use warmups, repeated trials, representative shapes and cache configuration results. Report the search space and selection rule.

Unseen problem: Design a tuning space for a new workload without blindly copying another kernel's parameters.

Mastery: Explain autotuning as an experiment-design problem, not “try random numbers until something is fast.”

Next abstraction → tuning → shape dispatch → configuration caching → online/offline performance policy.
Phase 07 · Runtime execution

CUDA Graphs

What is it? A captured execution graph that can replay a sequence of GPU operations with lower repeated launch/submission overhead than rebuilding the sequence each time.

Why care? Small, repetitive inference workloads can become CPU-launch-bound even when individual kernels are fast.

Problem + before: Measure an eager sequence of repeated kernels first. Identify whether CPU submission/launch overhead is material.

Simplest example: Capture a fixed-shape sequence and replay it repeatedly.

Modify / break / debug: Change shapes, memory addresses or control flow and observe what capture/replay constraints appear.

Benchmark: Compare eager vs graph replay for the same workload, including end-to-end latency rather than only kernel time.

Unseen problem: Decide whether a dynamic workload is a good candidate for graph capture.

Mastery: Explain the workload conditions that justify graphs and the dynamic-shape/state-management costs they introduce.

Next abstraction → graph capture → inference scheduling → CUDA Graphs + distributed execution.
Phase 07 · Multi-GPU communication

NCCL

What is it? NVIDIA's collective-communication library for moving and combining tensors across GPUs efficiently.

Why care? Multi-GPU training/inference can become communication-bound even when every individual GPU kernel is excellent.

Problem + before: Start with one GPU. Then split work and identify what data must be exchanged.

Simplest example: Time an all-reduce across two GPUs and compare message sizes.

Modify / break / debug: Change topology, message size, synchronization and participating ranks; learn to distinguish a communication problem from a compute problem.

Benchmark: Measure latency, effective bandwidth, scaling efficiency and overlap with computation.

Unseen problem: Choose between data/tensor/pipeline/expert parallelism based on communication patterns.

Mastery: Explain what collective is required, why, when it occurs and how it affects end-to-end scaling.

Next abstraction → collectives → communication/computation overlap → parallelism strategy → distributed serving.
Phase 06 · LLM inference memory

KV cache

What is it? Stored key/value attention state reused during autoregressive decoding so previous tokens do not need to recompute their attention projections.

Why care? Decode performance and memory capacity can become dominated by cache size, movement and layout.

Problem + before: Compare recomputing attention state for all previous tokens with reusing stored K/V tensors.

Simplest example: Generate a short sequence token by token and visualize cache growth per layer/head.

Modify / break / debug: Change sequence length, batch size, dtype and page/block layout. Check shape/indexing correctness and cache capacity.

Benchmark: Measure TTFT, TPOT, memory consumption and decode throughput across context lengths.

Unseen problem: Predict the memory impact of doubling context length or batch size before running it.

Mastery: Explain why KV cache is a systems problem, not merely a tensor in a model implementation.

Next abstraction → KV layout → paged cache → batching → decode scheduling → quantized/disaggregated inference.
Phase 06 · Sparse model execution

MoE

What is it? Mixture-of-Experts routing sends each token to a subset of expert networks rather than evaluating every expert.

Why care? Sparse compute creates routing, token movement, load imbalance and grouped-GEMM problems that dense models do not have in the same way.

Problem + before: Start with dense feed-forward execution. Then route tokens to experts and observe the extra movement and scheduling work.

Simplest example: A tiny router assigning tokens to two experts, followed by grouped matrix multiplications.

Modify / break / debug: Create skewed routing so one expert receives most tokens. Diagnose imbalance and capacity behavior.

Benchmark: Measure routing overhead, expert utilization, communication, grouped-GEMM efficiency and end-to-end latency.

Unseen problem: Given a routing distribution, predict where the bottleneck will appear.

Mastery: Explain MoE as a complete execution pipeline: route → move → compute → combine → synchronize.

Next abstraction → routing → token permutation → grouped GEMM → expert parallelism → distributed inference.
EXECUTION READINESS · TURN READING INTO ENGINEERING EVIDENCE

The roadmap cannot run your GPU for you. So it must tell you exactly what counts as evidence.

A learner should never be allowed to confuse “I understand the explanation” with “I can engineer this.” Every advanced topic therefore has an execution ladder. You may read and reason anywhere; execution mastery requires progressively stronger evidence.

01 · MENTAL MODEL

Explain

Define the mechanism, draw the data/control flow, explain the old approach and predict the tradeoff.

02 · REFERENCE

Reproduce

Run the smallest reference or simplified implementation. If no suitable GPU is available, complete the reasoning and CPU/reference portions but do not claim GPU execution mastery.

03 · REAL GPU

Measure

Run on supported hardware, validate correctness, benchmark controlled workloads and capture profiler evidence.

04 · WORKLOAD

Transfer

Integrate the technique into a realistic kernel/model/system, compare against a baseline and document the end-to-end impact.

Evidence rule: A screenshot, copied benchmark number or “it ran once” is not mastery evidence. A strong artifact contains the environment, code/configuration, correctness result, workload definition, benchmark method, profiler evidence where relevant, baseline comparison, observed tradeoffs and a conclusion that another person can reproduce.

4 Nsight Compute + bottleneck diagnosis

The profiler becomes part of the curriculum, not an optional debugging tool. For each major kernel, answer these questions before changing code.

  • Memory-bound? Check memory throughput, access efficiency, cache behavior and arithmetic intensity.
  • Compute-bound? Check instruction throughput and achieved FLOP/s against the relevant ceiling.
  • Occupancy-limited? Inspect registers, shared memory and active warps instead of assuming more occupancy is always better.
  • Warp-stalled? Identify memory dependency, synchronization, execution dependency or issue limitations.
  • Launch-bound? Especially for small kernels and repeated inference workloads.
  • Did the optimization change the intended metric? Re-profile rather than trusting source-code intuition.

5 Roofline diagnosis lab

Major optimization exercises classify their dominant limitation as one of six categories and defend that classification with profiler evidence.

Memory bound

Insufficient reuse or bandwidth utilization. Look at coalescing, cache locality, tiling and bytes moved per useful operation.

Compute bound

Arithmetic pipeline is limiting. Improve instruction efficiency, Tensor Core utilization, or useful work per instruction.

Latency bound

Too little independent work to hide dependency or memory latency. Increase parallelism or restructure dependencies where possible.

Instruction bound

Instruction count or issue pressure dominates even when raw FLOP/s is not the ceiling.

Synchronization bound

Barriers, atomics or coordination prevent useful work from progressing efficiently.

Launch bound

Kernel-launch overhead dominates; later phases can address fusion, batching and CUDA Graphs.

2 Full GPU memory-system model

Phase 3 phases the beginner memory hierarchy into a performance model. The question is not simply “which memory is faster?” but “where should this data live, how often should it move, and how much parallelism does that choice preserve?”

LayerPerformance questionEngineering lever
RegistersCan data stay close to the executing lane?Register reuse, accumulator tiling, lifetime reduction; watch spills.
Shared memoryCan a block reuse data cooperatively?Tiling, staging, bank-conflict avoidance, asynchronous copies.

Register pressure

More registers can improve reuse but reduce occupancy or trigger spills. Treat register count as a resource, not a score to maximize.

Shared-memory pressure

Larger tiles improve reuse until capacity, occupancy, or synchronization cost makes the tradeoff negative.

Cache locality

Do not automatically stage every load into shared memory. First determine whether cache already supplies sufficient reuse.

Overlap

Host/device transfer, memory staging, and computation can sometimes proceed concurrently; prove overlap with timeline/profiler evidence.

Then compare the workload against the relevant hardware bandwidth and compute ceilings. The goal is not to worship a theoretical roofline; it is to form a falsifiable hypothesis about what resource should matter.

4 The GEMM engineering ladder

GEMM becomes the central performance-engineering laboratory. Each rung must be benchmarked against the previous rung; no optimization is accepted merely because the code looks more sophisticated.

01 · Naive GEMMOne output element per thread. Establish the correctness and baseline performance model.
02 · Coalesced GEMMMake global-memory accesses friendly to the warp and expose the cost of poor layouts.
03 · Shared-memory tilingReuse A/B tiles across threads and quantify global-memory reads saved.
04 · Register tilingKeep multiple accumulators per thread and study the register/occupancy tradeoff.
05 · Warp tilingMap work to warps and understand how block tiles become warp-level tiles.
06 · Vectorized memoryUse aligned vector loads/stores where they actually improve memory efficiency.
07 · Double bufferingOverlap loading and compute to hide memory latency.
08 · cp.asyncBuild an asynchronous global→shared pipeline and compare it to synchronous staging.
09 · Tensor Core bridgePrepare the GEMM path for the dedicated Tensor Core phase without pretending WMMA is the end state.
10 · Persistent / grouped / split-KIntroduce workload-dependent scheduling strategies after the core tiled implementation is understood.
11 · Autotuned GEMMSearch tile sizes, warps, stages, and related parameters rather than hard-coding one configuration.
GEMM comparison contract

Every flagship GEMM study must compare naive CUDA → optimized CUDA → cuBLAS → the relevant later implementation(s). The objective is not to beat a vendor library at every shape; the objective is to understand where your implementation wins, loses, and why.

5 Register blocking + warp-level reasoning

Register reuse

Hold partial accumulators in registers so values do not return to shared/global memory between inner-loop operations.

Accumulator fragments

Think of the output as a per-thread fragment rather than one scalar. Track how fragment size affects instruction count and register pressure.

Tile-size tradeoff

Larger tiles improve reuse but consume shared memory/registers. Find the knee empirically.

Warp mapping

Understand which lane owns which output elements and how that mapping affects loads, reuse and synchronization.

6 Asynchronous pipeline laboratory

Global memory → asynchronous staging → shared-memory tile → compute → next tile
  • Build a synchronous tiled GEMM baseline before attempting asynchronous staging.
  • Implement a double-buffered version and identify the expected overlap.
  • Implement a cp.async-based pipeline on supported hardware.
  • Use profiler evidence to determine whether memory latency was actually hidden.
  • Record the register/shared-memory/occupancy cost of the pipeline.

7 Fusion as a performance decision

Fusion is not automatically good. It trades kernel launches and intermediate memory traffic against larger kernels, more registers, lower occupancy, and potentially harder scheduling.

QuestionMeasureDecision
Does fusion remove a large intermediate?Bytes written/read by intermediateStrong fusion candidate.
Does fusion remove launches?Kernel count + launch timePotentially valuable for small/repeated workloads.
Does fusion explode register use?Registers/thread + occupancyMay erase the memory/launch win.
Does fusion improve the critical path?End-to-end latencyJudge at workload level, not kernel-level aesthetics.

11.5 Failure modes you must learn to recognize

Tensor Core underfedTensor Core path exists, but memory movement, layout conversion or synchronization prevents useful utilization.
“More occupancy” fallacyIncreasing occupancy makes the kernel slower because registers, cache locality or pipeline behavior were more important.
Async without overlapcp.async/TMA is present in source code but the schedule does not actually hide the transfer latency.
Specialization overheadProducer/consumer roles reduce useful compute or introduce synchronization that outweighs the overlap benefit.
Precision trapLower precision improves kernel throughput but harms numerical quality or end-to-end model performance.
Architecture overfittingA kernel wins on one GPU but collapses elsewhere because the implementation was tuned to an accidental bottleneck.
Library denialA custom kernel loses to cuBLAS/CUTLASS because the comparison was never performed.
Unsupported-hardware bluffA feature is “tested” through an approximation on hardware that cannot execute the target path. The roadmap forbids treating that as validation.

11 Failure modes you must learn to recognize

2 Streams and concurrency — make the GPU see independent work

Learn streams as an execution-order and concurrency tool, not merely an API. CUDA streams serialize work within a stream while allowing independent work in different streams to overlap when dependencies and resources permit. citeturn0search13

  • Default vs non-default streams: understand implicit synchronization and why an innocent NULL/default-stream operation can destroy overlap.
  • Events: use CUDA events to express dependencies and measure device-side elapsed time.
  • Overlap: build H2D/compute/D2H pipelines and prove overlap in a profiler timeline.
  • Concurrency limits: distinguish “submitted concurrently” from “actually executing concurrently.”

3 CUDA Graphs — remove repeated submission overhead

CUDA Graphs separate workflow definition from repeated execution. They can reduce CPU launch/setup overhead by allowing a captured sequence of operations to be launched as a graph. citeturn0search3

  1. Baseline: execute a repeated transformer-like sequence with ordinary stream launches.
  2. Measure: separate GPU execution time from CPU submission overhead.
  3. Capture: build a CUDA Graph around the stable execution region.
  4. Replay: measure repeated execution after graph instantiation.
  5. Stress: test shape changes, dynamic allocations and changing control flow.
  6. Decision: document when graphs help, when they don't, and what constraints they introduce.
Modern production connection

PART A · UNIVERSAL FRAMEWORK

The GPU Problem-Solving Framework

Seven tools. Use them in this order when learning something new; use them in this order under interview/timed conditions too. Every worked example later in this roadmap will explicitly cite which of these seven steps it's applying, so it's worth internalizing the numbering now.

1 Deconstruct the problem statement

Before writing a single line of code, extract these five things. If you can't fill in all five, you don't understand the problem yet — go back and reread it.

  • Data shape/size — exact dimensions (N, or M×N, or B×H×S×D for attention-style tensors). Is a dimension a compile-time constant or a runtime argument? Small N (fits in one block) changes the whole strategy vs. large N (needs grid-stride loops).
  • Memory layout — row-major (C-style, the default for basically every LeetGPU problem) vs. column-major. For a matrix A[M][N] row-major, element A[i][j] lives at i*N + j. Getting this backwards is the single most common source of "correct algorithm, wrong output."
  • Data type — fp32 (default, forgiving), fp16/bf16 (needs care with accumulation precision), int8/int4 (quantized — usually paired with a scale/zero-point and packed multiple values per byte).
  • Output requirements — new output buffer, or in-place modification? Single scalar (reduction), same-shape tensor (elementwise), or different-shape tensor (matmul, transpose, pooling)? Does order of output elements matter (stable sort) or not?
  • Constraints that hint at expected performance — "N up to 10^8" screams memory-bound, coalescing-first. "matrix up to 4096×4096" screams shared-memory tiling for matmul. A tight time limit relative to naive O(N²) usually means an O(N log N) or tiled approach is expected, not just "make the naive version faster."

2 Problem → technique decision guide

Once you've deconstructed the problem, this table maps its shape to the right starting strategy. Read it top to bottom — later rows assume you've ruled out the earlier, simpler patterns.

Compute-bound vs. memory-bound — the 30-second gut check

Estimate arithmetic intensity: FLOPs / bytes moved. Vector add moves 3 elements (read A, read B, write C) per 1 FLOP → hopelessly memory-bound, so your only lever is coalesced access. Naive matmul does O(N) FLOPs per element loaded but reloads the same rows/columns from global memory N times — tiling fixes exactly this by reusing data from shared memory instead of re-fetching from global memory.

3 Naive-first checklist

Never optimize a kernel you haven't proven correct. This is the fixed order of operations:

  1. Get it correct with the dumbest possible mapping — usually one thread per output element, no shared memory, no tiling, direct global memory reads. Accept that it will be slow.
  2. Verify correctness against a CPU reference (see Tool 5) before touching performance at all.
  3. Fix memory coalescing — are consecutive threads (by threadIdx.x) reading/writing consecutive memory addresses? If not, this is almost always the first and biggest win.
  4. Introduce shared memory if there's data reuse across threads in the same block (tiling for matmul/conv, row caching for softmax/attention/normalization).
  5. Check occupancy — registers-per-thread and shared-memory-per-block both cap how many blocks can run concurrently on one SM. Too many registers or too much shared memory per block silently throttles parallelism even though the kernel is "correct."
  6. Check for shared memory bank conflicts — do threads in a warp hit the same bank (stride-32 access patterns are the classic trap, e.g. column access into a tile without padding)?
  7. Check for warp divergence — does an if inside the kernel split a warp into two execution paths that get serialized? Divergence on data (not on threadIdx) is usually unavoidable and fine; divergence that splits whole warps along predictable boundaries is often refactorable.
  8. Increase instruction-level parallelism if occupancy is already high but you're still not at the memory-bandwidth or compute roofline — e.g. have each thread process 2–4 elements instead of 1.

4 How to verbalize a solution under interview conditions

Say these five things out loud, in this order, before and while you type. Interviewers are grading the reasoning at least as much as the final kernel.

  1. Clarify. "So the input is an M×N row-major fp32 matrix, output is same shape, and I should handle M or N not being a multiple of the block size — is that right?"
  2. State the parallelization strategy before coding. "I'll launch a 2D grid where each thread owns one output element, with 16×16 thread blocks."
  3. Name the expected bottleneck up front. "This is memory-bound since it's one FLOP per element — I'll focus on coalesced access rather than compute tricks," or "this is compute-bound / reuse-heavy, so I'll tile into shared memory."
  4. Write the kernel, narrating boundary checks and index math as you go.
  5. Discuss correctness explicitly — where could a race condition occur? Do I need __syncthreads()? Is any memory read-after-write across threads without synchronization? — then discuss what you'd optimize next if given more time.

5 Correctness testing checklist

  • Write a straightforward CPU reference implementation first — nested loops, no cleverness. This is your oracle, not your solution.
  • Compare with tolerance, not exact equality, for floating point: |gpu - cpu| ≤ atol + rtol * |cpu|, typically atol=rtol=1e-5 for fp32, looser (1e-2 to 1e-3) for fp16/bf16.
  • Test the empty input (N=0) — does your kernel launch config or grid-size math divide by zero or launch 0 blocks safely?
  • Test a single-element input — does your reduction/attention/ softmax logic degrade correctly with only 1 valid element?
  • Test a non-power-of-2 size, and specifically a size that isn't a multiple of your block size — this is where boundary/masking bugs live.
  • Test negative numbers and zeros for anything involving ReLU- family activations, absolute value, or square roots.
  • For reductions/softmax: test an input where the naive (non-numerically- stable) version would overflow — large positive values before a softmax's exp(), for instance.

6 "If stuck" decision tree

● WRONG RESULTS — check in this order
  1. Off-by-one / boundary indexing — did you guard if (idx < N) on every global memory access?
  2. Missing __syncthreads() after writing to shared memory and before reading it back from a different thread.
  3. Race condition — two threads writing the same output address without atomics.
  4. Uninitialized memory — did you memset/initialize an accumulator or output buffer before accumulating into it?
  5. Row-major vs. column-major index math — recheck the flattening formula from Tool 1.
● CORRECT BUT SLOW — check in this order
  1. Memory coalescing — are adjacent threads touching adjacent addresses?
  2. Occupancy — profile registers/thread and shared-mem/block; are you under-subscribing the SM?
  3. Thread/block sizing — is your block size a multiple of warp size (32)? Too small wastes warps, too large can hurt occupancy via register/shared-mem pressure.
  4. Shared memory bank conflicts — pad tile arrays (e.g. [TILE][TILE+1]) if column-wise access is involved.
  5. Warp divergence — can a branch be rewritten as arithmetic/select instead of control flow?

1 C/C++, only the parts CUDA actually needs

This is not a C++ course. Every CUDA kernel is written in a restricted dialect of C++, and these are the only pieces of "real" C++ that show up constantly:

Pointers and pointer arithmetic

A kernel receives raw pointers to GPU memory, not arrays with bounds-checking. A[i] is sugar for *(A + i) — the pointer plus an integer offset, scaled by the size of the pointed-to type. This is the entire basis of every indexing formula you'll write.

pointer_basics.cpp
float* A = someArray;
// A[3] and *(A + 3) are identical — both read the 4th float
float x = A[3];
float y = *(A + 3);   // same value as x

// 2D row-major indexing is just this idea in two dimensions:
// element (row, col) of an M x N matrix stored as a flat 1D buffer
int idx = row * N + col;
float val = A[idx];

Manual memory allocation

No garbage collector, no RAII by default at the kernel level. You allocate, you free. This maps directly onto cudaMalloc / cudaFree later — the CPU-side pattern is identical to malloc/free.

manual_alloc.cpp
float* buffer = (float*)malloc(N * sizeof(float));
// ... use buffer ...
free(buffer);  // forgetting this is a leak; freeing twice is a crash

Structs

Used to bundle related fields — a complex number, an RGB pixel, a quantization (scale, zero-point) pair — when passing them into or out of a kernel as one unit.

structs.cpp
struct QuantParams {
    float scale;
    int zeroPoint;
};

Basic templates

Some problems (INT8 quantized matmul vs. fp32 matmul, e.g.) are structurally the same kernel over a different type. A function template lets you write it once.

templates.cpp
template<typename T>
T clamp(T val, T lo, T hi) {
    return val < lo ? lo : (val > hi ? hi : val);
}
  • Can read A[i*N+j] and immediately know it's row-major indexing into an M×N matrix without deriving it from scratch.
  • Can write a function that takes a raw pointer and a length, and loops over it correctly (including the boundary).
  • Know that arrays passed to functions decay to pointers — you lose the length, which is why kernels always take an explicit size parameter.

2 Core computer architecture, in plain language

Thread → Warp → Block → Grid

TermPlain-language definition
ThreadOne lane of execution — conceptually runs your kernel body once, for one index. Cheap to create; you launch thousands to millions of them.
WarpA hardware-scheduled group of 32 threads that physically execute the same instruction at the same time (SIMT — see below). This number, 32, is fixed by the hardware and shows up everywhere: bank conflicts, divergence, and "why block size should be a multiple of 32."
BlockA programmer-chosen group of threads (e.g. 256) that run on the same SM (streaming multiprocessor), can synchronize with __syncthreads(), and can share fast on-chip shared memory with each other. Blocks cannot synchronize with other blocks inside a single kernel launch.
GridAll the blocks launched for one kernel call. If you have N elements and 256 threads per block, your grid has ceil(N/256) blocks.

SIMT — Single Instruction, Multiple Thread

All 32 threads in a warp execute the same instruction in lockstep. If an if sends some threads down one path and some down another, the warp executes both paths serially, masking off the inactive threads each time — this is warp divergence, and it's why data-dependent branches inside a warp cost real time even though "only one thread" seems to be doing extra work.

Why shared memory tiling works

Every technique labeled "shared memory tiling" in this roadmap is doing one thing: copying a chunk of global memory into shared memory once, then letting every thread in the block reread that chunk from shared memory many times instead of re-hitting global memory. That's the entire trick behind fast matmul, convolution, and attention kernels.

Latency vs. throughput, and occupancy

A single thread's memory access is slow (high latency — hundreds of cycles). A GPU doesn't make that access faster; instead, while one warp waits on memory, the SM switches to executing a different warp that's ready to run. This works only if there are enough resident warps to switch between — that count is occupancy. Low occupancy means the SM runs out of other work while waiting on memory, and the latency becomes visible as idle time instead of being hidden.

3 Parallel complexity: work vs. span

Sequential Big-O assumes one processor. On a GPU you have (conceptually) as many processors as threads, so two numbers matter instead of one:

  • Work (W) — total number of operations across all threads combined. Same as sequential Big-O.
  • Span (S) — length of the longest chain of operations that must happen in order (the critical path), assuming infinite processors.

With P processors, runtime is roughly T ≈ O(W/P + S). This is why a reduction over N elements — W = O(N), S = O(log N) — finishes in roughly O(log N) time with enough threads, even though a sequential sum is O(N). It's also why some algorithms (e.g. anything with a true O(N) sequential dependency, like a naive running total with no reformulation) don't parallelize well no matter how many threads you throw at them: span stays O(N).

PatternWorkSpanWhy
Vector addO(N)O(1)Every output is independent — full parallelism, no dependency chain
Tree reductionO(N)O(log N)Each level of the tree halves the remaining elements
Naive matmul (per-output-thread)O(N³)O(N)Each thread does a length-N dot product sequentially
Prefix sum (naive sequential)O(N)O(N)Each element depends on all previous ones — must be reformulated (Hillis-Steele) to get S = O(log N)

1 Pattern: 1D elementwise map

Covers: Vector Addition, Matrix Addition, ReLU, Leaky ReLU, Sigmoid Activation, Value Clipping. Every one of these is "read one (or two) input value(s), apply a pure function, write one output value" — zero cross-thread communication.

Applying the framework

Tool 1: N fp32 elements, flat 1D layout, output same shape as input. Tool 2: output[i] depends only on input[i] → 1D grid-stride loop, no shared memory needed. Tool 3: naive version is the optimal version here — there's nothing to tile or cache.

vector_add.cu — representative example
__global__ void vectorAdd(const float* A, const float* B, float* C, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    // Tool 6 reflex: this boundary check is the #1 thing to verify if results are wrong
    if (idx < N) {
        C[idx] = A[idx] + B[idx];
    }
}

void launch(const float* dA, const float* dB, float* dC, int N) {
    int threads = 256;
    int blocks = (N + threads - 1) / threads;   // ceil(N / threads)
    vectorAdd<<<blocks, threads>>>(dA, dB, dC, N);
}

Every other problem in this pattern is a one-line swap of the kernel body:

2 Pattern: index remapping

Covers: Reverse Array, Interleave Arrays. Still one thread per output element, but the source or destination index is a function of thread index rather than equal to it — this is the pattern's whole teaching point.

Applying the framework

Tool 1: output requirement is a specific reordering, not a value transform. Tool 6 reflex: the most common bug here is an off-by-one in the index formula (N-1-idx vs. N-idx), not a race condition.

reverse_array.cu
__global__ void reverseArray(const float* in, float* out, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        out[idx] = in[N - 1 - idx];   // each thread reads from the mirrored position
    }
}

Interleave Arrays is the same idea in reverse — one thread reads one element but writes to two possible destinations depending on parity: out[2*idx] = A[idx]; out[2*idx+1] = B[idx]; — no synchronization needed because each thread owns disjoint output addresses.

3 Pattern: per-thread heavier compute, same elementwise shape

Covers: Rainbow Table. Structurally identical to Pattern 1 — one thread, one output — but each thread does a small internal loop of work (repeated hashing) instead of one operation. The lesson: adding a per-thread loop doesn't change the parallelization strategy at all.

rainbow_table.cu
__device__ unsigned int fnv1aHash(unsigned int x) {
    const unsigned int prime = 16777619u;
    unsigned int hash = 2166136261u;
    for (int b = 0; b < 4; b++) {
        hash ^= (x >> (b * 8)) & 0xFF;
        hash *= prime;
    }
    return hash;
}

__global__ void rainbowTable(const unsigned int* in, unsigned int* out, int N, int rounds) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        unsigned int h = in[idx];
        for (int r = 0; r < rounds; r++) h = fnv1aHash(h);  // per-thread loop, no cross-thread deps
        out[idx] = h;
    }
}
LeetGPU's exact Rainbow Table spec (which hash function, how many rounds) should be read directly on the problem page — the pattern above is illustrative of the technique, not a guaranteed-matching reference solution.

4 Pattern: image channel elementwise

Covers: Color Inversion, RGB to Grayscale. Still elementwise, but now each output pixel reads from multiple interleaved input channels — the first place channel layout (interleaved RGBRGBRGB... vs. planar RRR...GGG...BBB...) actually matters for coalescing.

Applying the framework

Tool 1: input is typically interleaved uint8 RGB, 3 bytes/pixel. Tool 2: one thread per pixel, each thread does 3 reads + 1 (or 3) write(s). Adjacent threads (adjacent pixels) read addresses 3 bytes apart — still coalesced at the warp level since the access is regular, just not 1:1.

rgb_to_grayscale.cu
__global__ void rgbToGrayscale(const unsigned char* rgb, unsigned char* gray, int numPixels) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < numPixels) {
        unsigned char r = rgb[idx * 3 + 0];
        unsigned char g = rgb[idx * 3 + 1];
        unsigned char b = rgb[idx * 3 + 2];
        // standard luminance weights — matches most reference implementations
        gray[idx] = (unsigned char)(0.299f * r + 0.587f * g + 0.114f * b);
    }
}

Color Inversion is simpler still: out[idx] = 255 - in[idx] applied per channel per pixel — same launch shape, trivial body.

5 Pattern: 2D matrix elementwise, copy, and transpose

Covers: Matrix Copy, Matrix Transpose. Matrix Copy is Pattern 1 in 2D clothing. Matrix Transpose looks just as simple but is the first problem in this roadmap where the naive version and the fast version are genuinely different kernels — worth slowing down for.

matrix_copy.cu
__global__ void matrixCopy(const float* in, float* out, int rows, int cols) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (row < rows && col < cols) {
        int idx = row * cols + col;   // Tool 1: row-major flattening
        out[idx] = in[idx];
    }
}
Applying the framework — naive transpose

Tool 2: looks like Pattern 1, but it isn't — the write address and read address use swapped row/col, so one of the two accesses can never be coalesced with a naive 1:1 thread mapping. Tool 3 (naive first): get this version correct, then measure — don't skip straight to tiling.

transpose_naive.cu
__global__ void transposeNaive(const float* in, float* out, int rows, int cols) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (row < rows && col < cols) {
        // read is coalesced (consecutive col -> consecutive address)
        // write is NOT coalesced: consecutive col -> addresses `rows` apart
        out[col * rows + row] = in[row * cols + col];
    }
}

The fix: stage a tile through shared memory so both the global read and the global write are coalesced, and the transpose only happens inside fast shared memory.

transpose_tiled.cu — the fast version
#define TILE 32

__global__ void transposeTiled(const float* in, float* out, int rows, int cols) {
    // +1 padding kills shared-memory bank conflicts on the column-wise read below (Tool 3, step 6)
    __shared__ float tile[TILE][TILE + 1];

    int x = blockIdx.x * TILE + threadIdx.x;
    int y = blockIdx.y * TILE + threadIdx.y;

    // Stage 1: coalesced read from global -> shared (every thread reads its natural row-major cell)
    if (y < rows && x < cols) {
        tile[threadIdx.y][threadIdx.x] = in[y * cols + x];
    }
    __syncthreads();  // Tool 6 reflex: skip this and you read a half-written tile

    // Stage 2: transposed output coordinates for this block
    int tx = blockIdx.y * TILE + threadIdx.x;
    int ty = blockIdx.x * TILE + threadIdx.y;

    // Stage 3: coalesced write from shared -> global, reading the tile transposed (cheap, it's on-chip)
    if (ty < cols && tx < rows) {
        out[ty * rows + tx] = tile[threadIdx.x][threadIdx.y];
    }
}

6 Pattern: windowed / halo access

Covers: 1D Convolution. First pattern where an output element depends on a neighborhood of inputs rather than exactly one. This is the direct prerequisite for 2D/3D convolution, Gaussian blur, and pooling in Level 2.

Applying the framework

Tool 1: input length N, kernel/filter length K, output length is typically N-K+1 (valid convolution) — check the exact output-length convention on the problem page. Tool 3: naive-first means each thread just loops over its own K-wide window directly from global memory; shared-memory halo caching is the optimization to reach for only after this works.

conv1d_naive.cu
__global__ void conv1d(const float* input, const float* kernel, float* output,
                       int inputLen, int kernelLen) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int outputLen = inputLen - kernelLen + 1;
    if (idx < outputLen) {
        float acc = 0.0f;
        for (int k = 0; k < kernelLen; k++) {
            acc += input[idx + k] * kernel[k];   // sliding window read — Tool 1's "constraints hint" applies:
        }                                         // large kernelLen means each thread does more sequential work
        output[idx] = acc;
    }
}

7 Pattern: dot-product-per-output (matmul introduction)

Covers: Matrix Multiplication, Simple Inference. The most important pattern in Level 1 — this naive kernel is deliberately not the fast version. It exists so Level 2's tiled GEMM has something concrete to improve on.

Applying the framework

Tool 2: high data reuse (every element of row i of A is re-read by every output in row i; every element of column j of B is re-read by every output in column j) → naive per-output-thread matmul is memory-bound despite doing O(N) FLOPs per output, because it re-fetches the same global memory over and over across threads. Fixing this with shared-memory tiling is Level 2's GEMM problem, not this one — naive-first applies here too.

matmul_naive.cu
__global__ void matmulNaive(const float* A, const float* B, float* C,
                             int M, int N, int K) {   // A: M x K, B: K x N, C: M x N
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    if (row < M && col < N) {
        float acc = 0.0f;
        for (int k = 0; k < K; k++) {
            acc += A[row * K + k] * B[k * N + col];   // Tool 6 reflex: verify this against row-major
        }                                              // flattening from Tool 1 if results are wrong
        C[row * N + col] = acc;
    }
}

Simple Inference is this exact kernel plus a bias add fused into the accumulator's final write: C[row*N+col] = acc + bias[col]; — running a torch.nn.Linear forward pass is matmul-plus-bias.

8 Pattern: sigmoid-family gated activations

Covers: Sigmoid Activation, Sigmoid Linear Unit (SiLU), Swish-Gated Linear Unit (SWiGLU), Gaussian Error Gated Linear Unit (GEGLU). These four build on each other in a strict chain — each one is the previous one wrapped in one more operation. This chain reappears, scaled up, as the "SwiGLU MLP Block" problem in Level 2 and inside every modern transformer's feed-forward layer.

sigmoid_and_silu.cu
__device__ float sigmoidf(float x) {
    return 1.0f / (1.0f + expf(-x));
}

__global__ void sigmoidActivation(const float* in, float* out, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) out[idx] = sigmoidf(in[idx]);
}

__global__ void silu(const float* in, float* out, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        float x = in[idx];
        out[idx] = x * sigmoidf(x);   // SiLU == Swish(beta=1): x * sigmoid(x)
    }
}

SWiGLU gates one linear projection with the Swish of another: out[i] = silu(xW1[i]) * xW2[i] — you compute two matmuls (Pattern 7), then combine them elementwise (Pattern 1) with the SiLU kernel above feeding the gate. GEGLU is structurally identical with GELU in place of SiLU: out[i] = gelu(xW1[i]) * xW2[i], using the tanh-approximation of GELU (0.5x(1+tanh(√(2/π)(x+0.044715x³)))) since the exact erf-based GELU is more expensive. Both are "assemble Patterns 1 and 7 you already built," not new kernel-writing techniques.

1 Family: reduction

Covers: Reduction, Dot Product, Mean Squared Error, Count Array Element (1D/2D/3D), Subarray Sum (1D/2D/3D). This is the pattern Part A's Tool 2 called out explicitly: work O(N), span O(log N). Every problem here is "combine N values into 1 (or a few) with an associative operator," just with a different operator or a pre/post transform.

Applying the framework

Tool 2: cross-thread communication required → tree reduction in shared memory, then warp-level finishing with shuffle intrinsics once down to 32 elements (a single warp doesn't need __syncthreads() — it's implicitly synchronized). Tool 6 reflex: the classic bug is reading a partially-reduced shared memory array before __syncthreads() completes.

reduction_sum.cu
__global__ void reduceSum(const float* in, float* out, int N) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + threadIdx.x;

    sdata[tid] = (idx < N) ? in[idx] : 0.0f;   // out-of-range threads contribute the identity element
    __syncthreads();

    // sequential addressing: no bank conflicts, no warp divergence from the stride pattern
    for (int s = blockDim.x / 2; s > 32; s >>= 1) {
        if (tid < s) sdata[tid] += sdata[tid + s];
        __syncthreads();
    }
    if (tid < 32) {
        volatile float* vsmem = sdata;
        // last warp: no __syncthreads needed, a warp executes in lockstep (SIMT)
        vsmem[tid] += vsmem[tid + 32]; vsmem[tid] += vsmem[tid + 16];
        vsmem[tid] += vsmem[tid + 8];  vsmem[tid] += vsmem[tid + 4];
        vsmem[tid] += vsmem[tid + 2];  vsmem[tid] += vsmem[tid + 1];
    }
    if (tid == 0) atomicAdd(out, sdata[0]);   // combine this block's result into the global total
}

2 Family: softmax

Covers: Softmax, Softmax Attention, Categorical Cross Entropy Loss, Top K Selection, Top-p Sampling. The defining trap here — flagged in Part A's Tool 7 — is numerical instability: exp(x) overflows for even moderately large x. Every kernel in this family subtracts the row max before exponentiating.

Applying the framework

Tool 2: small fixed-size dense op per row → one block per row, keep the row resident in shared memory. Tool 3 escalation: naive softmax is 3 reduction passes (max, then sum-of-exp, then normalize) — later, Level 3's "online softmax" fuses these into one pass for flash-attention-style kernels; don't reach for that fusion yet.

softmax_row.cu — one block per row
__global__ void softmaxRow(const float* in, float* out, int rows, int cols) {
    extern __shared__ float row[];
    int r = blockIdx.x;
    int tid = threadIdx.x;

    // Pass 1: cooperative load + running max (numeric stability, Part A Tool 7)
    float localMax = -INFINITY;
    for (int c = tid; c < cols; c += blockDim.x) {
        row[c] = in[r * cols + c];
        localMax = fmaxf(localMax, row[c]);
    }
    // block-wide max reduction (shared mem, omitted here — same skeleton as Family 1)
    __shared__ float blockMax;
    if (tid == 0) blockMax = localMax;   // simplified; real version reduces localMax across all threads
    __syncthreads();

    // Pass 2: exponentiate relative to the max, accumulate the sum
    float localSum = 0.0f;
    for (int c = tid; c < cols; c += blockDim.x) {
        row[c] = expf(row[c] - blockMax);
        localSum += row[c];
    }
    __shared__ float blockSum;
    if (tid == 0) blockSum = localSum;   // simplified; real version reduces localSum across all threads
    __syncthreads();

    // Pass 3: normalize and write back
    for (int c = tid; c < cols; c += blockDim.x) {
        out[r * cols + c] = row[c] / blockSum;
    }
}
The blockMax/blockSum lines above are simplified to keep the listing focused on the three-pass structure — in your real implementation, reduce localMax/localSum across all threads in the block using Family 1's tree-reduction skeleton before broadcasting.

Categorical Cross Entropy LossSame max-subtract trick, but fused with -log(softmax(x)[target]) — the log-sum-exp identity lets you compute this without materializing the full softmax: loss = -(x[target] - max) + log(sum).

3 Family: tiled GEMM and its variants

Covers: GEMM, Batched Matrix Multiplication, FP16 Batched Matrix Multiplication, FP16 Dot Product, Sparse Matrix-Dense Matrix Multiplication, Matrix Power. This is the direct fix for Level 1's memory-bound naive matmul — the single highest-leverage kernel pattern in the whole roadmap, since GEMM underlies almost every other ML kernel in Levels 2 and 3.

Applying the framework

Tool 2 recap from Level 1: naive matmul re-reads the same global memory rows/columns across many threads. The fix: cooperatively load a TILE×TILE block of A and B into shared memory once per tile, have every thread in the block reuse that tile TILE times, then slide the tile across K. This converts an O(N) global-memory-read-per-output kernel into an O(N/TILE) one.

gemm_tiled.cu
#define TILE 16

__global__ void gemmTiled(const float* A, const float* B, float* C,
                            int M, int N, int K) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int row = blockIdx.y * TILE + threadIdx.y;
    int col = blockIdx.x * TILE + threadIdx.x;
    float acc = 0.0f;

    int numTiles = (K + TILE - 1) / TILE;
    for (int t = 0; t < numTiles; t++) {
        // cooperative load: each thread loads exactly one element of each tile
        int aCol = t * TILE + threadIdx.x;
        int bRow = t * TILE + threadIdx.y;
        As[threadIdx.y][threadIdx.x] = (row < M && aCol < K) ? A[row * K + aCol] : 0.0f;
        Bs[threadIdx.y][threadIdx.x] = (bRow < K && col < N) ? B[bRow * N + col] : 0.0f;
        __syncthreads();   // Tool 6 reflex: both tiles must be fully loaded before the next loop reads them

        #pragma unroll
        for (int k = 0; k < TILE; k++) {
            acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];   // reused TILE times from fast shared memory
        }
        __syncthreads();   // don't let a fast thread overwrite the tile before slow threads finish reading it
    }
    if (row < M && col < N) C[row * N + col] = acc;
}

FP16 Batched MatMulLoad A/B as __half, but accumulate in fp32 (acc stays float) — this is Part A Tool 7's "subtle precision issues in FP16" trap; an fp16 accumulator loses precision over long K.
FP16 Dot ProductFamily 1's dot product, but inputs are __half with an fp32 accumulator — same precision rule applies.

4 Family: quantization

Covers: INT8 Quantized MatMul, INT4 Weight-Only Quantized MatMul, Weight Dequantization. (INT8 KV-Cache Attention combines this family with the attention family and is covered there, next message.) The core idea in all three: store low-precision integers plus a small number of fp32 scale/zero-point values, and only reconstruct fp32 values where the math actually needs them.

Applying the framework

Tool 1: dtype is now two arrays — the quantized values (int8/int4) and a much smaller fp32 (or fp16) scale array, sometimes per-tensor and sometimes per-row/per-channel. Tool 7 hard trap: applying the wrong granularity of scale (a global scale when the reference expects per-channel, or vice versa) produces numbers that are close but not within tolerance — re-check the exact quantization scheme on the problem page before assuming per-tensor.

weight_dequantization.cu — the base operation
__global__ void dequantize(const signed char* qWeights, const float* scale,
                             const int* zeroPoint, float* out, int N) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        out[idx] = (qWeights[idx] - zeroPoint[0]) * scale[0];   // per-tensor scale shown; index scale[idx/rowLen] for per-channel
    }
}
int8_matmul.cu — fuse dequantization into the GEMM accumulator
__global__ void int8Matmul(const signed char* A, const signed char* B, float* C,
                             float scaleA, float scaleB, int M, int N, int K) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < M && col < N) {
        int accInt = 0;   // accumulate in int32 — cheap, exact, no precision loss mid-sum
        for (int k = 0; k < K; k++) {
            accInt += (int)A[row * K + k] * (int)B[k * N + col];
        }
        C[row * N + col] = accInt * scaleA * scaleB;   // dequantize ONCE at the end, not per multiply-add
    }
}

INT4 Weight-Only Quantized MatMul packs two 4-bit weights per byte — unpack before the same accumulation loop: int8_t hi = (byte >> 4) - 8; int8_t lo = (byte & 0xF) - 8; (typical signed 4-bit unpacking, offset depends on the exact scheme specified), then proceed exactly like the INT8 kernel above with one extra unpack step per pair of weights.

5 Family: convolution, stencil, and pooling

Covers: 2D Convolution, 3D Convolution, Gaussian Blur, 2D Max Pooling, 2D Jacobi Stencil. (Causal Depthwise Conv1d is covered with the transformer-component family next message, since "causal" ties it to attention masking.) Direct extension of Level 1's 1D convolution into 2D/3D, now worth shared-memory halo caching because each output re-reads overlapping neighbors.

Applying the framework

Tool 2: data reuse across neighboring threads (adjacent output pixels share most of their input window) → shared memory tile plus a halo/apron border of extra elements around the tile, matching the filter radius. Tool 1: always check the padding convention (zero-padding vs. no padding / valid-only output) on the problem statement.

REFERENCE KERNEL · VERIFIED IN THIS PHASE
conv2d_tiled.cu
#define TILE 16
#define RADIUS 1   // 3x3 filter

__global__ void conv2dTiled(const float* input, const float* filter, float* output,
                             int H, int W, int filterSize) {
    constexpr int SH = TILE + 2 * RADIUS;
    __shared__ float tile[SH][SH];

    int tx = threadIdx.x, ty = threadIdx.y;
    int baseX = blockIdx.x * TILE - RADIUS;
    int baseY = blockIdx.y * TILE - RADIUS;

    // The shared tile is larger than the output tile. Cooperatively load
    // all TILE+2*RADIUS elements, including the halo/apron region.
    for (int y = ty; y < SH; y += blockDim.y) {
        for (int x = tx; x < SH; x += blockDim.x) {
            int gx = baseX + x;
            int gy = baseY + y;
            tile[y][x] = (gx >= 0 && gx < W && gy >= 0 && gy < H)
                       ? input[gy * W + gx] : 0.0f;
        }
    }
    __syncthreads();

    int outX = blockIdx.x * TILE + tx;
    int outY = blockIdx.y * TILE + ty;
    if (outX < W && outY < H) {
        float acc = 0.0f;
        for (int fy = 0; fy < filterSize; ++fy)
            for (int fx = 0; fx < filterSize; ++fx)
                acc += tile[ty + fy][tx + fx] * filter[fy * filterSize + fx];
        output[outY * W + outX] = acc;
    }
}

3D ConvolutionSame halo-tiling idea with a third axis; a full 3D shared-memory tile can exceed shared memory limits fast, so many practical kernels tile only 2 of the 3 dimensions and loop the third in registers.

2D Jacobi StencilSame halo-tile read pattern (typically a small fixed 5-point stencil), but it's iterative — you apply the stencil repeatedly. This requires two buffers (read from one, write to the other, swap) because in-place updates would let some threads read already-updated neighbor values — a correctness trap, not just a performance one.

6 Family: normalization

Covers: RMS Normalization, Batch Normalization, Group Normalization. All three reuse the reduction skeleton from Family 1, differing only in which axis gets reduced over and whether a mean is subtracted.

Applying the framework

Tool 2: one block per normalization group (one row for RMSNorm, one channel-across-batch for BatchNorm, one channel-group-per-sample for GroupNorm) — same "block owns a row, reduce, then broadcast a scalar back" shape as the softmax family.

rmsnorm_row.cu
__global__ void rmsNorm(const float* in, const float* gamma, float* out,
                          int rows, int cols, float eps) {
    extern __shared__ float row[];
    int r = blockIdx.x;
    int tid = threadIdx.x;

    float localSumSq = 0.0f;
    for (int c = tid; c < cols; c += blockDim.x) {
        row[c] = in[r * cols + c];
        localSumSq += row[c] * row[c];
    }
    // block-wide sum reduction of localSumSq goes here (Family 1 skeleton) -> rms
    __shared__ float rms;
    if (tid == 0) rms = rsqrtf(localSumSq / cols + eps);   // simplified: real version reduces across all threads first
    __syncthreads();

    for (int c = tid; c < cols; c += blockDim.x) {
        out[r * cols + c] = row[c] * rms * gamma[c];
    }
}

7 Family: scan / parallel primitives

Applying the framework

prefix_sum_hillis_steele.cu — inclusive scan, single block
__global__ void inclusiveScan(float* data, int N) {
    extern __shared__ float temp[];
    int tid = threadIdx.x;
    temp[tid] = (tid < N) ? data[tid] : 0.0f;
    __syncthreads();

    // each pass doubles the stride: after log2(N) passes, every element holds its full prefix sum
    for (int stride = 1; stride < blockDim.x; stride *= 2) {
        float valToAdd = (tid >= stride) ? temp[tid - stride] : 0.0f;
        __syncthreads();                 // Tool 6 reflex: read before write hazard without this
        if (tid >= stride) temp[tid] += valToAdd;
        __syncthreads();
    }
    if (tid < N) data[tid] = temp[tid];
}

Covers: Sparse Matrix-Vector Multiplication, Nearest Neighbor. First appearance of genuinely irregular memory access — the amount of work per thread is no longer uniform, which is a new failure mode (load imbalance) beyond anything in Level 1.

Applying the framework

Tool 1: sparse matrices are usually given in CSR format — a values[] array, a colIndex[] array, and a rowPtr[] array marking where each row's nonzeros start/end. Tool 2: one thread (or, better, one warp for load balance) per row.

spmv_csr.cu
__global__ void spmvCSR(const float* values, const int* colIndex, const int* rowPtr,
                          const float* x, float* y, int numRows) {
    int row = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < numRows) {
        float acc = 0.0f;
        for (int j = rowPtr[row]; j < rowPtr[row + 1]; j++) {

    }

Applying the framework — RoPE

Tool 1: input is a sequence of vectors, dimension D (even), each position gets a different rotation angle. Tool 2: fully elementwise per (position, dimension pair) — no cross-thread communication, back to Level 1's Pattern 1 shape despite being "attention adjacent."

rope.cu
__global__ void applyRoPE(float* x, int seqLen, int dim, float theta) {
    int pos = blockIdx.x;                                  // one block per sequence position
    int pairIdx = threadIdx.x;                             // one thread per (dim/2) rotation pair
    if (pos < seqLen && pairIdx * 2 < dim) {
        float freq = 1.0f / powf(theta, (2.0f * pairIdx) / dim);
        float angle = pos * freq;
        float cosA = cosf(angle), sinA = sinf(angle);

        int base = pos * dim + pairIdx * 2;
        float x0 = x[base], x1 = x[base + 1];
        x[base]     = x0 * cosA - x1 * sinA;   // standard 2D rotation applied to each dimension pair
        x[base + 1] = x0 * sinA + x1 * cosA;
    }
}
Applying the framework — Linear Recurrence (shared machinery for SSM Selective Scan)

Tool 2: looks sequential (h_t = a_t·h_{t-1} + b_t) but affine transforms compose associatively — (a₂,b₂)∘(a₁,b₁) = (a₂a₁, a₂b₁+b₂) — so this is exactly Family 7's scan pattern with a 2-tuple combine operator instead of scalar addition. Same Hillis-Steele shape, different combine() function.

linear_recurrence_scan.cu
struct AffinePair { float a, b; };

__device__ AffinePair combine(AffinePair left, AffinePair right) {
    // applying `left` then `right`: h -> right.a * (left.a * h + left.b) + right.b
    return { left.a * right.a, left.b * right.a + right.b };
}

__global__ void linearRecurrenceScan(AffinePair* pairs, int N) {
    extern __shared__ AffinePair temp[];
    int tid = threadIdx.x;
    temp[tid] = (tid < N) ? pairs[tid] : AffinePair{1.0f, 0.0f};  // identity pair for out-of-range
    __syncthreads();

    for (int stride = 1; stride < blockDim.x; stride *= 2) {
        AffinePair left = (tid >= stride) ? temp[tid - stride] : AffinePair{1.0f, 0.0f};
        __syncthreads();
        if (tid >= stride) temp[tid] = combine(left, temp[tid]);
        __syncthreads();
    }
    if (tid < N) pairs[tid] = temp[tid];   // temp[t].b now holds h_t given h_{-1} = 0
}

11 Family: FFT

Covers: 2D FFT. The most conceptually different problem in Level 2 — worth knowing the shape of the algorithm even though production code almost always calls a library (cuFFT) rather than hand-rolling this.

Search current cuFFT documentation before assuming any specific API surface — library APIs shift between CUDA toolkit versions more than the algorithmic idea below does.

A 2D FFT is separable: run a 1D FFT on every row, then a 1D FFT on every column of the result. Each 1D FFT (radix-2 Cooley-Tukey) is a sequence of log₂(N) "butterfly" passes over a bit-reversal-permuted input:

fft_butterfly_stage.cu — one radix-2 butterfly pass
__global__ void butterflyStage(float2* data, int N, int stage) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int halfStage = 1 << stage;
    int groupSize = halfStage * 2;
    int groupStart = (idx / halfStage) * groupSize;
    int posInGroup = idx % halfStage;

    if (idx * 2 < N) {
        float angle = -2.0f * 3.14159265f * posInGroup / groupSize;
        float2 twiddle = make_float2(cosf(angle), sinf(angle));

        float2 a = data[groupStart + posInGroup];
        float2 b = data[groupStart + posInGroup + halfStage];
        float2 t = make_float2(b.x * twiddle.x - b.y * twiddle.y, b.x * twiddle.y + b.y * twiddle.x);

        data[groupStart + posInGroup]             = make_float2(a.x + t.x, a.y + t.y);
        data[groupStart + posInGroup + halfStage] = make_float2(a.x - t.x, a.y - t.y);
    }
}

Launched once per stage (stage = 0 … log₂(N)-1), with a cudaDeviceSynchronize() or kernel-boundary between stages since each stage depends on the previous one completing across the whole array — this is Part A Tool 3's global synchronization case where __syncthreads() alone isn't enough because the dependency spans multiple blocks.

1 Family: attention variants

Covers: Causal Self-Attention, Multi-Head Attention, Linear Self-Attention, Sliding Window Self-Attention. Level 2 built attention as three separate passes (materialize scores, softmax, multiply by V). Level 3's version fuses this into one pass using online softmax — the technique behind FlashAttention — which never materializes the full N×N score matrix.

Applying the framework — the online softmax recurrence

Tool 3 escalation, delivering on Level 2's promise: as you sweep through key/value tiles, maintain a running max m, running sum l, and running output O. Every time a new tile's max exceeds the running max, rescale everything accumulated so far instead of recomputing from scratch:

  • m_new = max(m_old, rowmax(S_tile))
  • correction = exp(m_old - m_new)
  • l_new = l_old * correction + rowsum(exp(S_tile - m_new))
  • O_new = O_old * correction + exp(S_tile - m_new) @ V_tile
Phase 1 correction: this recurrence is the mathematical teaching bridge to FlashAttention, not a complete production kernel. The production implementation must perform the QK dot-product reduction across threads and then add architecture-specific tiling, Tensor Core execution, masking, synchronization, and pipelined data movement. Those belong to later phase phases.

online_softmax_attention.pseudo.cu
// Educational pseudocode: demonstrates the numerically-stable online-softmax
// recurrence. It intentionally omits the real cross-thread QK reduction,
// Tensor Core execution, tiling strategy, masking machinery, and pipeline
// synchronization required by a production FlashAttention implementation.

for each query row q: {
    float m = -INFINITY;
    float l = 0.0f;
    vector acc = zeros(headDim);

    for each key/value tile (K_tile, V_tile): {
        S_tile = q @ transpose(K_tile) / sqrt(headDim);
        apply_causal_mask_if_needed(S_tile);

        tileMax = rowmax(S_tile);
        mNew = max(m, tileMax);
        correction = exp(m - mNew);
        P_tile = exp(S_tile - mNew);

        l = l * correction + rowsum(P_tile);
        acc = acc * correction + P_tile @ V_tile;
        m = mNew;
    }

    output[q] = acc / l;
}

3 Family: sorting

Covers: Sorting, Radix Sort. Two different parallelization philosophies: bitonic sort is comparison-based and works on any orderable type but does more total work; radix sort is non-comparison, less total work, but only works on fixed-width keys (integers) and needs Level 2's histogram + scan machinery as a subroutine.

Applying the framework — bitonic sort

Tool 2: a bitonic sorting network compares and conditionally swaps fixed pairs of elements in log₂(N) stages, each with log₂(N) sub-stages — O(N log²N) work but each stage's span is O(1), giving fantastic parallelism at the cost of doing more total comparisons than a comparison-optimal sort. Requires N to be a power of 2 (pad with +∞ otherwise).

bitonic_sort_stage.cu — one compare-exchange stage
__global__ void bitonicStage(float* data, int j, int k) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int partner = idx ^ j;   // XOR trick: the classic bitonic partner-index formula

    if (partner > idx) {
        bool ascending = ((idx & k) == 0);
        if ((data[idx] > data[partner]) == ascending) {
            float tmp = data[idx]; data[idx] = data[partner]; data[partner] = tmp;
        }
    }
}
// host loop: for (k = 2; k <= N; k *= 2) for (j = k/2; j > 0; j /= 2) bitonicStage<<<...>>>(data, j, k);
// each (j,k) pair is a separate kernel launch — the network's stages have a strict order (global sync)

Radix Sort processes 4 or 8 bits at a time: for each digit, build a histogram of digit values (Level 2 Family 7's atomic histogram), exclusive-prefix-sum the histogram to get each digit-bucket's starting offset (Level 2 Family 7's scan), then scatter every element to bucketOffset[digit] + rankWithinBucket. This is a stable counting sort per digit, repeated once per digit — again one kernel-launch boundary per digit pass, since the next pass needs the previous pass's fully-scattered output.

4 Family: K-Means clustering

Covers: K-Means Clustering. An iterative two-kernel loop: assign each point to its nearest centroid (Level 2 Family 9's nearest-neighbor reduction), then recompute centroids as the mean of their assigned points (a scatter-add reduction, needing atomics since many points can target the same centroid).

kmeans_assign_and_update.cu
__global__ void assignClusters(const float2* points, const float2* centroids,
                              int* assignments, int numPoints, int K) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < numPoints) {
        float bestDist = INFINITY; int bestK = 0;
        for (int c = 0; c < K; c++) {
            float dx = points[idx].x - centroids[c].x, dy = points[idx].y - centroids[c].y;
            float dist = dx*dx + dy*dy;
            if (dist < bestDist) { bestDist = dist; bestK = c; }   // reduction to (argmin, value)
        }
        assignments[idx] = bestK;
    }
}

__global__ void updateCentroidsSum(const float2* points, const int* assignments,
                                 float2* centroidSums, int* centroidCounts, int numPoints) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < numPoints) {
        int c = assignments[idx];
        atomicAdd(&centroidSums[c].x, points[idx].x);   // scatter-add: many points -> few centroids
        atomicAdd(&centroidSums[c].y, points[idx].y);
        atomicAdd(&centroidCounts[c], 1);
    }
}

5 Family: graph algorithms

Covers: BFS Shortest Path, All-Pairs Shortest Paths. Both need correctness guarantees that __syncthreads() cannot provide, because the dependency spans the entire grid, not just one block — the clearest illustration in this whole roadmap of Part A's rule that global synchronization requires a kernel-launch boundary.

bfs_level_sync.cu
__global__ void bfsExpandFrontier(const int* rowPtr, const int* colIndex,
                                int* distances, const int* frontier, int frontierSize,
                                int* nextFrontier, int* nextFrontierCount, int currentLevel) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < frontierSize) {
        int node = frontier[idx];
        for (int e = rowPtr[node]; e < rowPtr[node + 1]; e++) {
            int neighbor = colIndex[e];
            // atomicCAS: only the FIRST thread to reach `neighbor` claims it — avoids duplicate frontier entries
            if (atomicCAS(&distances[neighbor], -1, currentLevel + 1) == -1) {
                int pos = atomicAdd(nextFrontierCount, 1);   // claim a slot in next frontier
                nextFrontier[pos] = neighbor;
            }
        }
    }
}
// host loop: launch once per BFS level, swap frontier<->nextFrontier, until nextFrontierCount == 0
// this is a strict kernel-per-level boundary: level L+1's correctness depends on ALL of level L finishing first

__global__ void floydWarshallStep(float* dist, int V, int k) {
    int i = blockIdx.y * blockDim.y + threadIdx.y;

    if (i < V && j < V) {
        float viaK = dist[i * V + k] + dist[k * V + j];
        if (viaK < dist[i * V + j]) dist[i * V + j] = viaK;
    }
}
// host loop: for (int k = 0; k < V; k++) floydWarshallStep<<<...>>>(dist, V, k);
// EVERY thread's read of dist[i*V+k] and dist[k*V+j] must see the FULLY updated matrix from iteration k-1 —
// this is why k cannot be a loop inside the kernel: it needs a grid-wide barrier, which only a new launch gives you

6 Family: FFT (completing the picture)

Covers: Fast Fourier Transform. Level 2 built the butterfly stage kernel; the missing piece for a correct Cooley-Tukey FFT is the bit-reversal permutation that must run before the butterfly stages.

bit_reversal_permute.cu
__device__ unsigned int reverseBits(unsigned int x, int numBits) {
    unsigned int result = 0;
    for (int i = 0; i < numBits; i++) {
        result = (result << 1) | (x & 1);
        x >>= 1;
    }
    return result;
}

__global__ void bitReversalPermute(float2* data, int N, int numBits) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        unsigned int rev = reverseBits((unsigned int)idx, numBits);
        if (rev > (unsigned int)idx) {   // swap each pair exactly once
            float2 tmp = data[idx]; data[idx] = data[rev]; data[rev] = tmp;
        }
    }
}
// full 1D FFT: bitReversalPermute once, then Level 2's butterflyStage once per stage (log2(N) launches)

7 Family: multi-agent simulation

Covers: Multi-Agent Simulation. Every agent's update depends on every other agent — an O(N²) all-pairs interaction, structurally identical to the classic N-body problem and to GEMM's data-reuse shape (Level 2 Family 3), just with a physics update instead of a dot product.

Applying the framework

Tool 2: naive version is one thread per agent, looping over all N other agents directly from global memory — memory-bound in exactly the way naive matmul was. Tool 3 escalation: tile other agents' positions into shared memory in chunks, exactly like GEMM's tiling, so each block re-reads agent data from fast shared memory instead of global memory.

multi_agent_naive.cu
__global__ void updateAgents(const float2* positions, float2* velocities, int N, float dt) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N) {
        float2 myPos = positions[idx];
        float2 force = make_float2(0.0f, 0.0f);
        for (int j = 0; j < N; j++) {          // every agent reads every other agent — Tool 2's memory-bound flag
            if (j == idx) continue;
            float dx = positions[j].x - myPos.x, dy = positions[j].y - myPos.y;
            float distSq = dx*dx + dy*dy + 1e-4f;   // softening term avoids divide-by-zero at close range
            float invDist3 = rsqrtf(distSq * distSq * distSq);
            force.x += dx * invDist3; force.y += dy * invDist3;
        }
        velocities[idx].x += force.x * dt; velocities[idx].y += force.y * dt;
    }
}
// optimization path: tile `positions` through shared memory in chunks (identical structure to gemmTiled's
// cooperative load loop), so each block re-reads other agents' positions from shared memory, not global

The one thing to remember if everything else is forgotten

Almost every kernel in this roadmap — 86 problems across 3 tiers — reduces to some combination of four ideas: (1) one thread per output, guarded by a boundary check; (2) shared memory to avoid re-reading global memory (tiling, halos, row caching); (3) a tree/scan reduction when threads need to combine results; (4) numerical stability (max-subtraction, fp32 accumulation) whenever exponentials or long accumulations are involved. Every "hard" problem in Level 3 is 2–3 of these four ideas stacked together, not a fifth idea you haven't seen.

Lesson 0.1

What LeetGPU is

Think of LeetGPU as a GPU engineering laboratory. You receive a computational specification, write an implementation, execute it, test correctness and optimize performance. The objective is not merely algorithmic correctness; the environment is designed around high-performance GPU programming.

Lesson 0.2

The Challenge page

The challenge catalogue is where the practical curriculum lives. Do not treat it as a list to grind from top to bottom. Use it as a map of computational patterns: elementwise work, reductions, memory movement, matrix operations, ML primitives, attention, inference and advanced algorithms.

Lesson 0.3

Run vs Submit

Run belongs to your development loop. Use it repeatedly while fixing code and testing hypotheses. Submit is a judged checkpoint. Do not turn every half-working experiment into a submission. Current challenge pages expose Run and Submit alongside Submissions, Leaderboard, Solutions and Discuss.

Lesson 0.4

Submissions

Treat submissions as an experiment history. A useful history answers: “What changed between version A and B, and what did the benchmark teach me?” Do not merely chase the highest number.

Lesson 0.5

Leaderboard

A leaderboard is a performance reference. It tells you that stronger implementations exist, and can reveal the magnitude of optimization possible. It does not tell you which concept you should learn next.

Lesson 0.6

Solutions are second-pass material. Discussions are community intelligence. Use them after an honest attempt, preferably with a precise question: “Why is this implementation memory-bound?” rather than “Give me the answer.”

Phase 1 · GPU Mental Model

Before CUDA syntax, understand the execution model.

The first goal is not memorizing API calls. The first goal is learning to look at a computation and ask: what can execute independently?

CPU

Serial mindset

Imagine one instruction stream progressing through work. Loops are the default mental model.

GPU

Massively parallel mindset

Look for many independent pieces of work that can be assigned to many threads.

KERNEL

GPU function

A kernel describes work that many GPU threads execute according to the same program structure.

CPU thinking for i = 0 ... N-1: C[i] = A[i] + B[i] GPU thinking ┌─────────────── GPU ───────────────┐ │ │ A[0], B[0] ──┤ Thread 0 → C[0] │ A[1], B[1] ──┤ Thread 1 → C[1] │ A[2], B[2] ──┤ Thread 2 → C[2] │ A[3], B[3] ──┤ Thread 3 → C[3] │ ... │ ... │ A[N], B[N] ──┤ Thread N → C[N] │ └───────────────────────────────────┘
Lesson 1.1 · The first question

Can the outputs be computed independently?

If C[i] depends only on A[i] and B[i], then one output does not need another output. That is an extremely GPU-friendly pattern. The moment outputs depend on each other, or many threads need to update the same location, the problem becomes more interesting.

Lesson 1.2 · Thread → work mapping

Every thread needs to know what it owns.

For a one-dimensional workload, a common CUDA mapping is: 

int idx = blockIdx.x * blockDim.x + threadIdx.x;

Read this as: which block am I in? × how many threads are in each block? + which thread am I inside the block?

The important skill is not memorizing the equation. It is being able to derive why it identifies a unique global position for a thread.

Readiness gate for the first challenge: You should be able to draw a box containing several threads, assign each thread a different array index, and explain why two threads must not accidentally write to the same output element.
Challenge Module 01 · Vector Addition

Vector Addition — your first real GPU laboratory

The supplied challenge catalogue defines this as an Easy challenge: perform element-wise addition of two vectors containing 32-bit floating-point values. This is the first practical bridge between the GPU mental model and the LeetGPU environment.

THE PROBLEM

What are we computing?

Given vectors A and B, produce C where:

C[i] = A[i] + B[i]

Each output element can be computed independently.

WHY GPU?

Why is this GPU-friendly?

There is no dependency between C[0], C[1], C[2] and so on. The work can be distributed across many threads.

1. Translate the problem into parallel work

Sequential view i = 0 → C[0] = A[0] + B[0] i = 1 → C[1] = A[1] + B[1] i = 2 → C[2] = A[2] + B[2] ... i = N-1 → C[N-1] = A[N-1] + B[N-1] Parallel view Thread 0 → C[0] Thread 1 → C[1] Thread 2 → C[2] ... Thread N-1 → C[N-1]

2. Decide thread ownership

The cleanest first decomposition is one thread owns one output element. This makes correctness easy to reason about: thread i reads A[i] and B[i], then writes C[i].

Engineering question

What happens when there are more threads than elements?

You normally launch enough threads to cover the input, often rounding the number of threads up to a convenient block size. The kernel then checks whether its calculated index is inside the valid range. 

if (idx < N) {
    C[idx] = A[idx] + B[idx];
}

This boundary check is not decorative. Without it, extra threads can access memory beyond the valid array.

3. Understand the kernel before using it

__global__ void vector_add(
    const float* A,
    const float* B,
    float* C,
    int N
) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;

    if (idx < N) {
        C[idx] = A[idx] + B[idx];
    }
}

4. The host launch

int threadsPerBlock = 256;
int blocksPerGrid =
    (N + threadsPerBlock - 1) / threadsPerBlock;

vector_add<<<blocksPerGrid, threadsPerBlock>>>(A, B, C, N);
Do the arithmetic yourself. If N = 1000 and threadsPerBlock = 256, the grid needs 4 blocks. That creates 1024 thread slots. The final 24 threads must fail the idx < N check.

5. Correctness before speed

Before worrying about optimization, test mental edge cases:

N = 1

Does exactly one valid output get written?

N = block size

Does the boundary align exactly?

N = block size + 1

Does the next block handle the final element?

6. Now think about performance

Vector addition performs very little arithmetic: one addition per output. Each output requires reading two values and writing one value. That means the workload moves substantially more data than it computes. This makes it a useful first introduction to the idea that some GPU workloads are constrained more by memory movement than by arithmetic throughput.

Performance concept

Arithmetic intensity

Arithmetic intensity asks, roughly: how much computation do we perform for the amount of data moved? Vector addition has very little arithmetic per byte moved. That makes it a terrible place to learn fancy tiling tricks—and an excellent place to learn why memory behavior matters.

Challenge Module 02

Matrix Addition

2D indexing → one thread, one output element

Matrix addition is the same computational idea as vector addition, but the data now has two coordinates. For matrices A and B with the same shape, C[i,j] = A[i,j] + B[i,j]. The important new lesson is not the addition; it is learning how a two-dimensional mathematical coordinate becomes a one-dimensional memory address and how a 2D grid of threads can map naturally onto the output.

Mental model

A[0,0] + B[0,0] → C[0,0] A[0,1] + B[0,1] → C[0,1] A[1,0] + B[1,0] → C[1,0] ... C[row,col] = A[row,col] + B[row,col]

Tiny implementation pattern

int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;

if (row < rows && col < cols) {
    int idx = row * cols + col;
    C[idx] = A[idx] + B[idx];
}

Questions you must be able to answer

Why is a 2D problem sometimes stored as a 1D array? What does row * cols + col mean? What breaks if you accidentally use rows instead of cols in the stride?

Next: Matrix Addition → Matrix Copy → Matrix Transpose
Challenge Module 03

Matrix Copy

memory movement → layout → contiguous access

Matrix Copy removes almost all arithmetic. The output is simply a copy of the input. That makes it a useful laboratory for separating computation from data movement. If a kernel does almost no math, the question becomes: how efficiently are threads reading and writing memory?

Mental model

Input matrix ┌───────┐ │ a b c │ │ d e f │ ─────────► Output matrix │ g h i │ ┌───────┐ └───────┘ │ a b c │ │ d e f │ │ g h i │ └───────┘

Tiny implementation pattern

int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;

if (row < rows && col < cols) {
    int idx = row * cols + col;
    output[idx] = input[idx];
}

Questions you must be able to answer

Why is this almost entirely a memory-traffic problem? Are neighboring threads reading neighboring addresses? Are they writing neighboring addresses?

Next: Matrix Copy → Matrix Transpose
Challenge Module 04

Reverse Array

index transformation → ownership without communication

Reversing an array is a beautiful early example of a transformation where the computation is independent, but the mapping is not identity. Thread i owns output i, but reads input N - 1 - i. The GPU lesson is that parallelism does not require the input and output indices to be the same.

Mental model

Output index: 0 1 2 3 4 Input index: 4 3 2 1 0 C[i] = A[N - 1 - i]

Tiny implementation pattern

int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < N) {
    output[i] = input[N - 1 - i];
}

Questions you must be able to answer

Can every output still be computed independently? Does reversing require synchronization? What memory-access pattern does the input read create?

Next: Reverse Array → Value Clipping → Matrix Copy
Challenge Module 05

ReLU / Leaky ReLU

elementwise nonlinearities → branch behavior

ReLU is max(0,x). Leaky ReLU keeps a small negative slope. These are still elementwise kernels, so they reinforce the one-thread-one-output pattern while introducing a conditional operation. That makes them an early opportunity to think about branches and numerical behavior.

Mental model

ReLU(x) = max(0, x) LeakyReLU(x) = x if x >= 0 αx if x < 0

Tiny implementation pattern

float x = input[i];
output[i] = x > 0.0f ? x : alpha * x;

Questions you must be able to answer

How many memory operations occur per output? Is the operation compute-heavy? What happens when neighboring threads take different branches?

Next: ReLU → Leaky ReLU → Sigmoid / SiLU later
Challenge Module 06

Value Clipping

elementwise bounds → simple control logic

Clipping constrains every value to an interval [lo, hi]. It is conceptually simple but teaches an important engineering pattern: a GPU kernel can implement a transformation that combines multiple comparisons while keeping each output independent.

Mental model

clip(x, lo, hi) = min(max(x, lo), hi)

Tiny implementation pattern

float x = input[i];
x = max(x, lo);
x = min(x, hi);
output[i] = x;

Questions you must be able to answer

Why can this still be one-thread-one-output? What edge cases occur when lo > hi? What assumptions does the challenge specification make?

Next: Value Clipping → Matrix Copy / elementwise ML kernels
Challenge Module 07

Interleave Arrays

multiple input streams → deterministic output mapping

Interleaving asks you to combine independent arrays into a structured output. The arithmetic is trivial; the indexing is the lesson. You learn to derive an output position from a logical pair rather than assuming that every kernel is simply C[i] = f(A[i]).

Mental model

A = [a0 a1 a2] B = [b0 b1 b2] Output = [a0 b0 a1 b1 a2 b2]

Tiny implementation pattern

int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < N) {
    output[2*i]   = A[i];
    output[2*i+1] = B[i];
}

Questions you must be able to answer

Each logical input element now produces two output positions. What changes in memory traffic? How do you avoid two threads writing the same output?

Next: Interleave Arrays → RGB to Grayscale → more layout transformations
Challenge Module 08

RGB to Grayscale

multi-channel data → weighted elementwise transform

RGB-to-grayscale introduces structured channels. A grayscale value is typically a weighted combination of the red, green and blue components. The important lesson is that the mathematical operation remains independent per pixel even though each output consumes several input values.

Mental model

gray = wr*R + wg*G + wb*B One pixel → one logical unit of work One thread → one pixel

Tiny implementation pattern

float r = input[3*i + 0];
float g = input[3*i + 1];
float b = input[3*i + 2];
output[i] = wr*r + wg*g + wb*b;

Questions you must be able to answer

Why is one thread per pixel a better mental model than one thread per scalar channel? How does channel layout affect memory access?

Next: RGB to Grayscale → convolution/image kernels
Challenge Module 09

Sigmoid / SiLU / GELU family

elementwise ML math → numerical function implementation

Activation functions show that GPU programming is not only about loops and memory. You are translating a mathematical function into thousands of independent evaluations. This becomes important later because transformer and neural-network kernels are built from these primitives.

Mental model

Sigmoid(x) = 1 / (1 + exp(-x)) SiLU(x) = x * sigmoid(x) GELU is a smoother nonlinear gating function used widely in neural networks.

Tiny implementation pattern

int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < N) {
    float x = input[i];
    output[i] = x / (1.0f + expf(-x)); // SiLU
}

Questions you must be able to answer

Where does numerical precision matter? Why might exp() be much more expensive than an integer add? Which parts are memory traffic and which parts are arithmetic?

Next: Activation kernels → Softmax / normalization
Challenge Module 10

Simple Inference

from primitive kernel → small ML computation

A simple inference challenge is the point where isolated elementwise operations start becoming a model-like computation. The lesson is decomposition: identify which parts are matrix operations, which are elementwise, and where intermediate tensors are produced.

Mental model

Challenge Module 11

Matrix Transpose

memory access pattern → coalescing → layout transformation

Transpose is the first Phase 2 challenge where a correct kernel can still be fundamentally inefficient because of how threads touch memory. The mathematical operation is simple: output[row,col] = input[col,row]. The engineering problem is that a row-major matrix is contiguous across columns, so a naive transpose can make neighboring threads access memory far apart.

Mental model

Input A Output B a b c d a e i m e f g h transpose → b f j n i j k l c g k o m n o p d h l p

Tiny implementation / reasoning pattern

int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;

if (row < rows && col < cols) {
    output[col * rows + row] =
        input[row * cols + col];
}

Questions you must be able to answer

Why can the naive kernel be slow even though every output is independent? Which side of the operation has contiguous accesses? What happens to global-memory transactions when neighboring threads read or write strided addresses?

Next: Learn coalescing first. Then compare naive transpose with a tiled transpose.
Concept Module 12

Memory Coalescing

warp-level memory access → contiguous transactions

Memory coalescing is the idea that GPU memory systems work best when threads that execute together access memory in a pattern that can be served efficiently by a small number of memory transactions. The key mental shift is: do not ask only what each thread reads; ask what a group of neighboring threads reads together.

Mental model

Good pattern Thread 0 → A[0] Thread 1 → A[1] Thread 2 → A[2] Thread 3 → A[3] ... Bad / strided pattern Thread 0 → A[0] Thread 1 → A[stride] Thread 2 → A[2*stride] Thread 3 → A[3*stride] ...

Tiny implementation / reasoning pattern

// Conceptual view:
int i = global_thread_id;
x = input[i];          // neighboring threads → neighboring addresses

// Compare with:
x = input[i * stride]; // large stride → poorer locality

Questions you must be able to answer

Why is contiguous access a property of the group, not merely one thread? Why can changing the thread-to-data mapping change performance without changing the mathematical result?

Next: Use Matrix Transpose as the laboratory for turning this concept into practice.
Concept Module 13

Memory Locality & Reuse

Locality asks whether useful data that is near one access is likely to be useful again soon. Reuse asks whether the same loaded value can serve multiple computations. These ideas become the foundation for tiling later.

Mental model

Without reuse: load A[x] → use once load A[y] → use once load A[x] again → same value fetched again With reuse: load tile → shared working set ├─ thread 0 uses A[x] ├─ thread 1 uses A[x] ├─ thread 2 uses A[x] └─ ...

Tiny implementation / reasoning pattern

The optimization question is not:
"Can I put this in shared memory?"

It is:
"Which data is reused enough that staging it can reduce expensive global-memory traffic?"

Questions you must be able to answer

What data is reused? How many times? What is the cost of loading it once versus repeatedly? When does synchronization become worth paying?

Concept Module 14

Shared Memory

Shared memory gives threads in a block a fast, explicitly managed storage area. It is especially useful when multiple threads need the same nearby data or when the global-memory access pattern is inconvenient.

Global memory ↓ load a tile ↓ ┌─────────────────────┐ │ shared-memory tile │ │ a b c d │ │ e f g h │ │ i j k l │ └─────────────────────┘ ↓ ↓ ↓ ↓ many threads reuse it

Concept Module 15

Tiled Matrix Transpose

tiling → coalesced global access → shared-memory rearrangement

The classic transpose optimization is a perfect Phase 2 laboratory. Threads load a tile from global memory coalesced, synchronize, then read the tile in a different orientation so the global write can also be efficient. The tile acts as a layout-conversion buffer.

Mental model

Global load: coalesced ↓ ┌───────────────┐ │ A tile │ │ loaded by │ │ neighboring │ │ threads │ └───────────────┘ ↓ synchronize ↓ tile[row][col] → tile[col][row] ↓ Global store: coalesced

Tiny implementation / reasoning pattern

__shared__ float tile[TILE][TILE];

int x = blockIdx.x * TILE + threadIdx.x;
int y = blockIdx.y * TILE + threadIdx.y;

if (x < cols && y < rows)
    tile[threadIdx.y][threadIdx.x] = input[y * cols + x];

__syncthreads();

int tx = blockIdx.y * TILE + threadIdx.x;
int ty = blockIdx.x * TILE + threadIdx.y;

if (tx < rows && ty < cols)
    output[ty * rows + tx] =
        tile[threadIdx.x][threadIdx.y];

Questions you must be able to answer

Why does the tile fix the access pattern? Why is the synchronization inside the block sufficient? What happens at matrix edges that are not multiples of TILE?

Challenge Module 22

Reduction

many inputs → one result → parallel tree

Reduction is the first major break from the one-thread-one-output pattern. Every output depends on many inputs. A sum reduction asks for one value such as sum(x[0:N]). A serial loop is easy, but it exposes the fundamental GPU problem: many threads must cooperate to produce a smaller amount of information.

Mental model

[1 2 3 4 5 6 7 8] Round 1: [3 7 11 15] Round 2: [10 26] Round 3: [36] Many values → fewer values → one value

Tiny implementation / reasoning pattern

// conceptual tree reduction
for (int stride = 1; stride < N; stride *= 2) {
    if (2 * stride * tid < N)
        partial[tid] += partial[tid + stride];
    synchronize();
}

Questions you must be able to answer

Where can two threads try to update the same value? Why is synchronization necessary? How does the amount of parallel work shrink at each reduction stage?

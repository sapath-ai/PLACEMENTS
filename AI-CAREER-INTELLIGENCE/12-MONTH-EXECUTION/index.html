Core Fine-Tuning Skills

LoRA / QLoRA + Unsloth Pipeline

  • Fine-tune Llama 3.1 (7B) or Mistral (7B) on a domain-specific dataset using LoRA or QLoRA. Use Unsloth for memory efficiency. Document training loss curves, eval metrics, inference latency, memory usage.
  • Understand LoRA theory: low-rank approximation of weight updates, why rank r determines parameter count. Know the math: ΔW = BA where B ∈ R^(d×r), A ∈ R^(r×k).
  • Understand QLoRA: 4-bit NF4 quantization + LoRA, double quantization, paged optimizers for memory. Know the trade-offs vs LoRA.
  • Choose a meaningful fine-tuning dataset — not just Alpaca. Use a real domain task: medical QA, code generation for a specific language, legal document summarization, financial analysis.
  • Run proper evaluation: ROUGE, BLEU, BERTScore for text tasks. Use a held-out test set. Compare base model vs fine-tuned. Document everything in README.
  • Implement DPO (Direct Preference Optimization) as an alternative alignment method. Compare to SFT (supervised fine-tuning) on a preference dataset.

Vector Databases & Embeddings

Internalize the Vector Search Stack

  • Understand HNSW indexing (Hierarchical Navigable Small World): how approximate nearest neighbor search works, the time-accuracy trade-off, ef_construction vs ef parameters.
  • Know the trade-offs between cosine similarity vs dot product vs L2 distance — and when to use each. This is a common interview question.
  • Set up and use at least two vector databases: Pinecone (managed) and Weaviate or pgvector (self-hosted). Understand metadata filtering strategies.
  • Implement several embedding models and benchmark them: OpenAI text-embedding-3-large, Cohere Embed, sentence-transformers (all-mpnet, bge-m3). Know their dimensionality, cost, and performance on benchmarks (MTEB).
  • Understand chunking strategies: fixed-size, sentence-level, recursive, semantic chunking (late chunking). Know the impact of chunk size on retrieval quality.

Project Quality Standards

What Makes a Hiring-Manager-Stopping GitHub Repo

  • README must contain: (1) Clear problem statement, (2) Architecture diagram, (3) Results with metrics vs baseline, (4) Technical decisions documented — WHY you chose RAG vs fine-tuning, transformer vs LSTM, etc., (5) Failure modes and limitations section, (6) How to reproduce locally in under 5 minutes.
  • Clean commit history: No single "initial commit" mega-dump. Commits should tell the story of development: "Add HNSW indexing to vector store", "Fix gradient explosion in transformer training", "Add Grad-CAM++ visualization".
  • Live demo or video walkthrough: HuggingFace Spaces (free), Streamlit Community Cloud (free), or screen recording on YouTube. No demo = the project didn't happen.
  • Evaluation section: What is the accuracy, latency, cost per query, memory footprint? Numbers matter. "The model performs well" is meaningless. "The model achieves 0.84 AUC-ROC at 230ms P95 latency on a T4 GPU, compared to the baseline of 0.71 AUC-ROC" is a signal of engineering maturity.

01

The Big Picture

What is this problem? You're handed one number per day — the stock's closing price. You may buy on exactly one day and sell on a later day. You want the trade that makes the most money. That's it. No shorting, no multiple trades, no crystal ball — just one clean read of a list of numbers.

Why interviewers love it. It looks like arithmetic, but it's really a test of whether you can resist the obvious-but-slow instinct (compare every pair of days) and instead notice that the problem has much less "memory" than it seems to. That noticing — realizing you don't need to remember everything, only one running fact — is the core skill interviewers are actually screening for.

What it develops. This problem is your first real exposure to single-pass, constant-memory reasoning: scanning data exactly once while carrying forward only the summary you truly need. That skill reappears constantly — it's the same instinct behind streaming analytics, cache eviction, and real-time monitoring dashboards.

Where it shows up in real life and real software. A monitoring system watching server latency wants to know "how much did the worst dip recover by" without storing every past reading. A shopper watching a price tracker wants to know the best moment they could have bought, using only what they've seen so far. Even everyday decisions — "should I have bought plane tickets sooner?" — are this exact shape: a stream of values, and a running "best reference point so far."

02

Understanding the Problem

Let's slow the problem down into plain statements before touching any code.

INPUT
A list of daily prices, e.g. [7, 1, 5, 3, 6, 4]. Index = day number, value = price that day.
OUTPUT
A single number: the maximum profit obtainable from one buy followed by one later sell.
CONSTRAINTS
1 ≤ prices.length ≤ 10⁵. Prices are non-negative integers. Only one buy and one sell, total.
Why must buying happen before selling?
You can't sell a stock you don't yet own. If day i is your buy day, your sell day j must satisfy j > i. This ordering constraint is the whole reason the "compare every pair" brute force even needs the restriction j > i — and it's exactly the constraint the optimal algorithm respects for free, since it only ever looks backward at prices already seen.
Why only one transaction?
This version of the problem caps you at a single buy and a single sell. That restriction is what keeps the answer to "one interval, one dip, one rise." (LeetCode has a follow-up variant, Best Time to Buy and Sell Stock II, where unlimited transactions are allowed — we'll touch on how the strategy changes for that in the pattern-recognition section.)
Why is returning 0 sometimes correct?
If prices only ever fall — like [7,6,4,3,1] — every possible trade loses money. Since you're never forced to trade, the best move is to not trade at all, which yields a profit of exactly 0. The algorithm needs to recognize "doing nothing" as a valid, sometimes-optimal answer.

05

Discovering the Better Idea

Don't jump to the answer — interrogate the brute force instead. Click each question to think about it, then reveal.

What information do we actually need, standing on day i?
To evaluate "sell today," we don't need every individual price before today — we only need to know one thing: the lowest price among all of them. That single number is enough to compute the best possible profit if today is the sell day.
Do we need to remember every previous price?
No. Once we know the minimum price so far, every other previous price is strictly worse to buy at (it can only produce equal or smaller profit). They can be safely forgotten.
If today's selling price is fixed, which buying day maximizes profit?
Always the day with the smallest price seen so far. Buying any higher than the historical minimum can only shrink the profit, never grow it. This is the entire insight in one sentence.
So what's the only "memory" the algorithm needs to carry forward?
Two numbers: the minimum price seen so far, and the maximum profit found so far. Everything else — the full history of prices — can be thrown away the moment it's been used to update those two numbers.
06

The Key Insight

Say it plainly: we never need all previous prices — we only need the cheapest one we've seen. Every day, two questions get asked, in this order:

1. "Is today's price a new record low?" → if so, update the minimum.
2. "If I'd bought at the minimum and sold today, is that better than my best profit so far?" → if so, update the best profit.

09
Why the Algorithm Works

      

        
The claim to prove: tracking the smallest price seen so far, and comparing today's price against only that number, is guaranteed to find the true maximum possible profit — even though we never explicitly compare every pair of days.

        
The reasoning: for any fixed sell day j, the best possible buy day is whichever earlier day had the lowest price — there's no other buy day that could produce a larger prices[j] − prices[buy_day]. Our running minimum, by construction, always equals "the lowest price among all days before now." So at every single day j, when we compute prices[j] − min_so_far, we are computing exactly the best possible profit achievable if j is the sell day. Since we do this check on every day, and keep the largest result, we're guaranteed to have checked the best profit for the true optimal sell day too — we just never had to compare it against every candidate buy day individually, because the running minimum already is that comparison, pre-computed.

        
In other words: the brute force's inner loop asked "which buy day was best for this sell day?" — one comparison at a time. The running minimum answers that same question in O(1), because it's been silently comparing all along.

Complexity

      

        
Brute force: for each of n buy days, we scan up to n sell days → O(n²) time. Optimal: one single pass over the array, carrying two variables → O(n) time, O(1) extra space (no matter how long the price list is, we only ever store min_price and max_profit).

Common Mistakes

      

        
✕
Selling before buyingComparing prices[i] to a later prices[j] where j < i — always require the sell index to come after the buy index.

        
✕
Resetting the minimum incorrectlyThe minimum should only ever go down (or stay the same) as you scan forward — never reset it back up or recompute it from scratch each day.

        
✕
Updating profit before updating the minimumOrder matters: check whether today is a new minimum first, then compute today's potential profit — otherwise you might compute a "profit" using tomorrow's low as if it were available today.

        
✕
Forgetting to return 0If every day's price is lower than the last, no profitable trade exists — the answer must default to 0, not a negative number.

        
✕
Confusing today's profit with the max profitToday's price − min_so_far is just one candidate. It must be compared against — and only overwrite — the running maximum, never used directly as the final answer.

        
✕
Using nested loops out of habitIf you find yourself writing a loop inside a loop for this problem, it's a sign you're re-deriving information (the minimum) that a single running variable already gives you for free.

      

    


    
    

      
12
Interview Thinking

      
Imagine the interviewer asking these live. Click a question, think for a moment, then reveal the answer.

      

        
Q.Can you explain your intuition in one sentence?
"At every day, the most profitable possible sale is today's price minus the lowest price seen so far — so I just track that running minimum and the best profit it's produced."

        
Q.Why does a single pass work here?
Because the only piece of history that matters for any future decision — the minimum price — can be maintained incrementally. There's no need to look backward more than once per element.

        
Q.Why don't you need all previous prices?
Every price except the running minimum is provably a worse buy point than the minimum itself, so keeping them around adds memory without adding any correctness.

        
Q.Could you solve it with two loops instead?
Yes — it's the brute force, and it's still correct, just O(n²). I'd mention it briefly to show I understand the naive baseline, then pivot to explaining why it's unnecessary here.

        
Q.Which solution would you actually choose, and why?
The one-pass O(n) / O(1) solution — it's strictly better on both time and space, and it's not any harder to write or explain once you see the running-minimum insight.

        
Q.What changes if multiple transactions are allowed?
The problem becomes "capture every upward slope," not just the single biggest one — you'd sum up every day-over-day price increase (see Section 13 for how this generalizes).

Pattern Recognition

      

        
Learn to spot this shape again. The signals that a "running minimum / running best" one-pass approach applies:

      

      
    
        
  • You're asked for a best pair (max difference, max ratio, max gap) where order matters (one side must come before the other).
    • 
        
  • The brute force naturally nests two loops, and the inner loop is always answering the same repeated question ("what's the best X seen so far?").
    • 
        
  • You can describe the needed memory in one or two words: a running minimum, a running maximum, a running sum, or a running count.
    • 
        
  • The problem is inherently greedy — the locally-best choice at each step (buy at the lowest point so far) never needs to be revisited later.

15
Final Cheat Sheet

      
Everything you need to re-derive this problem in under five minutes.

      

        

          
Core Intuition

          
  • Only one previous fact matters: the lowest price seen so far.
  • Profit today = today's price − running minimum.
  • Track the best such profit across the whole pass.

        

        

          
Step-by-Step Algorithm

          
  • Set min_price = first price, max_profit = 0.
  • For each later price: update min_price if it's a new low.
  • Compute price − min_price; update max_profit if bigger.
  • Return max_profit.

        

        

          
Python Template

          
  • min_price = prices[0]
  • max_profit = 0
  • for p in prices[1:]:
  •   min_price = min(min_price, p)
  •   max_profit = max(max_profit, p - min_price)

        

        

          
Complexity

          
  • Time: O(n) — one pass.
  • Space: O(1) — two running variables.
  • Brute force alternative: O(n²) time, O(1) space.

        

        

          
Common Mistakes

          
  • Selling before buying (index order).
  • Updating profit before updating the minimum.
  • Forgetting the "no trade" case returns 0.

        

        

          
Interview Tips

          
  • Mention brute force first, briefly, then pivot to the insight.
  • State the invariant out loud: "min_price is always the lowest price seen so far."
  • Know the multi-transaction follow-up (Stock II).

        

        

          
Pattern Recognition Cues

          
  • Best pair with order constraint → running min/max.
  • Nested loop where inner loop repeats the same "best so far" question → collapse to one variable.
  • Greedy local choice that's never revisited → one-pass candidate.

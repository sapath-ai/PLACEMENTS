    01 The Big Picture

    Why the very first LeetCode problem matters so much

    Two Sum looks small. It is not small — it's the smallest possible container for some of the biggest ideas in software engineering.

    What is Two Sum?

    You're given a list of numbers and a target. You must find two numbers in the list that add up to the target, and return their positions. Exactly one pair works. You cannot use the same position twice.

    Why is it problem #1?

    It's the smallest problem where the "obvious" solution and the "right" solution genuinely differ. That gap — between what works and what's efficient — is the entire subject of algorithms. Nearly every interview loop starts here because it tests whether you notice that gap at all.

    Skills it secretly tests

    Turning a vague sentence into a precise spec. Noticing repeated work. Trading memory for speed on purpose. And picking the right data structure before writing a single line of code.

    The idea hiding inside it

    The core move — remember what you've already seen, so you never have to look for it again — is one of the most reused ideas in computing. It's why your browser caches pages, why databases build indexes instead of scanning every row, why a spell-checker looks up a word instantly instead of reading the whole dictionary, and why a fraud system can check "have I seen this card number before" without re-reading every past transaction. Two Sum is the smallest possible rehearsal of that idea.

    02 Understanding the Problem

    Turning the problem statement into something precise

    Before solving anything, restate it so plainly that there's no room for ambiguity.

    Input

    nums — a list of integers.
    target — a single integer.

    Output

    A list of exactly two indices (positions), not the values themselves, such that nums[i] + nums[j] == target.

    Constraints tap to expand
    • Each input has exactly one valid answer.
    • You may not use the same element twice — i ≠ j.
    • Numbers can repeat in the array, and can include zero or negative numbers.
    • You can return the two indices in either order.
    Edge cases worth noticing
    • Duplicate values: [3, 3], target 6 → valid answer is [0, 1], not "the same element twice."
    • Negative numbers: [-3, 4, 1], target 1 → -3 + 4 = 1.
    • Zero as a value or target: zero is a perfectly normal number here, not a special case to guard against.
    • Because a solution is guaranteed, you never need to handle "no answer found."
    03 Building Intuition

    Before any algorithm — a picture

    Every number in the array is looking for exactly one partner. Its partner is whatever number would complete it to reach the target.

    Think of it like a dance floor where the target is fixed at 9. The number 2 isn't looking for "any" partner — it's looking for exactly one specific value: 7. Everyone on the floor is silently asking the same question: "is my partner standing somewhere in this room?"

    Why it works

    It's exhaustive. Every possible pair gets checked eventually, so it can never miss the answer that's guaranteed to exist.

    Why it becomes a problem

    For every one of the n numbers, we re-scan almost the whole array again. Work grows roughly with n × n. At 4 elements that's fine. At 100,000 elements, that's ~10 billion comparisons.

    05 Discovering the Better Idea

    Don't be told the answer — reason your way there

    Sit with these questions for a moment before scrolling past them.

    Q: What are we repeatedly searching for?

    At every position, we search the rest of the array for one specific value: the complement, target − current.

    Q: Why is that search slow?

    Because a plain list has no shortcuts — checking "is this value in here?" means looking at entries one by one.

    Q: What if we remembered every number we'd already passed, the instant we passed it?

    Then by the time we reach a new number, we could ask "have I already seen its complement?" as a single instant check — instead of re-scanning anything.

    The insight: we don't need to search the future for a partner — we only need to remember the past well enough to recognize it. That requires a structure built for instant lookup. That structure is a hash map.

    06 Hash Map Intuition

    The instant-lookup box

    A hash map (Python's dict) stores key → value pairs and can answer "do I know this key?" in roughly one step, no matter how many keys it holds — because it computes exactly where a key lives instead of searching for it.

    Picture a wall of labeled cubbies. To store something, you compute an address from the key and drop it straight in that cubby. To look something up, you compute the same address and walk directly there — you never check the other cubbies.

    Watch the difference for yourself

    Both panels hold the same three numbers. Pick a value to look up and see how many steps each structure needs.

    Plain list — must scan

    Hash map — direct jump

    Key

    What you look things up by. Here: a number from the array.

    Value

    What you store at that key. Here: the number's index.

    Average O(1)

    Insertion and lookup both take roughly constant time — independent of how many items are already stored.

    08 Python Implementation

    The solution, line by line

    def two_sum(nums, target):
    seen = {}  # value -> index, built as we go
    for i, n in enumerate(nums):
        complement = target - n
        if complement in seen:
            return [seen[complement], i]
        seen[n] = i
    return []  # unreachable given the problem's guarantee
    enumerate(nums)gives both the index i and the value n at once — no manual counter needed. complementthe exact value that would complete n to reach target. Always target − n, never target + n. if complement in seenan O(1) average-case membership check — this is the whole speedup, done before we touch the dictionary for this iteration. seen[complement]the index where that complement was stored earlier — that's our first answer index. seen[n] = ionly after checking do we record the current number, so a number is never matched against itself. naming: seennamed for what it represents — "numbers I have already looked at" — not just "d" or "map".

    Running it: two_sum([3, 2, 4], 6) → [1, 2], because nums[1] + nums[2] = 2 + 4 = 6.

    09 Why the Algorithm Works

    Order is not a style choice — it's correctness

    Lookup must happen before insertion. Reverse it, and the algorithm silently breaks.

    Correct order

    Check complement → not found → then insert current number. A number can never be paired with itself, because it isn't stored yet when its own complement is checked.

    Broken order

    Insert current number → then check complement. Now the number is already sitting in the dictionary when you ask "have I seen my own complement" — and if target is exactly double the number, it matches itself.

    Watch it fail: nums = [3, 2, 4], target 6. At i = 0, the broken version inserts 3 → 0 first, then checks for complement 3 — and finds the one it just inserted.

    10 Complexity

    What we actually bought with that dictionary

    "O" notation just describes how work grows as the input grows — not an exact count of steps.

    O(n²)

    Brute force. Doubling the array roughly quadruples the work.

    O(n)

    Optimal time. Doubling the array roughly doubles the work — one pass, no matter what.

    O(n)

    Optimal space. The dictionary can hold up to n entries — we traded memory for speed on purpose.

    11 Common Mistakes

    The bugs almost everyone writes once

    ✗Building the whole dictionary first, then scanning
    seen = {n: i for i, n in enumerate(nums)}  # built all at once, up front
for i, n in enumerate(nums):
    complement = target - n
    if complement in seen:
        return [i, seen[complement]]

    With nums = [3, 2, 4], target 6: at i = 0, n = 3, complement is 3 — and seen[3] is 0, its own index. This returns [0, 0], using one element twice. Building the dictionary incrementally, as you go, is what prevents this.

    ✗Adding instead of subtracting

    Writing complement = target + n instead of target - n. The lookup will almost never find anything real, and on the rare occasion it does, the pair won't actually sum to the target.

    ✗Inserting before checking

    Covered in detail in Section 9 — but worth repeating here because it's the single most common bug in this problem. Always check first, insert second.

    ✗Storing index as the key instead of the value

    Writing seen[i] = n instead of seen[n] = i. Now you can only look things up by position, not by value — which defeats the entire point, since what you need to search for is a value (the complement).

    ✗Using list.index() instead of a dictionary

    nums.index(complement) always returns the first occurrence of a value — which silently breaks on duplicates, and still scans the list each time, giving you none of the speed you were trying to get.

    12 Interview Thinking

    The follow-up questions — answer them before revealing

    Why a hash map, specifically?
    Because the operation we repeat most is "have I seen this value before" — a membership check. A hash map answers that in average O(1); a list makes us re-scan, which is O(n) every single time.
    Could we do better than O(n)?
    Not for the general case — every element must be examined at least once, since any one of them could be part of the answer. O(n) is the theoretical floor here.
    What if the array were already sorted?
    A two-pointer approach works in O(n) time and O(1) extra space — one pointer at each end, moving inward based on whether the current sum is too high or too low. The catch: it returns sorted positions, not original ones, so you'd need to track original indices separately if the input had to be sorted first.
    What if there were multiple valid pairs?
    Store a list of indices per value instead of a single index, and continue scanning instead of returning on the first match — collect every valid pair as you go.
    What if memory were tightly constrained?
    If you truly cannot afford O(n) space, fall back to brute force (O(n²) time, O(1) space) — or, if reordering is allowed, sort first and two-pointer it (O(n log n) time, O(1) extra space). There's always a time/space trade-off available; picking one is the point of the question.
    13 Pattern Recognition

    Spotting this shape again in the wild

    The signal to look for: "I keep needing to check whether something has appeared before, or find something related to what I'm looking at right now." That's almost always a hash map.

    Concretely, reach for a hash map when you notice: repeated "does this exist already" checks inside a loop; needing to pair, group, or count things by a shared property; or a nested loop that's really just re-searching for the same kind of thing over and over.

    15 Final Cheat Sheet

    Everything on one page — revise it in five minutes

    Core intuition

    For every number, ask "have I already seen its complement?" Remember every number as you pass it, so that question is instant.

    Algorithm

    • Walk the array once, keeping a dictionary of value → index.
    • At each number, compute complement = target − n.
    • Check the dictionary before inserting.
    • Found → return the two indices. Not found → insert and continue.

    Python template

    def two_sum(nums, target):
    seen = {}
    for i, n in enumerate(nums):
        c = target - n
        if c in seen:
            return [seen[c], i]
        seen[n] = i

    Complexity

    • Time: O(n) — one pass.
    • Space: O(n) — the dictionary.

    Common mistakes

    • Building the dictionary before scanning (self-match bug).
    • target + n instead of target - n.
    • Inserting before checking.
    • Storing index as key instead of value.

    Interview tips

    • Say out loud why brute force is O(n²) before optimizing — show you noticed the gap.
    • Mention the sorted-array two-pointer alternative unprompted.
    • Know the space/time trade-off cold — it's the actual point of the question.

    Pattern cue

    "I need to repeatedly check if something has appeared before" → hash map.

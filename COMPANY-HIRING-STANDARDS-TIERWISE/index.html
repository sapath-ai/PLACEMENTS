MODERN ENGINEERING PRACTICE

AI-assisted engineering is now part of the workflow

Modern teams increasingly use AI during software development. The hiring bar is therefore shifting toward the ability to delegate, inspect, test, debug and verify AI-generated work rather than merely knowing how to prompt a model. Recent 2026 research reports growing movement toward real-time, higher-order assessment and critical evaluation of AI output. citeturn0academia32

01
DELEGATE

Break work into tasks suitable for AI assistance. Give the model bounded, testable work instead of outsourcing the entire engineering problem blindly.

02
VERIFY

Review generated code, reasoning and model outputs critically. Check assumptions, documentation, APIs and edge cases before accepting the result.

03
TEST

Use tests, evaluations and benchmarks instead of trusting plausible output. Treat generated work exactly like work written by another engineer.

04
DEBUG

Diagnose failures independently when AI-generated solutions are wrong. Understand the system well enough to locate and fix the real cause.

05
SECURE

Check dependencies, secrets, permissions, data exposure and unsafe tool use. AI-generated code must pass the same security bar as human-written code.

06
OWN

Remain accountable for the final system and its technical decisions. AI assistance changes the workflow, not who owns the engineering outcome.

SECTION 04 PROJECT LADDER

Projects escalate from implementation → systems → research → frontier specialization

Do not collect toy projects. Every project must produce an executable artifact, measurable evidence, failure analysis and a technical defense. The ladder is deliberately cumulative: later projects reuse and extend earlier infrastructure.

PROJECT 01 · FOUNDATIONBuild a Transformer inference/evaluation harness from first principles. Include batching, token accounting, deterministic evaluation, latency/throughput measurements, tests and a reproducible run manifest.
PROJECT 02 · PERFORMANCEImplement and benchmark a non-trivial GPU kernel in CUDA or Triton. Profile it with Nsight, diagnose memory/compute bottlenecks, compare against a reference and document the optimization chain.
PROJECT 03 · DISTRIBUTEDRun a multi-GPU training workload with checkpoint/restart, failure injection, experiment tracking and distributed data loading. Measure scaling efficiency and diagnose the bottleneck.
PROJECT 04 · SERVINGBuild a production-style inference service. Compare eager/baseline serving against continuous batching, KV caching and one advanced strategy such as speculative decoding or disaggregated prefill/decode. Report TTFT, p95/p99 ITL, throughput, memory and cost.
PROJECT 05 · COMPILERTake a real model bottleneck through torch.compile. Diagnose graph breaks, inspect generated code, test dynamic/static shapes and fusion, and prove numerical correctness plus measured performance impact.
PROJECT 06 · RESEARCHDesign a controlled research study with a baseline, hypothesis, estimand, power/precision rationale, ablations, uncertainty analysis, failure analysis and a reproducible artifact. Write it like a short workshop paper.
PROJECT 07 · SPECIALIZATIONComplete one deep primary-track build: Training/MoE, Evals/Safety, Agents, GPU/Performance, Inference, ML Systems, Multimodal/World Models or Interpretability. It must involve source-level debugging and a novel or non-obvious technical decision.
PROJECT 08 · FRONTIER CAPSTONEOwn an end-to-end research-engineering system: problem definition → baseline → architecture → implementation → distributed execution → evaluation → profiling → failure analysis → reproducible release. Defend every major decision without AI assistance during the defense.
NO-AI CHECKPOINTFor Projects 02, 05, 06 and 08, complete a defined implementation/debugging segment without generative-AI assistance. Preserve commit history or a signed work log showing what was done independently.
EXPERT DEFENSEBe able to explain bottlenecks, alternatives, failed approaches, measurement methodology and why the result should be trusted. A polished README without technical ownership does not pass.
RESEARCH EVIDENCEKeep raw benchmark outputs, configs, environment versions, datasets/checksums, profiler traces and experiment manifests. Never report only the best run.
PASS CONDITIONEvery project must have: executable code, tests, benchmark/evaluation results, failure analysis, reproducibility instructions, architecture/data-flow documentation and a concise technical defense.

  1. Python build-from-scratch: Starting from an empty directory and with no AI, build a typed CLI program that ingests JSON/CSV records, validates them, handles malformed input, logs failures, produces a summary report and has a clean package structure. Include tests.
  2. Python reasoning: Explain and demonstrate iterators vs generators, context managers, exceptions, mutable defaults, shallow vs deep copy, decorators, type hints and dependency isolation. Write at least two examples live.
  3. Debugging: Take a deliberately broken Python program containing a logic bug, exception-handling bug, resource leak and performance issue. Diagnose each with evidence before changing the code.
  4. Second language: Implement the same small algorithm in C++/Java/JavaScript or another approved language. Explain compilation/runtime behavior, collections and memory/runtime trade-offs at a basic level.
  5. Git exercise: Create a repository, make feature branches, produce two meaningful commits, open a PR, introduce a conflict intentionally, resolve it, and explain merge vs rebase.
  6. Code review: Review a 100–200 line unfamiliar program and identify at least five issues across correctness, maintainability, testing, security or performance. Suggest fixes, not just complaints.
02

DSA + LeetCode Interview Standard

Pattern recognition, implementation speed and correctness under pressure.

  1. Timed Easy: Solve an unseen array/string/hash-map problem in ≤20 minutes, without AI, with tests and Big-O analysis.
  2. Timed Medium #1: Solve an unseen binary-search/sliding-window/two-pointer problem in ≤35 minutes.
  3. Timed Medium #2: Solve an unseen tree/heap/graph problem in ≤40 minutes.
  4. Timed Medium #3: Solve an unseen stack/interval/backtracking/DP problem in ≤45 minutes.
  5. Pattern defense: For every solution, explain why the chosen data structure works, the invariant, the complexity and at least one plausible alternative.
  6. Minimum evidence: Maintain a solved-problem log covering arrays, hashing, two pointers, sliding window, binary search, linked lists, stacks/queues, trees, heaps, graphs, recursion/backtracking and introductory DP. Target the Gate 01 range of ~75–125 well-understood problems rather than counting shallow submissions.
03

SQL + Data Modeling

Demonstrate query fluency and relational reasoning.

  1. Query set: Given a realistic schema, write joins across 4+ tables, aggregations, CASE logic, NULL-safe logic, subqueries and CTEs without assistance.
  2. Analytics query: Write a query that ranks entities within groups, calculates rolling or comparative metrics and filters on the derived result.
  3. Data model: Design a normalized schema for a small marketplace or job platform. Identify primary keys, foreign keys, cardinalities and indexing candidates.
  4. Performance: Given a slow query and EXPLAIN output, identify the bottleneck and propose a concrete index/query/schema improvement.
  5. Transactions: Explain atomicity, consistency, isolation and durability, plus one practical race condition that transactions can prevent.
04

System Design — Foundation

You are not exempt from system design because you are early-career.

  1. Design #1: Design a URL shortener. Cover requirements, API, data model, read/write path, caching, IDs, availability and basic scaling.
  2. Design #2: Design a background job/task service. Explain API → queue → worker → database, retries, idempotency and failure handling.
  3. Design #3: Design a file-upload service. Discuss object storage, metadata, authentication, upload limits, asynchronous processing and failure recovery.
  4. Capacity: For one design, make rough QPS, storage, bandwidth and latency estimates. Identify the first bottleneck.
  5. Defense: Explain why you selected your database, cache and queue. State what would change at 10× traffic.
05

Linux + Networking + APIs

Prove that you can operate and troubleshoot a real service.

  1. Linux lab: Create a non-root user, manage permissions, inspect processes, identify a listening port, inspect environment variables and troubleshoot a failed process.
  2. CLI lab: Use pipes/redirection plus grep/find/sed/awk or equivalent to inspect a log and produce a useful diagnostic report.
  3. Networking: Explain DNS → TCP/TLS → HTTP request flow. Diagnose a service that resolves DNS but fails at the application layer.
  4. API build: Build a FastAPI/Flask or equivalent CRUD API from scratch with validation, structured errors, authentication basics, configuration and tests.
  5. Failure exercise: Given elevated latency and intermittent 5xx errors, determine whether the likely fault is client, network, application, database or dependency related using observable evidence.
06

Testing + Quality

Working code is not enough; you must know whether it works.

  1. Unit testing: Add tests to an existing service covering happy path, boundary cases, invalid input and regression behavior.
  2. Fixtures/mocking: Use fixtures and mock an external dependency. Explain what should and should not be mocked.
  3. Test failure: Given a failing CI test, reproduce it locally, isolate the cause and document the fix.
  4. Quality gate: Define what must pass before a small API/ML project can be merged: tests, lint/type checks, security checks and reproducibility.
07

Classical ML + Mathematics

Know what the model is doing and why the evaluation is trustworthy.

  1. Math: Work through vector dot products, matrix multiplication, conditional probability, expectation/variance and a gradient calculation by hand.
  2. ML build: Train a scikit-learn classification pipeline from raw tabular data including preprocessing, train/validation/test separation, cross-validation and metrics.
  3. Leakage: Identify at least three possible leakage paths in a supplied dataset and redesign the pipeline to prevent them.
  4. Imbalance: Given a heavily imbalanced classification problem, justify metric choice and compare at least two mitigation strategies.
  5. Model defense: Explain why you selected the model, preprocessing, validation method and threshold. Discuss what evidence would make you distrust the result.
08

Data Workflow

Demonstrate an end-to-end reproducible data path.

  1. Pipeline build: Implement Load → Validate → Clean → Transform → Split → Train → Evaluate with explicit intermediate artifacts.
  2. Messy data: Handle missing values, duplicates, inconsistent categories, outliers and malformed records without silently deleting information.
  3. Reproducibility: Make the pipeline deterministic where appropriate, version its configuration and provide one command to reproduce the result.
  4. Error analysis: Produce a short report showing which data slices perform poorly and what you would investigate next.
09

AI Application Baseline

Use modern AI as an engineering component, not as magic.

  1. LLM integration: Build a small application using a current model API or open model. Handle configuration, retries, timeouts, rate limits and structured output.
  2. Context engineering: Demonstrate token/context budgeting and explain how prompt/context construction changes reliability and cost.
  3. Failure analysis: Create five adversarial inputs and document where the system fails, why it fails and what mitigation you added.
  4. Model choice: Given three candidate models, compare quality, latency, context, cost and privacy constraints and justify a selection.
10

AI-Assisted Engineering Discipline

The test is whether you remain the engineer.

  1. No-AI implementation: Complete one small software build entirely without AI. Record the time, mistakes and debugging process.
  2. AI-assisted implementation: Repeat a comparable task with AI assistance. Keep a short audit log of what you delegated, what you rejected and what you verified.
  3. Verification: Take intentionally flawed AI-generated code and identify correctness, security, dependency and maintainability problems before running it in a trusted environment.
  4. Ownership test: Explain every important line, dependency and architectural decision in the final system. If you cannot explain it, it does not count as demonstrated skill.
11

Security + Responsible Engineering

Fundamental security failures are critical failures, not bonus points.

  1. Secrets: Find and remove a hard-coded API key from a project and replace it with a safe configuration pattern.
  2. Authorization: Identify an insecure direct-object-reference or broken-access-control bug in a sample API and fix it.
  3. AI security: Demonstrate prompt injection against a toy AI application and implement a mitigation plus an explicit residual-risk note.
  4. Dependencies: Inspect dependencies for known/high-risk issues and explain how you would handle a vulnerable transitive dependency.

Advanced Software Engineering + DSA

Section 03 assumes that production engineering fundamentals are automatic, not fragile.

  1. Timed DSA set: Solve three unseen problems in one sitting: one graph/union-find problem, one advanced tree/heap/interval problem, and one DP/backtracking problem. Target ≤45 minutes per problem, no AI, with tests and complexity proof.

  4. Performance debugging: Given a service whose p95 latency doubled, use profiling and telemetry to isolate whether the bottleneck is CPU, I/O, database, serialization, contention or an external dependency.

02

Advanced SQL + Data Systems

You should be able to reason about data at system scale, not just write SELECT statements.

  1. Complex SQL case: Solve a 6–8 table analytics problem involving CTEs, windows, ranking, conditional aggregation, temporal logic, NULL semantics and deduplication under a strict time limit.
  2. Query-plan diagnosis: Given a slow production query and EXPLAIN/EXPLAIN ANALYZE output, identify the bottleneck and compare index, query rewrite, partitioning and schema alternatives.
  3. Transaction reasoning: Reproduce a race condition involving concurrent writes and demonstrate how transaction isolation, locking or idempotency changes the outcome.
  4. Data model evolution: Design a schema for an event-driven AI product, then evolve it for 10× data volume without breaking existing consumers.
  5. Batch vs streaming: Decide when the system should use batch processing, streaming or a hybrid design. Defend the choice using freshness, cost, complexity and correctness requirements.
03

System Design — Specialist Level

Section 03 requires architecture depth beyond ordinary CRUD + cache + queue diagrams.

  1. Global inference platform: Design a multi-region model-serving platform with a strict latency SLO, autoscaling, model versioning, canary releases, GPU capacity management, fallbacks and disaster recovery.
  2. Training platform: Design a distributed training system covering dataset access, scheduling, GPU allocation, checkpointing, failure recovery, experiment tracking and artifact storage.
  3. RAG at scale: Design a retrieval platform for millions of documents and high query volume. Explain indexing, sharding, freshness, hybrid retrieval, reranking, cache strategy and evaluation drift.
  4. Agent runtime: Design a multi-tenant agent execution platform with sandboxed tools, quotas, state, durable workflows, human approval, auditability, retries and exactly-once/idempotent behavior where required.
  5. Capacity exercise: Estimate QPS, tokens/sec, GPU capacity, storage growth, network bandwidth and monthly infrastructure cost. State assumptions and identify the first scaling wall.
  6. Failure game: The model is healthy but p99 latency triples, retrieval quality falls 15%, and cloud cost rises 40%. Diagnose possible causes and produce a staged incident-response plan.
04

PyTorch + Deep Learning Internals

Move from training-model familiarity toward engineering control over the training stack.

  2. Numerical debugging: Diagnose NaNs, exploding/vanishing gradients, silent label corruption and unstable loss using instrumentation and controlled experiments.
  3. Transformer internals: Implement scaled dot-product attention manually and explain tensor shapes, masking, complexity and memory cost.
  4. Fine-tuning strategy: Given limited compute and data, choose between full fine-tuning, parameter-efficient fine-tuning, freezing, distillation or prompt-based approaches. Quantify the trade-offs.

RAG / Retrieval / Evaluation Mastery

Retrieval quality, grounding and evaluation must be treated as engineering disciplines.

  4. Evaluation: Create task-level agent evals that measure completion, tool correctness, failure recovery, cost and latency—not just final answer quality.

Statistics, Experimentation + Scientific Reasoning

Advanced AI engineering requires knowing whether an observed improvement is real.

  3. Bias: Identify sampling, selection, leakage and evaluation-set bias in a supplied experiment.
  4. Model comparison: Compare two model versions under uncertainty and decide whether the improvement is sufficient to justify higher latency/cost.

REPRODUCIBILITY — Version datasets, code, configs, tokenizer/model artifacts and environments. Record hardware, software, random seeds and training metadata sufficiently for independent reconstruction.
TRAINING EFFICIENCY — Tokens/sec, step time, MFU/HFU-style metrics, memory efficiency, communication overhead, dataloader wait and checkpoint overhead. Tie optimization to end-to-end training throughput.
→Training practical: reproduce a published training behavior at feasible scale, formulate one scaling/data/optimization hypothesis, run controlled experiments, produce an ablation table and defend the conclusion plus its limitations.

UPDATE 11 · Frontier evaluation, benchmarking + measurement science
→Evaluation is an engineering discipline. A frontier candidate must be able to decide what should be measured, build the measurement system, quantify uncertainty, detect evaluator failure and prevent regressions—not merely run a benchmark.
EVALUATION DESIGN — Define the capability, target population, task distribution, unit of analysis, success criterion and failure taxonomy before selecting metrics or datasets.
BENCHMARK HYGIENE — Dataset provenance, contamination checks, train/test separation, benchmark leakage, saturation, versioning and reproducible evaluation environments.
METRICS — Accuracy, precision/recall, calibration, ranking metrics, pass@k, success rates, latency/cost and task-specific metrics. Know when a metric can be gamed or hides a failure mode.
STATISTICAL VALIDITY — Sampling, confidence intervals, variance, bootstrap/permutation concepts, paired comparisons, effect sizes, power/precision and multiple-comparison awareness.
MODEL-BASED GRADERS — Rubrics, calibration, agreement with humans, false positives/negatives, judge bias, position/order effects and adversarial evaluator exploitation.
AGENT EVALS — Task success, partial completion, trajectory quality, tool correctness, recovery rate, cost, latency, robustness and long-horizon failure probability.
REGRESSION GATES — Automated pre/post-release evaluations, confidence thresholds, capability/safety regression checks and blocking criteria for model or system changes.
ADVERSARIAL EVALUATION — Red-team prompts, distribution shifts, rare failures, jailbreak attempts, prompt injection, tool abuse and evaluator gaming. Treat successful attacks as measurement evidence, not anecdotes.
CAPABILITY + SAFETY JOINT EVALUATION — Measure useful capability alongside refusal, misuse, robustness, privacy/security and behavioral regressions so optimization does not improve one axis while silently damaging another.
EVAL INFRASTRUCTURE — Reproducible harnesses, dataset/version control, parallel execution, result storage, artifact lineage, dashboards, caching and failure replay. Current frontier evaluation roles explicitly combine graders, environments, continuous evaluation and scalable research infrastructure. citeturn0search0turn0search2
→Evaluation practical: build an evaluation harness with at least one automated grader and one adversarial suite; measure grader reliability; run a controlled model comparison; report uncertainty and failure clusters; then create a regression gate that can block a future model change.
UPDATE 12 · AI safety, security + alignment engineering
→Safety is not a policy-reading requirement. Section 05 treats safety and security as technical system properties spanning training, evaluation, inference, agents, data, tools and deployment.
THREAT MODELING — Identify assets, actors, trust boundaries, attack surfaces, abuse cases, assumptions and impact. Produce explicit mitigations rather than generic "secure it" language.
PROMPT INJECTION + TOOL SECURITY — Direct/indirect injection, untrusted retrieved content, tool authorization, capability boundaries, confirmation policies, credential isolation and safe tool execution.
MODEL / AGENT MISUSE — Abuse pathways, jailbreaks, data exfiltration, dangerous tool chains, privilege escalation and long-horizon agent failures. Evaluate realistic attack paths, not only benchmark prompts.
REWARD HACKING — Specification gaming, evaluator exploitation, proxy optimization and unintended strategies. Build tests that distinguish genuine task improvement from reward manipulation.
ALIGNMENT / BEHAVIORAL EVALUATION — Behavioral specifications, refusal/assistance boundaries, monitorability, scalable oversight concepts and tests for behavior under distribution shift.
RED TEAMING — Construct adversarial cases systematically, track attack success, cluster failures, reproduce them and turn discoveries into regression tests or mitigations.
PRIVACY + DATA SECURITY — Data provenance, access control, secret handling, training-data exposure concepts, logging boundaries, retention and secure experiment artifacts.
SUPPLY-CHAIN SECURITY — Dependencies, model weights, datasets, containers, packages, build provenance, artifact integrity and reproducible environments. Know how a compromised dependency or model artifact propagates risk.
INCIDENT RESPONSE — Detection, containment, rollback, evidence preservation, root-cause analysis, communication and post-incident regression coverage.
SAFETY/UTILITY TRADE-OFFS — Quantify how mitigations affect useful capability, latency, cost and user experience. Avoid declaring a mitigation successful without measuring collateral regressions.
→Security practical: threat-model a sandboxed agent, demonstrate an injection/tool-abuse path in a controlled environment, implement least-privilege mitigations, verify that the attack fails, and add the case to a repeatable regression suite.

VISION-LANGUAGE MODELS — Image/token representations, patching/tokenization, multimodal encoders, cross-modal attention/alignment, image-text data and evaluation of grounding rather than text-only fluency.
VIDEO + TEMPORAL MODELING — Frame sampling, temporal representations, long-context video, action/event localization, temporal consistency and compute/memory trade-offs.
AUDIO / SPEECH — Audio representations, spectrogram/token approaches, streaming constraints, multimodal alignment and latency considerations where the track requires audio.
VISION-LANGUAGE-ACTION — Perception → language/goal → policy/action, action tokenization/representation, closed-loop inference and evaluation in environments.
WORLD MODELS — Learned dynamics/state representations, prediction, planning, uncertainty and the distinction between predictive models and policies that actually control an environment.
SIMULATION — Synthetic environments, scenario generation, domain randomization, simulator fidelity, evaluation leakage and compute-efficient experimentation.
ROBOTICS / EMBODIED SYSTEMS — Sensors, perception, planning, control concepts, action latency, safety constraints, hardware interfaces and closed-loop failure modes for robotics-oriented paths.
SIM-TO-REAL / DISTRIBUTION SHIFT — Identify simulation-to-reality gaps, sensor/action mismatch, dynamics differences and behavioral drift. Design evaluations that expose rather than hide the gap.

CLOSED-LOOP EVALUATION — Evaluate perception, reasoning and action together in realistic trajectories; measure success, recovery, safety, latency and robustness rather than relying only on static benchmarks.
→Multimodal practical: build a small multimodal or VLA pipeline, define an evaluation protocol that includes distribution shift, instrument latency and failure modes, and demonstrate where the system breaks rather than presenting only its best-case performance.
UPDATE 14 · Interpretability + mechanistic research
→Interpretability is an empirical science, not visualization. The standard is causal/mechanistic evidence: formulate a hypothesis about internal computation, design an intervention or controlled measurement, test it, and distinguish correlation from mechanism.
REPRESENTATIONS — Activations, residual streams, attention patterns, neurons/features, token-level behavior and representation similarity. Understand what an observation can and cannot establish.
SPARSE AUTOENCODERS / FEATURES — Feature extraction concepts, sparsity, reconstruction/error trade-offs, feature splitting/monosemanticity claims and rigorous feature validation.
CIRCUIT ANALYSIS — Trace information flow through components, formulate circuit hypotheses, identify candidate mechanisms and test them with interventions.
CAUSAL INTERVENTIONS — Activation patching, ablation, steering/intervention concepts and controlled counterfactuals. Quantify behavioral change and rule out confounders.
MECHANISTIC HYPOTHESES — Convert a behavioral observation into a falsifiable internal-mechanism hypothesis with predicted outcomes before running the decisive experiment.
SCALING + GENERALIZATION — Test whether an observed mechanism survives across prompts, seeds, layers, model sizes or task distributions rather than relying on one illustrative example.
INTERPRETABILITY TOOLING — PyTorch hooks/traces, activation capture, visualization, statistical analysis and reproducible experiment pipelines; use specialized interpretability libraries when they materially accelerate the work.
FAILURE ANALYSIS — Track false explanations, cherry-picking, probe leakage, feature instability, measurement artifacts and evaluator bias. Negative evidence must remain visible.
SAFETY CONNECTION — Use interpretability findings to investigate behavior, monitorability, deceptive/undesired patterns or intervention hypotheses, while avoiding claims that exceed the evidence.
RESEARCH DEFENSE — Explain why the chosen intervention establishes more than a correlation, what alternative explanations remain, and which experiment would most efficiently discriminate them.
→Interpretability practical: choose a small open model and a concrete behavior, formulate a mechanistic hypothesis, identify candidate internal features/components, perform at least one causal intervention, replicate across multiple conditions and publish a falsifiable conclusion with limitations.
UPDATE 15 · Research methodology + experimental science
→Frontier capability requires scientific judgment. A sophisticated implementation is not research unless the question, evidence, controls and conclusion are defensible.
PROBLEM FORMULATION — Turn a broad idea into a precise research question, measurable hypothesis, scope boundary and falsifiable prediction.
LITERATURE / PRIOR ART — Search systematically, identify the strongest relevant baselines, understand competing explanations and state exactly what is already known versus what remains uncertain.
BASELINES — Select credible baselines, reproduce them fairly, preserve comparable compute/data conditions and document deviations from published implementations.
ABLATIONS — Isolate components, variables and assumptions. Change one meaningful factor where possible and avoid attributing gains to a component that was never independently tested.
EXPERIMENT CONTROL — Seeds, splits, preprocessing, hyperparameter budgets, evaluation checkpoints, hardware/software versions and other confounders must be controlled or explicitly accounted for.
STATISTICAL REASONING — Variance, uncertainty, confidence intervals, effect size, repeated runs and practical significance. Know when a claimed improvement is smaller than experimental noise.
REPRODUCIBILITY — Code, configuration, data/version provenance, environment, seeds, checkpoints, evaluation scripts and exact run metadata sufficient for independent reconstruction.
NEGATIVE RESULTS — Preserve failed experiments, unexpected behavior and null results when they constrain the hypothesis space. Do not silently discard experiments that weaken the story.
RESOURCE-AWARE RESEARCH — Estimate compute, time and storage before running. Prefer experiments with high information value and use staged pilots before expensive scaling runs.
CLAIM DISCIPLINE — Separate observation, interpretation and causal claim. State limitations, external-validity boundaries and what evidence would change your conclusion.
RESEARCH COMMUNICATION — Produce a concise technical narrative: question → method → evidence → failure analysis → conclusion → limitation → next experiment. Be able to defend every important number.
→Research practical: reproduce a credible baseline, propose one falsifiable improvement, predefine the decisive metric and ablations, run controlled experiments within a fixed compute budget, preserve failures, and write a report that a skeptical expert could audit.
UPDATE 16 · Frontier project ladder + evidence standard
→Projects are the proof layer. Section 05 projects must demonstrate implementation, measurement, debugging, research judgment and defense. Tutorial clones, API wrappers and benchmark screenshots alone do not qualify.

PROJECT 2 · DISTRIBUTED TRAINING — Train a non-trivial model across multiple GPUs or a realistic distributed simulation; measure scaling, communication, memory and failure recovery; produce a reproducible performance report.
PROJECT 3 · INFERENCE / SERVING — Deploy and benchmark a model server under controlled load; implement one performance/reliability improvement; report TTFT/latency/throughput/cost and explain the trade-offs.
PROJECT 4 · POST-TRAINING — Fine-tune or post-train an open model with a clearly defined intervention and independent evaluation; include ablations and capability/regression analysis.
PROJECT 5 · AGENT / ENVIRONMENT — Build a sandboxed multi-tool agent with trajectory logging, programmatic verification, failure recovery and adversarial testing. One debugging cycle must be completed without AI assistance.
PROJECT 6 · EVAL / SAFETY — Build an evaluation harness, grader and red-team suite; quantify grader reliability; identify a failure class; implement a mitigation and regression gate.
PROJECT 7 · RESEARCH REPRODUCTION — Reproduce a meaningful result from a recent paper or open technical report, document deviations, reproduce key measurements and identify at least one limitation or unresolved question.
PROJECT 8 · FRONTIER INTEGRATION CAPSTONE — Combine at least two Section 05 specializations into one substantial system or research project. Example combinations: post-training + inference; agents + evals; training + GPU performance; multimodal + robotics; interpretability + safety.

DEFENSE — Be prepared to explain what you personally built, why each major decision was made, what failed, what measurements support the conclusion, what you would change with more compute/time and which claims remain uncertain.

UPDATE 03 · Frontier AI system design
DESIGN FROM WORKLOAD → CONSTRAINTS — Begin with users/workloads, model characteristics, data volume, sequence lengths, concurrency, latency SLOs, availability, quality targets, security boundaries, energy/cost limits and failure assumptions.
TRAINING SYSTEMS — Design data/model/tensor/pipeline/expert parallelism, data loading, checkpointing, restart semantics, orchestration, cluster scheduling, collective communication, topology awareness and failure recovery. Reason about scaling efficiency rather than simply naming a framework.
INFERENCE SYSTEMS — Design request routing, admission control, batching, prefill/decode, KV-cache management, model parallelism, speculative decoding, disaggregation, autoscaling, observability and graceful degradation. Analyze TTFT, ITL, throughput, tail latency and cost per token.
RESEARCH INFRASTRUCTURE — Design experiment orchestration, dataset/version management, run manifests, evaluation pipelines, checkpoint lineage, artifact storage, reproducibility and regression gates. Make it possible for another researcher to reproduce and audit a result.

RELIABILITY + SECURITY — Define failure domains, retries, idempotency, checkpoint/recovery, monitoring, incident response, secrets, least privilege, network egress, data isolation, prompt/tool injection defenses and supply-chain controls.

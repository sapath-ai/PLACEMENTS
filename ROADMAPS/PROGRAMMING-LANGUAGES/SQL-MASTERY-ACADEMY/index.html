ADVANCED

PRODUCTION

Engineering Decision Drills

Why did the planner choose a sequential scan?
REASON

A query filters a table where 95% of rows satisfy the predicate. Decide whether an index is likely to help before inspecting the answer.

Why can an index make writes slower?
EXPLAIN

Every maintained index creates additional work during INSERT, UPDATE, and DELETE. Decide when the read benefit justifies that write cost.

Why can two correct transactions still deadlock?
CONCURRENCY

Trace two transactions acquiring the same locks in opposite order, then identify the application-level prevention strategy.

Mastery Gate

Explain It

Explain MVCC, index selectivity, cardinality estimation, and logical query evaluation without notes.

Diagnose It

Given a slow query and an execution plan, identify the bottleneck and propose a measurable intervention.

Phase 5 · Applied SQL
SQL Specializations
Take the core SQL and database-engineering foundation into three real engineering tracks: Backend, Analytics, and AI.

01 · Backend SQL Engineering

Connect application code to relational databases: ORM-generated SQL, N+1 queries, transactions, connection pools, pagination, upserts, locking, migrations, and safe parameter binding.

Core Drills

  • Diagnose an N+1 query and redesign the access pattern.
  • Choose offset vs cursor pagination.
  • Design a transaction boundary for a multi-step write.
  • Identify an unsafe dynamic SQL construction.
  • Design an index from an application's real query pattern.

02 · Analytics Engineering

Move from isolated SQL queries to analytical data systems: fact/dimension modeling, ETL vs ELT, incremental transformations, cohorts, funnels, retention, metrics, and warehouse-oriented SQL.

Core Drills

  • Design a star schema for an event stream.
  • Build a cohort-retention query.
  • Turn raw events into a reusable metric table.
  • Reason about incremental vs full-refresh transformations.
  • Identify a metric-definition inconsistency.

03 · AI Data Engineering

Use SQL as the data layer for modern AI applications: documents, chunks, embeddings, metadata, retrieval logs, feedback, evaluations, and pgvector-style similarity search.

Core Drills

  • Design a document/chunk/embedding schema.
  • Combine metadata filtering with vector similarity.
  • Model retrieval and generation observability.
  • Store user feedback for evaluation.
  • Build SQL queries for retrieval-quality analysis.

Cross-Track Architecture

One database, three workloads
SYSTEM THINKING

Start with an operational relational schema, derive analytical structures from its events, and extend the data layer for AI retrieval and evaluation. The goal is not memorizing three unrelated SQL tracks — it is learning how the same data model evolves under different workloads.

Choose the right abstraction
DECISION

For each scenario, identify whether the right answer is a normalized OLTP schema, an analytical model, a cached/materialized result, or an AI retrieval structure. Defend the trade-off instead of merely writing a query.

Phase 6 · Capstone Engineering
Capstone Case Studies
Stop solving isolated SQL exercises. Design, implement, debug, optimize, and defend complete database systems.

CAPSTONE A · Production E-commerce DB

BACKEND

Build a transactional commerce database from requirements through production hardening.

Requirements

  • Customers, products, inventory, carts, orders, order items, payments, shipments.
  • Primary/foreign keys, uniqueness, CHECK constraints, and deliberate NULLability.
  • Transactional order placement with rollback behavior.
  • Indexes derived from real application query patterns.
  • Role-based access and parameterized queries.
  • Diagnose and optimize at least three slow queries.

Final Defense

Explain why the schema is normalized, where transactions begin/end, which indexes exist, and what happens under concurrent inventory updates.

CAPSTONE B · Product Analytics Warehouse

ANALYTICS

Turn raw product events into an analytical model capable of answering real business questions.

Requirements

  • Model users, sessions, events, products, orders, and revenue.
  • Design fact and dimension tables.
  • Build reusable transformation layers.
  • Answer funnel, cohort, retention, revenue, and conversion questions.
  • Handle late-arriving or duplicate events explicitly.
  • Define metrics precisely enough that two analysts get the same result.

Final Defense

Explain why the analytical model differs from the transactional model and defend the grain of every major fact table.

CAPSTONE C · Production RAG Data Layer

AI

Design the relational data layer behind a production-style retrieval-augmented generation system.

Requirements

  • Documents, versions, chunks, embeddings, metadata, users, conversations.
  • Retrieval logs containing query, retrieved chunks, scores, and model output.
  • Feedback and evaluation records.
  • Metadata-filtered vector retrieval.
  • Queries for retrieval quality and failure analysis.
  • Auditability of document and embedding versions.

Final Defense

Explain the schema, retrieval path, observability strategy, and how SQL helps diagnose poor RAG answers.

What Not To Do

  • Do not memorize 450 queries.
  • Do not look at solutions after thirty seconds of discomfort.
  • Do not ignore NULLs and duplicate rows.
  • Do not learn window functions only by memorizing syntax.
  • Do not spend all your time on hard problems while your JOIN fundamentals are weak.
  • Do not confuse completing a question with mastering its underlying pattern.

Definition of Done

The SQL Skill Ladder

01 · Mental Model

Understand how a relational query is logically processed. Learn what FROM, JOIN, WHERE, GROUP BY, HAVING, SELECT, ORDER BY and LIMIT are doing before you chase syntax.

02 · Fundamentals

SELECT, filtering, expressions, NULL, CASE, sorting and limiting. Solve roughly 20 focused problems immediately.

03 · Aggregation

COUNT, SUM, AVG, MIN, MAX, GROUP BY, HAVING and DISTINCT. Learn to reason about the grain of your result.

04 · JOINs

INNER, LEFT, FULL, CROSS, SELF and multi-table joins. Learn cardinality and duplicate multiplication—not just JOIN syntax.

05 · Subqueries & CTEs

Scalar and correlated subqueries, EXISTS, NOT EXISTS, IN, NOT IN and CTEs. Understand when each pattern communicates intent.

06 · Window Functions

ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, running totals, moving averages, PARTITION BY and window frames.

07 · Dates & Analytics

Date arithmetic, DATE_TRUNC, cohorts, retention, rolling periods, conversion funnels and change-over-time analysis.

08 · Database Engineering

Keys, constraints, normalization, transactions, ACID, isolation levels, indexes and execution-plan reasoning.

The Interview-Ready Test

For a problem, you should eventually be able to:

  1. Identify the tables and their grain.
  2. Recognize the underlying SQL pattern.
  3. Formulate a solution without looking it up.
  4. Handle NULLs, duplicates and boundary cases.
  5. Explain why each JOIN, aggregation or window exists.
  6. Discuss what changes when the data grows 100×.
  7. Suggest an alternative solution when appropriate.

The Goal

Don't aim to finish SQL. Aim to reach the point where you can see an unfamiliar SQL problem, identify its structure, formulate a solution, debug it, and explain it confidently.

Interview Reference
SQL Interview Reference
A practical preparation layer: recognize the pattern, solve the query, explain the reasoning, handle edge cases, and survive the follow-up.

Screening

SELECT, filtering, sorting, aggregates, simple JOINs and NULL handling.

Core

Multi-table JOINs, GROUP BY/HAVING, subqueries, CTEs and conditional aggregation.

Strong

Window functions, ranking, deduplication, date logic and complex business queries.

Advanced

Optimization, transactions, isolation, recursive SQL and analytical patterns.

Interview Answer Structure

Clarify assumptions → state the approach → write the query → test edge cases → discuss complexity → propose an alternative.

Must-Know Patterns

Top-N per Group

ROW_NUMBER / RANK / DENSE_RANK with PARTITION BY.

Deduplication

Window ranking followed by filtering the selected row.

Anti-Join

NOT EXISTS or LEFT JOIN ... IS NULL, with careful NULL reasoning.

Running Total

Windowed SUM with explicit ordering.

Conditional Aggregation

SUM/COUNT with CASE expressions.

Gaps & Islands

Ordered differences or cumulative grouping for consecutive runs.

Interviewer Follow-Ups

  • What happens if there are NULLs?
  • What happens when values are duplicated?
  • What happens when the dataset becomes 100× larger?
  • Can you solve it another way?
  • What indexes would you consider?
  • What is the complexity of your approach?
Reference
SQL Cheatsheets
Fast revision for the day before, morning of, or five minutes before an interview.

JOINs

INNER = matches. LEFT = all left rows + matches. FULL = both sides. CROSS = Cartesian product.

WHERE vs HAVING

WHERE filters rows before aggregation. HAVING filters groups after aggregation.

UNION vs UNION ALL

UNION removes duplicates. UNION ALL preserves them and is generally cheaper.

Ranking

ROW_NUMBER gives unique numbers. RANK leaves gaps after ties. DENSE_RANK does not.

DELETE / TRUNCATE / DROP

DELETE removes rows. TRUNCATE clears table data. DROP removes the object.

EXISTS vs IN

Understand membership semantics and NULL behavior before choosing between them.

CTE vs Subquery

Choose for clarity and maintainability; recursive CTEs solve recursive relationships.

ACID

Atomicity, Consistency, Isolation, Durability. Know COMMIT, ROLLBACK and isolation levels.

Window Function Template

SELECT *,
       ROW_NUMBER() OVER (
         PARTITION BY group_col
         ORDER BY metric DESC
       ) AS rn
FROM table_name;

Conditional Aggregation

SELECT category,
       COUNT(*) AS total,
       SUM(CASE WHEN status = 'paid' THEN 1 ELSE 0 END) AS paid
FROM orders
GROUP BY category;

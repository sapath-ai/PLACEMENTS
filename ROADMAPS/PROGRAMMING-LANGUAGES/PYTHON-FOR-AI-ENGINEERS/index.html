Not a research prep track. A general AI engineer track — built so week 1 doesn't assume week 8's fluency.

Four weeks of real foundations (core Python, software design, the NumPy/Pandas/data toolkit, and the modern AI stack end to end — training and serving), then eight weeks of the senior-level judgment that separates someone who prompts an LLM to write code from someone who catches it when it's wrong. What changed from the first draft

The original version front-loaded internals, profiling, and concurrency on the assumption you already had senior-level Python foundations under you — that was the wrong assumption, and it also over-indexed on your research background as the only lens. This version adds four foundation weeks so nothing in Phase 2 depends on a skill you haven't actually built yet, and it generalizes the material so it works whether you end up doing research, product AI engineering, or infra work. Your BraTS/FL background still shows up here and there as one flavor of worked example, because it's genuinely good material to practice on — but it's no longer the frame the whole regimen is built around, and Week 12's capstone gives you a choice of track rather than assuming one.

Scope reality check — read this before week 1

Where even 12 weeks is genuinely tight

  • Cython still only gets a "know when to reach for it and write a minimal kernel" treatment in Phase 2, not fluency — that's a multi-month track on its own regardless of how much foundation time precedes it.
  • Multi-GPU / multi-node DDP debugging is still simulated on one machine with multiple processes. No amount of foundation-building substitutes for time on a real cluster — that has to come later, from actual multi-node compute access.
  • LLM-specific engineering (prompt engineering depth, agent frameworks, RAG system design, eval harnesses) gets exactly one week's worth of exposure in Week 4 — enough to not be lost when a job description mentions it, not enough to be the specialist. If that's your actual target, it deserves its own follow-on track after this one.
  • Cryptographic side-channel defense (Week 11) is still conceptual/review-level, not applied-cryptography-engineering-level — see Week 11 for the exact line.
  • Docker/deployment in Week 4 covers enough to serve a model locally and understand what "containerize this" means in a job description — it is not a DevOps/MLOps track. If your target roles are infra-heavy, that's a legitimate reason to extend further after Week 12, not a gap this plan silently papers over.
  • This still assumes 4–5 focused hours/day, 6 days/week. At 12 weeks that's roughly 300 hours total — realistic for foundations-through-senior-judgment, not for foundations-through-specialist-depth in any one area above.

Core Python fluency for AI engineering

review_w1.py
difficulty 1 / 12
# Helper function an LLM generated for grouping items
# into a running collection, "should just work."
def add_to_group(item, group=[]):
    group.append(item)
    return group

# result_a = add_to_group("cat")   -> ["cat"]
# result_b = add_to_group("dog")   -> expected ["dog"], got ["cat", "dog"]
The classic one. Know it cold — you'll see LLMs produce it constantly.
The bug

The mutable default argument group=[] is created once, when the function is defined, not fresh on every call. Every call that doesn't explicitly pass its own list shares and mutates the same list object, so state silently leaks across unrelated calls — the second call sees the first call's leftover data. This is one of the most common bugs LLMs produce because the code reads as correct at a glance and passes any test that only calls the function once.

The fix

Default to None and create a fresh list inside the function body: def add_to_group(item, group=None): group = [] if group is None else group; group.append(item); return group.

review_w2.py
difficulty 2 / 12
# Custom exception an LLM generated to carry extra context
# (an error code) alongside the usual message.
class DataValidationError(Exception):
    def __init__(self, message, code):
        self.message = message
        self.code = code

# try:
#     raise DataValidationError("missing patient_id column", code=400)
# except DataValidationError as e:
#     print(e)   -> prints nothing useful
#     logger.exception(e)   -> traceback shows no message either
The exception "works" — it raises and can be caught. Something else is missing.
The bug

__init__ overrides the base Exception.__init__ without calling super().__init__(message). Exception's own machinery for producing a string representation (what str(e), print(e), and traceback formatting all rely on) depends on the base class actually storing the message via its own __init__. Without that call, the custom attributes (self.message, self.code) exist and are accessible, but anything that prints or logs the exception the normal way shows an empty message — which is exactly the kind of bug that makes a production incident far harder to debug than it needed to be, because the traceback itself lies about having no information.

The fix

Call super().__init__(message) inside __init__ before setting the extra attributes, so the exception's string representation works everywhere Python expects it to.

review_w3.py
difficulty 3 / 12
# "Normalize each row's values against the column means,"
# generated for a feature-scaling step.
import numpy as np

def center_rows(data, col_means):
    # data shape: (n_samples,), col_means shape: (n_samples,)
    return data - col_means

# centered = center_rows(row_data, column_means)
# centered.shape turns out to be (1000, 1000), not (1000,)
# and memory usage spikes on a dataset that should be tiny
Both arrays really are length 1000. The output shape is still wrong.
The bug

The comment claims both arrays are shape (n_samples,), but if col_means was actually produced elsewhere as shape (n_samples, 1) (a very common outcome of a careless .mean(axis=1, keepdims=True) or a reshape upstream), then data - col_means doesn't broadcast elementwise the way the docstring assumes — NumPy broadcasts a (1000,) array against a (1000,1) array into a (1000,1000) result, pairing every element of one against every element of the other. The operation doesn't crash — broadcasting rules make it legal — it just silently computes something entirely different from "subtract each row's mean," and the memory/shape blowup is often the only symptom.

The fix

Assert shapes explicitly before the operation (assert col_means.shape == data.shape, or reshape/squeeze deliberately with a comment explaining why), and never trust a shape claimed in a comment — verify it with .shape at the point of use, especially right after any keepdims=True reduction upstream.

review_w4.py
difficulty 4 / 12
# FastAPI service an LLM generated for model inference,
# "ready for production, handles concurrent requests fine."
from fastapi import FastAPI
import torch

app = FastAPI()

@app.post("/predict")
async def predict(payload: dict):
    model = torch.load("model.pt")
    model.eval()
    x = torch.tensor(payload["features"])
    with torch.no_grad():
        result = model(x)
    return {"prediction": result.tolist()}
Works fine for one request. Falls over under real traffic.
The bug

torch.load("model.pt") runs inside the request handler, so the model is deserialized from disk on every single incoming request instead of once at startup. Beyond the obvious latency cost, this is a correctness and stability problem too: repeated deserialization under concurrent load multiplies memory pressure (multiple copies of the model may be alive simultaneously depending on garbage-collection timing) and can exhaust memory or crash the process under real traffic, even though a single manual test request looks completely fine.

The fix

Load the model once at application startup (a FastAPI lifespan/startup event or a module-level load) and reuse the same in-memory model object across all requests. Separately worth flagging: a CPU-bound model(x) call inside an async def handler blocks the event loop for every other concurrent request unless it's offloaded to a thread pool (e.g. run_in_threadpool) — worth testing directly, since it connects to Week 7's concurrency material.

difficulty 5 / 12
# A teammate asked an LLM for a context manager that times
# a job and swallows keyboard interrupts cleanly.
import time
from contextlib import contextmanager

@contextmanager
def job_timer(logger):
    start = time.perf_counter()
    try:
        yield
    except Exception as e:
        logger.warning(f"job interrupted: {e}")
        return True
    finally:
        elapsed = time.perf_counter() - start
        logger.info(f"job took {elapsed:.2f}s")
A one-line class of bug you'll see constantly.
The bug

return True inside a generator-based @contextmanager function does nothing to suppress exceptions — that suppression semantic only applies to a class-based context manager's __exit__ returning a truthy value. Combined with the bare except Exception, every exception raised inside the with job_timer(...): block gets logged as a warning and then effectively lost track of, while the job appears to have "handled" its own crash. The job looks alive in the logs while it has actually died.

The fix

Don't catch exceptions you don't intend to suppress. Drop the except block entirely and let finally log elapsed time regardless of success or failure; if suppression is genuinely wanted, do it explicitly per contextlib's documented generator protocol — never silently.

difficulty 6 / 12
# "Optimized" patch-collection loop from an LLM, claimed to
# be vectorized and memory-efficient for streaming large arrays.
import numpy as np

def collect_patches(volume, patch_size=64, stride=32):
    patches = np.array([])
    for z in range(0, volume.shape[0] - patch_size, stride):
        for y in range(0, volume.shape[1] - patch_size, stride):
            for x in range(0, volume.shape[2] - patch_size, stride):
                p = volume[z:z+patch_size, y:y+patch_size, x:x+patch_size]
                patches = np.append(patches, p)
    return patches.reshape(-1, patch_size, patch_size, patch_size)
Runs fine on a small test array. Times out on a real one.
The bug

np.append inside a loop is not amortized like list.append — every call reallocates and copies the entire growing array, making this O(n²) in the number of patches. On a small test volume this is invisible; at real scale it becomes the dominant cost, and it's exactly the kind of bug an LLM produces because the code "looks vectorized" (it uses NumPy, no explicit Python-level math loop) while still being an accidental quadratic-copy loop underneath.

The fix

Collect patches in a plain Python list and stack once at the end with np.stack(patch_list), or pre-allocate the output array once you know the patch count from the loop bounds and write into it by index — no reallocation at all.

# Dataset that "caches" preprocessed items across epochs
# to avoid recomputing them, used with a multi-worker DataLoader.
class CachedDataset(torch.utils.data.Dataset):
    def __init__(self, items):
        self.items = items
        self._cache = {}  # populated lazily
        self.cache_hits = 0

    def __getitem__(self, idx):
        if idx in self._cache:
            self.cache_hits += 1
            return self._cache[idx]
        item = expensive_preprocess(self.items[idx])
        self._cache[idx] = item
        return item

# loader = DataLoader(dataset, num_workers=4, ...)
# after training: print(dataset.cache_hits)  -> always near 0
The cache "works" — cache_hits just always reports ~0. Why?
The bug

With num_workers>0 and the default fork start method, each worker process gets its own copy-on-write copy of the Dataset object, including self._cache and self.cache_hits. Each worker builds up its own private cache that never gets merged back into the main process, and PyTorch's default worker lifecycle can spin up a fresh set of workers between epochs, silently discarding whatever each worker had cached. The caching mechanism the person believes exists — a global cache growing across the whole run — doesn't exist at all, and cache_hits read from the main process is reading a counter that workers never actually update in a shared way.

The fix

Either precompute and cache to disk/memmap (crosses the process boundary naturally via the filesystem) or use a true shared structure such as multiprocessing.Manager().dict() / shared memory, understanding the added IPC overhead. Precomputing to a memmapped file on disk is usually the right call over in-memory per-worker caching.

The bug

Two separate gaps. First, torch.manual_seed(seed) alone does not fully seed CUDA operations — torch.cuda.manual_seed_all(seed) is also needed for multi-GPU determinism, and cuDNN's autotuned/non-deterministic algorithms need torch.backends.cudnn.deterministic=True and torch.backends.cudnn.benchmark=False explicitly set, none of which are here. Second, more subtly: with num_workers=4, each DataLoader worker process gets its own independent random state derived from the initial fork — without a worker_init_fn that seeds each worker deterministically, any augmentation randomness inside __getitem__ will differ between runs even though set_seed was called correctly in the main process.

The fix

Add torch.cuda.manual_seed_all(seed) and the cuDNN determinism flags to set_seed, and pass a worker_init_fn to the DataLoader that seeds each worker from torch.initial_seed() so per-worker randomness is also reproducible.

# Hypothesis property test for the extraction function,
# meant to check it never produces an out-of-bounds patch.
from hypothesis import given
import hypothesis.strategies as st
import numpy as np

@given(
    depth=st.integers(min_value=-10, max_value=200),
    height=st.integers(min_value=-10, max_value=200),
    width=st.integers(min_value=-10, max_value=200),
)
def test_extraction_bounds(depth, height, width):
    volume = np.random.rand(depth, height, width)
    patches = extract_patches(volume, patch_size=32, stride=16)
    for p in patches:
        assert p.shape == (32, 32, 32)
Hypothesis will find a failing example almost immediately — but not the one you'd expect from reading the assert.
The bug

The strategy itself is invalid before the assertion even matters: st.integers(min_value=-10, ...) allows negative dimensions, and np.random.rand(depth, height, width) raises a ValueError for negative arguments — so the test fails with a crash inside the test setup, not with a meaningful assertion about extraction bounds. This is a common Hypothesis mistake: writing a strategy that generates values your system under test can't even accept, so the shrinker reports a "failure" that has nothing to do with the property you actually meant to check, and it's easy to misread the crash as confirming a real bug in extract_patches when it's really a bug in the test.

The fix

Constrain the strategy to the domain the function under test actually accepts (e.g. min_value=32 to guarantee at least one patch fits, or explicitly test the too-small case as its own scenario with an expected exception), and separate "does the function reject invalid input correctly" from "does the function produce correctly-bounded output for valid input" as two distinct properties.

# Gradient-accumulation training step, generated to "support
# larger effective batch sizes on limited GPU memory."
accumulation_steps = 4
optimizer.zero_grad()

for step, (x, y) in enumerate(dataloader):
    x, y = x.to(device), y.to(device)
    pred = model(x)
    loss = criterion(pred, y)
    loss.backward()

    if (step + 1) % accumulation_steps == 0:
        optimizer.step()
        optimizer.zero_grad()

    running_loss = loss.item()
    if step % 50 == 0:
        print(f"step {step} loss {running_loss}")
Trains, loss goes down, curve looks plausible. Effective LR is still wrong.
The bug

The per-batch loss is never divided by accumulation_steps before backward(). Gradient accumulation is supposed to simulate a larger batch by summing gradients over several micro-batches before stepping — but without scaling the loss down first, the accumulated gradient is effectively accumulation_steps times larger than a true large-batch gradient would be, which acts like silently multiplying the learning rate by 4. The loss curve still trends downward — which is exactly why this bug survives code review by eye — but the effective optimization dynamics don't match what a real equivalent-batch-size run would produce.

The fix

Scale the loss before the backward call: loss = criterion(pred, y) / accumulation_steps, then loss.backward(). Also fix the smaller secondary issue: running_loss logs the scaled-down loss, which should be multiplied back by accumulation_steps (or tracked pre-scaling) so logged values stay comparable to a non-accumulated run.

# DP-SGD training step, generated as "standard differentially
# private gradient descent with gradient clipping and noise."
def dp_train_step(model, batch, optimizer, clip_norm=1.0, epsilon=1.0):
    x, y = batch
    optimizer.zero_grad()
    pred = model(x)
    loss = criterion(pred, y)
    loss.backward()

    # clip the gradient
    torch.nn.utils.clip_grad_norm_(model.parameters(), clip_norm)

    # add DP noise scaled by epsilon
    for p in model.parameters():
        if p.grad is not None:
            noise = torch.randn_like(p.grad) * (clip_norm / epsilon)
            p.grad += noise

    optimizer.step()
This trains, and the loss curve looks completely normal — that's exactly the danger.
The bug

Two compounding DP-SGD errors, either one alone would break the privacy guarantee. First: clip_grad_norm_ clips the already-aggregated gradient for the whole batch, not each example's gradient individually before aggregation — real DP-SGD requires per-sample gradient clipping (via per-example gradient computation, e.g. microbatching or a per-example-grad library) precisely because clipping the average does nothing to bound any single training example's influence on the result, which is the actual quantity DP is protecting. Second: the noise scale clip_norm / epsilon is not how Gaussian-mechanism sigma is derived — proper DP-SGD noise calibration comes from a composition accountant (moments accountant / RDP accountant) that accounts for the number of steps, sampling rate, and delta, not a single-step formula using epsilon directly as if privacy composed for free across the whole run. The code trains and produces a plausible loss curve while providing dramatically weaker privacy than the stated epsilon implies — the single most common "looks right, isn't" DP-SGD bug.

The fix

Compute per-example gradients, clip each one individually to clip_norm, sum the clipped per-example gradients, then add Gaussian noise with standard deviation derived from a proper privacy accountant given the noise multiplier, sampling rate, and number of steps — not from epsilon divided into a single step's clip norm.

review_w12.py
difficulty 12 / 12 — two independent bugs, one symptom
# FedAvg aggregation + train/val split setup for the
# integrated pipeline. Validation accuracy looks great —
# suspiciously better than the paper's reported baseline.

def federated_average(client_updates):
    # client_updates: list of (state_dict, num_samples)
    avg_state = {}
    for key in client_updates[0][0].keys():
        avg_state[key] = sum(sd[key] for sd, _ in client_updates) / len(client_updates)
    return avg_state

def make_split(all_items, val_frac=0.2):
    random.shuffle(all_items)
    n_val = int(len(all_items) * val_frac)
    return all_items[n_val:], all_items[:n_val]  # train, val
One is FL-specific, one is data-splitting-specific. They compound into one suspicious symptom.
Bug 1 — unweighted FedAvg

federated_average divides by len(client_updates), giving every client's update equal weight regardless of how many samples it trained on. Correct FedAvg weights each client's contribution by its local dataset size relative to the total, because a client with 500 samples and a client with 20 samples should not move the global model equally. With non-uniform client sizes and dropout, this systematically biases the aggregated model and inflates apparent convergence speed in ways that don't reflect a real deployment.

Bug 2 — item-level, not group-level, split

make_split shuffles and splits individual items. If those items are highly correlated within a group (slices from the same patient, frames from the same video, rows from the same user session), splitting at the item level near-guarantees that correlated items appear in both train and val — textbook data leakage. The model partially memorizes group-specific patterns rather than generalizing, producing an artificially high validation accuracy — exactly matching the suspiciously-good symptom described in the comment.

The fix

Weight federated_average by each client's num_samples relative to the total, and change make_split to shuffle and split at the group ID level first, only then expanding each group's items into their assigned split — with an assertion that no group ID intersects between train and val before training ever starts.

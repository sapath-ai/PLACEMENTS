F08

FINAL AI SECURITY ENGINEER BOARD

Defend the entire portfolio and capstone under a simulated senior-level technical, architecture and risk review.

Who this is for: Any project built with Cursor, Copilot, Claude, v0, Bolt, Lovable, Replit AI, or similar — or any project where you suspect more than 30% of the code was AI-generated. These tools ship predictable vulnerability patterns at scale.
01
Scope & Reconnaissance
Before touching any code, understand exactly what you're auditing. Define the attack surface. Read all READMEs, env files, deployment configs, and any AI tool configs (`.cursorrules`, `CLAUDE.md`, Copilot configs). Identify what the app does, what data it handles, and what AI tools were used to build it.
  • Map all entry points: API routes, forms, file uploads, webhooks
  • Identify auth boundaries: what requires login vs public
  • Note all third-party integrations and external API calls
  • Identify data sensitivity: PII, payments, health data, auth tokens
  • Document AI features in the app (LLM calls, embeddings, agents)
  • Note which AI coding tool built it — shapes vulnerability profile
  • Check git history: were secrets ever committed?
02
Automated Secret Scanning
AI tools frequently embed secrets directly in code. Run automated scans first — this is your fastest win and often the most critical finding. Scan the entire repo history, not just current state.
# Run all three — they catch different patterns trufflehog git file://. --since-commit HEAD~100 --only-verified gitleaks detect --source . --report-format json --report-path leaks.json detect-secrets scan > .secrets.baseline && cat .secrets.baseline # Check env files and configs manually too grep -r "sk-\|api_key\|secret\|password\|token" . --include="*.py,*.js,*.ts,*.env"
  • All three scanners run: trufflehog, gitleaks, detect-secrets
  • Full git history scanned (not just HEAD)
  • .env files and .env.example reviewed
  • Config files: docker-compose, k8s manifests, CI/CD yamls
  • All findings triaged: false positives removed, real leaks escalated immediately
  • Any leaked credential: rotated before proceeding
03
Dependency Vulnerability Scan
AI tools select dependencies with high plausibility but low security awareness. They often pick outdated packages, vulnerable versions, or confused packages. Run dependency audits across all package managers present.
# Python pip-audit -r requirements.txt --output json safety check --full-report # Node.js / JS npm audit --audit-level moderate --json snyk test --json # Containers trivy image your-image:tag --format json grype . --output json
  • All package managers audited (pip, npm, cargo, go.mod, etc.)
  • CVE severity critical/high findings documented with CVE IDs
  • Dependency confusion attacks checked (private package names)
  • Container base images scanned
  • Transitive (indirect) dependencies included
04
Static Code Analysis (SAST)
AI code has high rates of injection vulnerabilities, missing input validation, and broken auth patterns. Run SAST tools with rulesets tuned for AI-generated code patterns, not just generic code.
# Semgrep with AI-specific + OWASP rulesets semgrep scan --config p/owasp-top-ten --config p/python --config p/jwt \ --config p/secrets --json > semgrep-results.json # Python: Bandit bandit -r . -f json -o bandit-results.json -ll # JavaScript/TypeScript npx eslint . --ext .js,.ts --rulesdir eslint-security-rules --format json # SQL injection patterns (AI loves raw string concat) grep -rn "execute(\|query(\|cursor.execute" . | grep "f\"\|format(\|%"
  • Semgrep: OWASP + language-specific rulesets run
  • Bandit (Python) or ESLint-security (JS) complete
  • SQL injection: all raw query patterns found and reviewed
  • Command injection: os.system, subprocess, exec calls reviewed
  • Deserialization issues: pickle, yaml.load, eval() flagged
  • Path traversal: file open/read operations with user input
  • All findings triaged (remove false positives, rank real findings)
05
Authentication & Authorization Review
AI tools consistently generate auth that looks correct but has gaps: routes without middleware, JWT without expiry checks, admin checks that can be bypassed, and missing ownership validation (IDOR). This is manual — tools miss the logical flaws.
  • Every route: does it require auth? Is that correct?
  • JWT: algorithm verified (not "none"), expiry enforced, secret strong
  • IDOR check: can user A access user B's resources by changing IDs?
  • Admin routes: role check enforced server-side (not just client-side)
  • Password: bcrypt/argon2 used (not MD5/SHA1/plaintext)
  • Session: secure, httpOnly cookies; CSRF protection present
  • OAuth flows: state parameter present; redirect URIs validated
  • API keys: scoped minimally, rotatable, not user-facing secrets
06
AI/LLM Feature Audit
If the app has any LLM features — chatbots, AI assistants, RAG search, agent workflows — these need a dedicated security pass. AI components fail in completely different ways from traditional code.
  • System prompt: not user-accessible, not in client-side code
  • Prompt injection: test all user inputs that reach the LLM
  • Indirect injection: documents/URLs fed to LLM sanitised first
  • LLM tool/function calls: scope minimised, dangerous tools gated
  • RAG: does retrieval return data the user isn't authorised to see?
  • Output: does app blindly execute/render LLM output as HTML/code?
  • Rate limiting on LLM endpoints (cost + abuse protection)
  • Data leakage: does LLM echo back sensitive data from context?
  • Model API key: scoped, not hardcoded, rate-limited at provider
07
Dynamic Testing (DAST)
Run the app and attack it. Automated DAST tools find things static analysis misses — especially in how components interact at runtime. Also do manual testing of the most sensitive flows.
# OWASP ZAP automated scan zap-full-scan.py -t https://target-app.local -r zap-report.html -J zap-report.json # Nikto web server scan nikto -h https://target-app.local -Format json -output nikto-results.json # sqlmap on suspected injection points sqlmap -u "https://target/api/search?q=test" --batch --level 3 --risk 2 # nuclei: template-based vulnerability scanner nuclei -u https://target-app.local -t ~/nuclei-templates/ -j -o nuclei-results.json
  • OWASP ZAP full scan completed and reviewed
  • All input fields tested for XSS manually
  • All query parameters tested for SQL injection
  • File upload tested: malicious files, path traversal
  • API endpoints: unauthenticated access attempted on all
  • HTTP headers: security headers present (CSP, HSTS, X-Frame)
  • Error handling: does the app leak stack traces or DB info?
08
Infrastructure & Deployment Audit
AI-generated deployment configs (docker-compose, K8s manifests, Terraform) often have overpermissive IAM, exposed ports, missing network policies, and disabled security features. Review all infra-as-code.
  • Docker: no privileged mode, no root user, no exposed unnecessary ports
  • K8s: RBAC configured, NetworkPolicies present, secrets encrypted
  • Cloud IAM: least privilege — no wildcard permissions
  • Database: not internet-exposed, auth required, backups encrypted
  • Logging: all auth events, errors, and AI calls logged
  • HTTPS enforced everywhere, no HTTP fallback in prod
  • Environment separation: dev secrets ≠ prod secrets
09
Compile Report & Risk Matrix
Compile all findings into a structured report. Categorise by severity, map to OWASP/CVE references, and provide clear remediation for each finding. The report is the deliverable — make it client-readable.

  • All findings assigned severity (Critical / High / Medium / Low / Info)
  • Each finding has: description, impact, reproduction steps, fix guidance
  • Executive summary written (no jargon, business impact focus)
  • Risk matrix diagram included
  • Remediation priority order recommended
10
Re-test & Issue Certificate
After the client fixes critical and high findings, re-run your tools and manually verify each fix. Only issue a security certificate when all critical/high issues are remediated and your re-test confirms fixes are effective — not just applied.
  • All Critical findings: re-tested and confirmed fixed
  • All High findings: re-tested and confirmed fixed
  • Medium findings: addressed or accepted risk documented
  • Automated scans re-run: no new critical/high issues
  • Re-test report issued: lists what was fixed and verified
  • Audit certificate issued with date, scope, and your details
  • Recommended: schedule next audit (6 months or after major change)
Certificate scope matters. Your certificate covers what you tested, at the time you tested it. Always include scope limitations: "This audit covers the codebase as of [date] and does not cover [X, Y, Z]." Never certify what you didn't test.

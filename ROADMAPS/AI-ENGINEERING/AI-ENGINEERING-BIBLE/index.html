LLMs · Transformers · RAG · Software Engineering
Why This Matters
Understanding at a mechanistic level — not just API-calling level — is what separates senior AI engineers from junior ones. Everything else builds on these three pillars.
Transformer internals to internalise
  • Tokenisation (BPE) — Raw text → sub-word tokens. ~50k vocab. Non-English tokenises poorly.
  • Multi-head attention — Q·Kᵀ/√d_k scores relevance. Multiple heads learn syntax, coreference, semantics.
  • KV cache — Attention is O(n²). KV cache stores past key/value pairs. Why long contexts are expensive.
  • LoRA / QLoRA — Freeze base model, train low-rank adapters. 99%+ parameter reduction. Standard for fine-tuning.
  • Quantisation — fp32 → int8 → int4. Massive memory savings with acceptable quality loss.
RAG — the dominant production pattern
  • Naive RAG — Chunk → embed → store → retrieve top-k → inject into prompt.
  • Advanced RAG — Hybrid search (dense + BM25), re-ranking, HyDE, query rewriting, parent-child chunking.
  • Multimodal RAG — ColPali for page image retrieval. Table understanding. Figure captioning pipelines.
  • RAGAS evaluation — Faithfulness, answer relevancy, context recall, context precision. Always measure.

PHASE 1 — THE MCP RESET
MCP is no longer a “build a server + expose tools” checkbox. The 2026-07-28 specification makes MCP a stateless, routable, cacheable and extensible protocol for production agent infrastructure. This phase upgrades you from SDK familiarity to protocol-level engineering competence.
01 / Stateless Core
No initialize/initialized handshake and no protocol-level session ID. Every request carries the information needed to be independently routed. Understand why ordinary round-robin load balancing now works.
02 / Routable HTTP
Master MCP-Protocol-Version, Mcp-Method and Mcp-Name headers. Design gateways that can route, meter, authorize and observe MCP traffic.
03 / Cacheable Catalogs
Understand ttlMs, cacheScope and deterministic list ordering. Design safe caching for tools, resources and prompts without stale capabilities.

  • JSON-RPC semantics — Requests, responses, notifications, errors, IDs, validation and bounded schemas.
  • Server discovery — Understand server/discover without treating it as a mandatory handshake.
  • Tools / Resources / Prompts — Learn lifecycle, authorization and caching implications, not just definitions.
  • Multi Round-Trip Requests — Understand server-to-client interaction without permanent bidirectional protocol sessions.
  • Structured output — JSON Schema 2020-12, output schemas and safe schema validation.
Transport & infrastructure

  • Gateway routing — Route by protocol headers, tenant, capability and policy.
  • Catalog caching — Cache tool/resource/prompt catalogs while respecting authorization boundaries.
  • Rate limiting & backpressure — Protect expensive tools and downstream systems from agent bursts.

P2 GOD MODE
Agent Runtime Engineering
Durable Execution · Sandboxing · State · Recovery · Permissions · Long-Running Agents
PHASE 2 — STOP BUILDING CHATBOTS. BUILD RUNTIMES.
An agent is not a prompt wrapped in a while-loop. Production agents execute actions, hold state, call privileged tools, consume compute, fail halfway through tasks and must recover without corrupting the world. This phase turns agent knowledge into runtime-engineering competence. MCP is the connectivity protocol; this layer owns execution.
01 / Execution Lifecycle
Model decision → policy check → tool execution → observation → state update → next step. Define explicit lifecycle states, termination conditions, budgets and failure transitions.
02 / Durable Execution
Checkpoint long-running work so a process crash, network failure or machine restart does not erase the task. Resume from durable state rather than replaying blindly.
03 / Controlled Agency
Every tool call becomes a capability with identity, authorization, resource limits, auditability and optional human approval. The agent never receives unlimited authority by default.
Runtime architecture
  • Agent loop — Observe → decide → validate → act → observe. Define exactly where model output becomes executable behavior.
  • State machine — Explicit states for queued, running, waiting, blocked, approval-required, succeeded and failed.
  • Task identity — Stable task/run IDs, parent-child relationships, idempotency keys and correlation IDs.
  • Execution budgets — Max steps, token budget, wall-clock timeout, tool-call budget, compute budget and monetary ceiling.
  • Termination — Success predicates, failure predicates, loop detection and bounded retries. Never assume the model will stop itself.
  • Concurrency — Parallel tool calls, task queues, worker pools, backpressure and safe cancellation.
Durability & recovery
  • Checkpointing — Persist state at safe boundaries so work can resume after process failure.
  • Exactly-once illusion — Understand why external side effects usually require idempotency rather than magical exactly-once execution.
  • Retry policy — Exponential backoff, jitter, retry budgets and distinction between transient and permanent errors.
  • Crash recovery — Recover queued/running tasks after worker death without duplicating side effects.
  • Compensation — Saga-style compensating actions for multi-step workflows with irreversible side effects.
  • Human resume — Pause a task for approval or missing information, then continue from durable state.

Failure engineering — where agents actually break
  • Infinite loops — Repeatedly calling the same tool or generating equivalent plans.
  • Tool hallucination — Calling nonexistent tools, malformed arguments or unsupported operations.
  • Partial side effects — Step 3 succeeds while Step 4 fails, leaving the world in an intermediate state.
  • Duplicate actions — Retry causes duplicate emails, payments, tickets or database writes.
  • Stale state — Resume from an obsolete snapshot after the underlying resource changed.
  • Context exhaustion — Long-running tasks accumulate state until the model becomes ineffective.
  • Runaway cost — Agent consumes tokens/tools/compute without approaching the goal.
  • Worker loss — Process dies while holding a task; another worker must safely resume it.
  • Adversarial tool output — External content attempts prompt injection or instruction hijacking.
  • Permission drift — Agent gains capabilities that exceed the task it was originally authorized to perform.
ENGINEERING RULE
Never make “the model should behave” your safety mechanism. Runtime invariants, authorization, budgets, schemas, sandboxing, retries and state transitions must enforce the boundaries even when the model behaves badly.

P3 A2A 1.0
A2A — Agent Interoperability Engineering
Discovery · Agent Cards · Tasks · Artifacts · Streaming · Webhooks · Multi-Tenancy · Trust
PHASE 3 — AGENTS MUST TALK TO AGENTS
MCP connects agents to tools, resources and applications. A2A connects independent, potentially opaque agents to one another. The current released A2A specification is 1.0.0. This phase turns “multi-agent” from a framework demo into a protocol interoperability discipline: discovery, capability negotiation, asynchronous tasks, artifacts, security and versioning.
01 / Discovery
Agent Cards declare identity, skills, supported interfaces, capabilities and security requirements. Learn well-known discovery, registries and direct configuration.
02 / Collaboration
Delegate work without exposing another agent’s internal memory, tools or reasoning. Model collaboration as tasks, messages, parts and artifacts.
03 / Async by Design
Support synchronous responses, streaming, polling and push notifications. Long-running and human-in-the-loop work must survive disconnected clients.
A2A core data model
  • Agent Card — Identity, description, provider, supported interfaces, skills, capabilities and authentication requirements.
  • Message — A communication turn containing one or more Parts. Use messages for communication, not as the primary task-output channel.
  • Task — The fundamental unit of work with a stable ID and lifecycle. Understand terminal and non-terminal states.
  • Part — Text, file references or structured data carried inside messages and artifacts.
  • Artifact — Durable task output. Separate generated results from conversational/status messages.
  • Context — Group related tasks and messages without assuming agents share internal memory.
Operations to master
  • Send Message — Initiate work and understand when an agent returns a direct Message versus a Task.
  • Send Streaming Message — Receive incremental task status and artifact updates.
  • Get / List Task — Poll task state and retrieve authorized task information.
  • Cancel Task — Explicitly terminate work and reason about cancellation semantics.
  • Subscribe to Task — Maintain a stream for live updates when supported.
  • Push Notification Config — Configure webhook delivery for long-running or disconnected clients.

Multi-Tenancy
Route multiple agents or tenants behind one endpoint while preserving authorization boundaries, task isolation, tenant routing and data separation.
Security & trust
  • HTTPS / TLS — Production A2A communication must use encrypted transport.
  • Agent identity — Validate server identity and authentication requirements declared by the Agent Card.
  • Authorization — Scope access by identity, skills, actions, data policies, OAuth scopes and tenant boundaries.
  • In-task authorization — Support tasks that pause while authorization is obtained rather than giving agents unlimited authority.
  • Signed Agent Cards — Verify cryptographic integrity and provenance when signatures are provided.
  • Task isolation — Never leak task history, artifacts or existence across authorization boundaries.
  • Webhook security — Authenticate notifications, verify task IDs and process duplicate deliveries idempotently.
  • Opaque execution — Collaborating agents exchange capabilities and results without requiring access to private chain-of-thought, memory or tools.
ARCHITECTURE RULE — MCP ≠ A2A
Do not collapse the two protocols into “agent communication.” MCP is the tool/data/application connectivity layer. A2A is the agent-to-agent collaboration layer. A serious system can use both: an A2A agent delegates a task to another A2A agent, while each agent independently uses MCP to access its own tools and data.

Agent Evaluation & Eval Engineering
Task Success · Trajectories · Tool Use · RAG · Safety · Regression · Production Evaluation
PHASE 4 — IF YOU CANNOT MEASURE IT, YOU DO NOT CONTROL IT.
“The agent seemed good” is not an evaluation. Production AI requires a repeatable way to determine whether a model, RAG system or agent completed the user's objective, selected appropriate tools, respected policy, avoided unnecessary work and remained reliable as models, prompts, tools and data changed. This phase turns evaluation into an engineering system rather than a final demo checklist.
01 / Task Success
Define explicit success criteria before running the agent. Separate binary completion, graded quality, constraint adherence and user-visible outcomes.
02 / Trajectory Quality
Evaluate the path, not only the final answer: tool selection, argument correctness, unnecessary calls, recovery, ordering, policy compliance and budget efficiency.
03 / Regression Control
Every meaningful prompt, model, tool, retrieval or runtime change should be tested against a versioned evaluation set before production rollout.
Evaluation taxonomy
  • Model evals — Accuracy, instruction following, factuality, reasoning quality, robustness and format compliance.
  • RAG evals — Retrieval recall/precision, ranking quality, context relevance, groundedness and citation correctness.
  • Agent evals — Task completion, trajectory correctness, tool choice, recovery, latency and cost.
  • Tool evals — Schema adherence, argument validity, authorization behavior, error handling and idempotency.
  • Safety evals — Prompt injection, indirect injection, unsafe tool use, data exfiltration and privilege escalation.
  • System evals — End-to-end reliability, availability, latency, resource consumption and degradation behavior.
Evaluation modes
  • Offline — Curated datasets and deterministic test cases run before deployment.
  • Online — Sample production traces and score them continuously under privacy controls.
  • Shadow — Run a candidate system against real traffic without changing user-visible output.
  • Pairwise — Compare two systems on the same task rather than relying on an absolute score alone.
  • Human review — Expert adjudication for subjective or high-impact criteria.
  • Red-team — Deliberately search for failure modes instead of sampling only normal behavior.

Deterministic graders
Prefer exact or rule-based checks where possible: schemas, required fields, SQL results, tests passing, HTTP status, file existence, tool-call policy and objective completion.

Use rubric-driven model graders for subjective dimensions, but calibrate them against human judgments, test position/order bias and never treat a single judge score as truth.
Human adjudication
Maintain labeled samples for ambiguous, high-risk and high-impact cases. Measure inter-rater agreement and periodically recalibrate the rubric.
Evaluation dataset engineering
  • Golden set — Small, high-quality, human-validated cases representing critical behavior.
  • Adversarial set — Injection, malformed inputs, ambiguity, boundary conditions and malicious content.
  • Regression set — Every historically broken behavior becomes a permanent test.
  • Production samples — De-identified representative cases from real traffic under appropriate privacy controls.
  • Stratification — Slice by task type, difficulty, language, tool, customer/tenant and failure class.
  • Versioning — Version datasets, rubrics, graders and expected outputs independently.
  • Contamination control — Avoid leaking benchmark answers into prompts, retrieval corpora or synthetic generation.
  • Coverage analysis — Know what the suite does not test; a high score on a narrow dataset is not competence.
EVAL ANTI-PATTERNS
Do not optimize against one benchmark until it becomes meaningless. Do not let the same LLM generate the test, answer the test and grade the test without independent controls. Do not report a single “agent quality” number while hiding catastrophic failures in important slices. Always retain per-case evidence and failure categories.

P5 CRITICAL
AI Observability & Telemetry
OpenTelemetry · Traces · Metrics · Logs · Agent Trajectories · Cost · Quality · Reliability
PHASE 5 — IF YOU CANNOT SEE THE SYSTEM, YOU CANNOT OPERATE IT.
Evaluation tells you whether the system was good. Observability tells you what the system actually did, where time and money went, which component failed, which tool was called, what the model consumed and how a production request moved through the entire AI stack. This phase makes AI systems diagnosable.
01 / Distributed Traces
Trace a request across gateway → agent → model → retrieval → tool → database → response. Preserve parent/child relationships and correlation IDs across asynchronous work.
02 / GenAI Signals
Capture model identity, provider, operation, token usage, latency, tool calls, retrieval context and agent events without turning telemetry into a privacy leak.
03 / Operational Control
Convert telemetry into alerts, SLOs, cost controls, incident investigation, regression detection and capacity decisions. Dashboards are outputs, not observability itself.
OpenTelemetry foundation
  • Traces — Spans, parent/child relationships, trace IDs, span IDs, attributes and events.
  • Metrics — Counters, gauges, histograms, rates and latency distributions.
  • Logs — Structured events correlated to traces rather than isolated text logs.
  • Context propagation — Carry correlation across HTTP, queues, workers, async tasks and service boundaries.
  • OTLP — Understand telemetry transport, collectors and backend-agnostic instrumentation.
  • Semantic conventions — Use standardized GenAI attributes where available instead of inventing incompatible field names.
AI-specific telemetry
  • Model calls — Provider, model, operation, request/response metadata, latency and usage.
  • Token accounting — Input, output and cached-token usage; associate consumption with requests, users and workloads.
  • Tool calls — Tool identity, arguments policy, result status, duration, retries and downstream dependencies.
  • Retrieval — Query, retriever, top-k, document identifiers, ranking metadata and retrieval latency.
  • Agent trajectories — Steps, decisions, state transitions, approvals and task lifecycle events.
  • Costs — Model/provider pricing, infrastructure cost allocation and cost per successful task.

DO NOT MEMORIZE “DISAGGREGATION = FASTER”
Disaggregation is workload-dependent. It can independently scale and size prefill and decode, improve tail-latency control and prevent long prefills from disrupting decode, but it adds KV-transfer and orchestration overhead. For small models, short prompts or low concurrency, aggregated serving may be simpler and faster. Benchmark both architectures under the same workload. citeturn0search3turn0search10

Classic optimization levers
  • Coalescing — Make global memory transactions efficient.
  • Reuse — Move data closer to compute and reuse it.
  • Fusion — Remove intermediate memory traffic and launch overhead.
  • Occupancy — Increase active warps only when it helps hide latency.
  • Instruction efficiency — Reduce unnecessary instructions and dependencies.
  • Asynchrony — Overlap data movement, communication and computation.
Advanced optimization levers
  • TMA pipelines — Stage tiles asynchronously.
  • Cluster cooperation — Coordinate blocks beyond a single block.
  • Tensor Core utilization — Match shapes/layouts/precision to matrix hardware.
  • CUDA Graphs — Reduce repeated launch overhead.
  • L2 locality — Shape reuse and cache behavior deliberately.
  • Communication overlap — Hide NCCL/NVLink/network costs behind useful compute.

REWARD HACKING IS A FIRST-CLASS CURRICULUM ITEM
If the reward can be gamed, the model will eventually find the loophole. Build independent verification, hidden tests, adversarial cases, held-out tasks and multiple reward signals. Never use the training reward as the sole evidence that reasoning improved.
Reasoning data engineering
  • Distilled traces — Generate reasoning demonstrations from stronger models, then filter aggressively.
  • Verifier filtering — Retain only traces that solve the task correctly under an independent verifier.
  • Difficulty curriculum — Mix easy, medium and frontier tasks to avoid training only on one difficulty regime.
  • Contamination control — Prevent benchmark solutions from leaking into training data.
  • Trajectory diversity — Avoid teaching one brittle reasoning template.
Reasoning evaluation
  • Held-out tasks — Test on unseen problems and domains.
  • Transfer — Measure whether gains survive outside the reward/training distribution.
  • Efficiency — Track accuracy versus tokens, latency and compute.
  • Robustness — Perturb wording, distract the model and vary tool/environment conditions.
  • Capability regression — Ensure reasoning gains do not destroy general instruction following.
Distillation — make reasoning cheaper
Logit / Distribution Distillation
Transfer the teacher's token distribution or softened targets rather than only its final answer. Understand temperature, KL/JSD-style objectives and sequence-level trade-offs.
On-Policy Distillation

Synthetic data failure modes
  • Model collapse — Recursive synthetic training can narrow distributions and amplify artifacts.

Benchmark engineering
Benchmark construction
  • Representative sampling — Match the actual task distribution rather than optimizing a convenient toy set.
  • Difficulty strata — Separate easy, medium and hard cases.
  • Hidden tests — Keep evaluation examples unavailable to training and tuning loops.
  • Golden answers — Use verified references where objective correctness is possible.
  • Adversarial cases — Include failures deliberately, not only normal traffic.
  • Versioning — Evaluation sets must be immutable/versioned artifacts.
Benchmark hygiene
  • Contamination checks — Search training sources and generated corpora for benchmark overlap.
  • Prompt stability — Avoid accidental improvements caused by wording changes.
  • Leakage control — Separate development, validation and final test sets.
  • Slice integrity — Do not let aggregate scores hide subgroup regressions.
  • Temporal splits — Use future data where freshness/generalization matters.
  • Re-evaluation — Retest old claims when evaluation methodology changes.
BENCHMARK SCORE ≠ CAPABILITY
A score can increase because of contamination, prompt optimization, evaluator leakage, benchmark-specific tuning or changes in scoring methodology. The Bible therefore requires multiple independent evaluation views and held-out tests before claiming a capability improvement.

ENGINEERING RULE
“Model A scored 84.2 and Model B scored 85.0” is not enough. Report the evaluation set, uncertainty, paired comparison where appropriate, effect size, slices and experimental conditions. A 0.8-point gain may be huge, noise or a benchmark artifact depending on the experiment.
A/B testing for AI systems
  • Unit of randomization — User, session, request or task; choose based on interference/carryover.
  • Control — Preserve a stable baseline for comparison.
  • Treatment — Change one meaningful variable where possible.
  • Guardrails — Monitor safety, latency, cost and failure metrics alongside the primary outcome.
  • Sample size — Estimate required traffic before declaring success.
  • Sequential testing — Do not repeatedly peek and stop whenever the metric looks good without a valid design.
  • Novelty effects — Allow systems/users to stabilize before final interpretation.
  • Network effects — Watch for users or agents sharing state across variants.
  • Segment analysis — Check whether gains are concentrated in one workload.
  • Rollback — Define stop conditions before deployment.

The NVIDIA / DeepMind Gate

  • Pipeline parallelism — Different layers on different GPUs. GPipe, PipeDream.

Mathematical Foundations: Derive, Not Just Use
Linear Algebra · Calculus · Probability · Information Theory · Numerical Stability
The DeepMind / NVIDIA Maths Bar
DeepMind interviews are designed to assess whether you can translate theory into computational form. You will be asked to derive the attention gradient, explain why cross-entropy is correct from first principles, or prove that softmax temperature scales entropy. This section makes that knowledge explicit and actionable.
What you must be able to derive
  • Backpropagation — Chain rule applied repeatedly. Derive gradients for softmax, cross-entropy, attention.
  • Why cross-entropy — Minimising cross-entropy = maximising log-likelihood of data under model. Know this derivation cold.
  • KL divergence — Measure of distribution difference. Appears in RLHF penalty, VAE loss, distillation. KL(P‖Q) ≠ KL(Q‖P).
  • LoRA via SVD — If W = U·S·Vᵀ, LoRA approximates ΔW = A·B where rank(A·B) = r. Why low-rank preserves information.
Numerical stability — the NVIDIA bar
  • bf16 vs fp16 — bf16 has fp32's dynamic range (8 exponent bits). Far fewer overflow issues. Modern LLMs train in bf16.
  • Stable softmax — Naive exp(x_i)/Σexp(x_j) overflows. Stable: subtract max(x) first. Common interview question.
  • Loss scaling — fp16 gradients underflow. Scale loss before backward, unscale before update. PyTorch AMP does this.
  • NaN debugging — NaN propagates backward. Causes: log(0), division by zero, overflow. Use detect_anomaly().

  • The core idea — Replace FFN with N expert FFNs. Router selects top-K per token. Parameters and compute decouple.
  • Load balancing problem — Without balancing, all tokens route to same experts. Solutions: auxiliary loss, expert choice routing.
  • DeepSeek-V3 MLA — Multi-head Latent Attention. Low-rank KV projection reduces KV cache by ~60%. Combined with MoE for dramatic efficiency.
  • DeepSeek aux-loss-free balancing — Dynamic bias per expert instead of a loss term. Cleaner gradient flow.
Modern architecture innovations
  • RoPE — Rotary position embeddings. Better length generalisation. LLaMA, Mistral, Gemma.
  • SwiGLU — Swish(xW) * xV activation. Outperforms GELU. LLaMA, PaLM, Gemma standard.
  • RMSNorm — Removes mean-centering from LayerNorm. Cheaper, equally effective. Modern standard.
  • GQA / MQA — Grouped/Multi-Query Attention. Reduce KV heads. Used in LLaMA 3, Gemma, Mistral.

Systems Design & Architecture for AI
Distributed Systems · AI Architecture Patterns · Judgment Framework · 20 Canonical Designs
Why This Is Genuinely Irreplaceable
AI can generate a plausible-looking architecture diagram. It cannot make the judgment calls that determine whether that architecture survives contact with reality — traffic spikes, partial failures, data drift, budget constraints, and team turnover. This is the discipline, not just the interview patterns.
10 distributed systems fundamentals
  • CAP Theorem — Consistency, Availability, Partition tolerance. Choose CP or AP. Your vector DB choice is a CAP trade-off.
  • Back-of-envelope estimation — 10M embeddings at 1536 dims in fp32 = ~58GB. Practice weekly. Asked directly.
  • Consistent hashing — Route same user to same server for KV cache affinity in LLM serving.
  • Circuit breakers — Stop calling a failing service to let it recover. Essential for multi-LLM-provider setups.
  • Idempotency — Operations safely retried. If your embedding job fails midway, restarting must not create duplicates.
AI-specific architecture patterns
  • Feature stores — Computed once, reused across models, with point-in-time correctness. Feast, Tecton.
  • Shadow deployment — New model runs in parallel with production. Compare outputs offline. Zero user risk.
  • Canary releases for models — Route 1% → 5% → 10% → 100%. Auto-rollback if metrics degrade.
  • Semantic caching — Embed query, find similar past queries, return cached response if similarity > threshold. 30–60% LLM cost reduction.
  • Two-tower architecture — Separate query and document encoders. Pre-compute doc embeddings. Only run query encoder at query time.

1. Clarify requirementsLatency (p99, not average), throughput, consistency, failure modes, budget, cost of being wrongAssuming requirements. Most architecture failures start here.

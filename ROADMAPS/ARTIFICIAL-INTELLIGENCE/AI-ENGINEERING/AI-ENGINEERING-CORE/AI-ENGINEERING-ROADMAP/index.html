Skills Universe

Start here before entering the phases. This is the canonical capability map: every major skill has an explicit curriculum, practice requirements, proof artifact, and capability exit standard. The phases tell you when to learn it; this section tells you what mastery actually means.

Use this as the depth layer for the entire roadmap.

Do not treat a phase card as the complete curriculum. When a phase says Python, Transformers, RAG, CUDA, or any other capability, come back here for the detailed specification. Each card tells you exactly what to study, what to practice, what to build, and what counts as passing.

M1
Linear Algebra
foundational · gates everything
why it matters
Every neural network is a chain of matrix operations; interpretability, optimization, and attention mechanisms are unreadable without fluency here.
subtopics
Vectors & vector spacesMatrix multiplication & inversesEigenvalues / eigenvectorsSVD & PCANorms & inner productsQR / Cholesky decompositionTensor ops & broadcasting
CAPABILITY CURRICULUM — WHAT YOU MUST ACTUALLY COVER
1 · THEORY / CONCEPTS
  • Scalars, vectors, matrices, tensors; shapes, ranks, axes and broadcasting
  • Dot products, matrix multiplication, transpose, inverse, trace, determinant and quadratic forms
  • Norms, inner products, projections, orthogonality, subspaces, basis changes and geometric interpretation
  • Eigenvalues/eigenvectors, diagonalization, SVD, QR and Cholesky; know what problem each decomposition solves
  • Least squares, normal equations, PCA, covariance, whitening, embeddings, low-rank approximation and attention projections
  • Numerical conditioning, floating-point error, stable solves, avoiding explicit matrix inversion and checking dimensions
2 · HANDS-ON PRACTICE
  • Derive and implement matrix operations with NumPy without relying on high-level ML libraries
  • Implement least-squares regression and PCA from scratch; compare against trusted libraries
  • Implement a small attention block and trace every tensor shape through Q/K/V
  • Solve numerical edge cases: singular matrices, ill-conditioned systems and rank-deficient data
3 · CAPABILITY EXIT STANDARD
  • Explain every operation geometrically and algebraically
  • Choose an appropriate decomposition for a concrete problem
  • Debug a shape/broadcasting/numerical error without guessing
  • Produce a short derivation plus tested implementation for a real ML component
what exactly to cover
  1. Core objects: scalars, vectors, matrices, tensors, shapes and dimensionality.
  2. Operations: dot products, matrix multiplication, transpose, inverse, trace, determinant and broadcasting.
  3. Geometry: norms, distances, projections, orthogonality, subspaces and basis changes.
  4. Decompositions: eigenvalues/eigenvectors, SVD, QR and Cholesky; know when each is useful.
  5. ML connections: least squares, PCA, embeddings, covariance matrices, attention projections and low-rank approximations.
  6. Numerical practice: conditioning, floating-point error, stable formulations and why naive inversion can fail.
learn via
Gilbert Strang's linear algebra course, 3Blue1Brown's "Essence of Linear Algebra" for intuition, then a proof-based text if going the research route.
project to prove it
Implement backprop and an attention layer from raw numpy, no autograd.
M2
Probability & Statistics
foundational
why it matters
Loss functions, evaluation design, A/B testing, and uncertainty quantification are all applied statistics.
subtopics
Random variables & distributionsBayes' theoremMLE / MAP estimationHypothesis testing & p-valuesConfidence intervalsCentral limit theoremSampling methodsBias-variance decomposition
CAPABILITY CURRICULUM — WHAT YOU MUST ACTUALLY COVER
1 · THEORY / CONCEPTS
  • Conditional probability, independence, Bayes rule, total probability and expectation
  • Discrete/continuous random variables and Bernoulli, Binomial, Categorical, Gaussian, Multivariate Gaussian and Poisson distributions
  • Expectation, variance, covariance, correlation, conditional expectation and common transformations
  • MLE, MAP, likelihood, priors, estimators, bias/variance and confidence intervals
  • Sampling, CLT, bootstrap, hypothesis tests, Type I/II errors, power, effect size and multiple comparisons
  • A/B testing, calibration, uncertainty, dataset shift and statistical interpretation of model metrics
2 · HANDS-ON PRACTICE
  • Simulate distributions and verify theoretical expectations numerically
  • Perform MLE/MAP on a small dataset and derive the objective
  • Design an A/B test with power analysis, effect size and stopping criteria
  • Bootstrap a model metric and report uncertainty rather than a single point estimate
  • Analyze a misleading statistical result and explain why it is misleading
3 · CAPABILITY EXIT STANDARD
  • Choose an appropriate statistical test or confidence procedure
  • Distinguish statistical significance from practical significance
  • Explain sampling bias, leakage and confounding
  • Report uncertainty and limitations honestly
what exactly to cover
  1. Probability: conditional probability, independence, Bayes rule, expectation, variance and covariance.
  2. Distributions: Bernoulli, Binomial, Gaussian, Multivariate Gaussian, Poisson and categorical distributions.
  3. Estimation: likelihood, MLE, MAP, estimators, bias/variance and confidence intervals.
  4. Testing: null/alternative hypotheses, Type I/II errors, power, p-values and multiple-comparison issues.
  5. ML evaluation: sampling, train/validation/test splits, bootstrap confidence intervals and calibration.
  6. Experimentation: A/B testing, effect sizes, statistical significance vs practical significance, and sequential-testing pitfalls.
learn via
A standard mathematical statistics course; supplement with Bayesian methods if working on evaluation or RLHF.
project to prove it
Design and run a proper A/B test with power analysis for a small project, not just a p-value.
M3
Optimization
foundational
why it matters
Understanding why training diverges, plateaus, or overfits requires knowing what SGD/Adam are actually doing.
subtopics
Convexity & gradientsSGD & momentumAdam / AdamW / RMSpropLearning-rate schedulesSecond-order methods (Newton, L-BFGS)Lagrange multipliersLoss landscape geometry
CAPABILITY CURRICULUM — WHAT YOU MUST ACTUALLY COVER
1 · THEORY / CONCEPTS
  • Derivatives, gradients, Jacobians, Hessians and chain rule
  • Convexity, smoothness, Lipschitz intuition, local/global minima, saddle points and conditioning
  • SGD, momentum, RMSProp, Adam and AdamW: derive the update rules and understand their state
  • Learning-rate schedules, warmup, decay, gradient clipping, weight decay, normalization and initialization
  • Second-order methods, Newton/L-BFGS, constrained optimization and Lagrange multipliers at awareness level
  • Training diagnosis: divergence, plateaus, exploding/vanishing gradients, bad conditioning and unstable loss
2 · HANDS-ON PRACTICE
  • Implement SGD, momentum and Adam from scratch
  • Visualize optimization trajectories on convex and non-convex losses
  • Run controlled experiments changing learning rate, batch size, optimizer, initialization and weight decay
  • Diagnose a deliberately broken training run and document the root cause
  • Compare optimizer behavior with fixed seeds and repeated trials
3 · CAPABILITY EXIT STANDARD
  • Derive why an optimizer update has its form
  • Select an optimizer and schedule based on workload characteristics
  • Diagnose training instability systematically
  • Explain optimization tradeoffs rather than memorizing optimizer names
what exactly to cover
  1. Calculus: partial derivatives, gradients, Jacobians, Hessians and chain rule.
  2. Optimization geometry: convexity, smoothness, local/global minima, saddle points and conditioning.
  3. Optimizers: SGD, momentum, RMSProp, Adam and AdamW; understand update equations rather than memorizing names.
  4. Schedules: warmup, cosine decay, step decay, one-cycle and learning-rate scaling.
  5. Practical training: gradient clipping, weight decay, normalization, initialization and diagnosing divergence/plateaus.
  6. Advanced awareness: L-BFGS/Newton methods, constrained optimization, Lagrange multipliers and loss-landscape intuition.
learn via
A convex optimization course for fundamentals, then read the original Adam/AdamW papers directly.
project to prove it
Implement SGD, momentum, and Adam from scratch and compare convergence on a toy loss landscape.

Python (production-grade)
foundational
why it matters
The default language across the entire stack; the bar is "can you write tested, typed, maintainable code," not just "can you write a script."
subtopics
Type hints & mypyTesting (pytest, fixtures, mocking)Packaging (pyproject.toml)Async/concurrency (asyncio, threading)Decorators & context managersProfiling & memory optimizationCI basics (GitHub Actions)
CAPABILITY CURRICULUM — WHAT YOU MUST ACTUALLY COVER
1 · THEORY / CONCEPTS
  • Core language: functions, classes, modules, packages, iterators/generators, comprehensions, exceptions and context managers
  • Design: separation of concerns, interfaces, dependency injection, composition, API boundaries and clean module structure
  • Typing: annotations, generics, Protocol, TypedDict/dataclasses, mypy or pyright and runtime-vs-static validation
  • Testing: pytest, fixtures, parametrization, mocks, integration tests, property-based testing awareness and test isolation
  • Packaging: pyproject.toml, virtual environments, dependency pinning/locking, package layout, versioning and publishing
  • Concurrency: asyncio, threading, multiprocessing, queues, cancellation, timeouts and CPU-bound vs I/O-bound work
  • Production tooling: logging, configuration, environment variables, secrets handling, linting, formatting, profiling, memory analysis and CI
  • Performance: algorithmic complexity, profiling before optimization, allocations, serialization overhead, NumPy vectorization and when native extensions are justified
2 · HANDS-ON PRACTICE
  • Build a package rather than a script: CLI/API entry point, typed public interfaces and documentation
  • Write unit + integration tests and deliberately test failure paths, not only happy paths
  • Create a CI pipeline that runs formatting, static checks, tests and packaging
  • Build one async service with cancellation, timeout and retry behavior
  • Profile CPU and memory usage, identify one real bottleneck and prove the optimization with measurements
  • Practice refactoring a 300–500 line messy script into modules with tests and explicit interfaces
3 · CAPABILITY EXIT STANDARD
  • A reviewer can install and run the project without manual environment surgery
  • Public functions are typed and have clear contracts
  • Tests cover normal, edge and failure behavior
  • CI is green and reproducible
  • You can explain every concurrency and architecture decision
  • You can debug a production-style exception from logs and reproduce it locally
what exactly to cover
  1. Language: functions, classes, iterators/generators, comprehensions, exceptions, modules and clean API design.
  2. Typing: type hints, Protocol, generics, dataclasses and static checking with mypy/pyright.
  3. Testing: pytest, fixtures, parametrization, mocks, integration tests and testable architecture.
  4. Packaging: pyproject.toml, virtual environments, dependency locking, package structure and semantic versioning.
  5. Concurrency: asyncio, threading vs multiprocessing, queues, cancellation and I/O-bound vs CPU-bound work.
  6. Production quality: logging, configuration, secrets handling, profiling, memory analysis, linting/formatting and CI.
learn via
Ship a real package with tests, type hints, and CI — reading a book only gets you to syntax fluency.
project to prove it
A pip-installable package with >80% test coverage and a CI pipeline.

  • Implement a thread-safe producer/consumer pipeline and measure contention
3 · CAPABILITY EXIT STANDARD
  • Explain ownership/lifetime of every important object
  • Use profiling and sanitizers rather than guessing about performance or correctness
  • Design a native component with a stable Python boundary
  • Demonstrate measurable benefit over a straightforward Python implementation
what exactly to cover
  1. C++: RAII, pointers/references, move semantics, smart pointers, templates, STL and modern C++17/20 patterns.
  2. Rust: ownership, borrowing, lifetimes, traits, enums, Result/Option and Cargo.
  3. Memory: stack vs heap, allocation, cache locality, alignment and lifetime management.
  4. Concurrency: threads, mutexes, atomics, lock-free concepts and data races.
  5. Performance: profiling, allocations, SIMD awareness, zero-copy paths and avoiding unnecessary serialization.
  6. AI integration: pybind11/PyO3, tensor memory layouts, custom operators and inference/runtime components.

SQL
foundational
why it matters
Almost every role eventually needs to pull, join, and aggregate data directly — a surprisingly common interview filter.
subtopics
SELECT / WHERE / GROUP BYJoins (inner/outer/cross)Window functionsCTEs & subqueriesIndexing & query optimizationReading query plans (EXPLAIN)
CAPABILITY CURRICULUM — WHAT YOU MUST ACTUALLY COVER
1 · THEORY / CONCEPTS
  • Querying: SELECT, filtering, CASE, NULL semantics, aggregation, dates/times and conditional aggregation
  • Joins: inner/outer/cross joins, join cardinality, duplicate amplification and anti/semi-join patterns
  • Advanced SQL: CTEs, subqueries, correlated queries, window functions, recursive queries and set operations
  • Database fundamentals: keys, constraints, normalization, transactions, isolation and indexes
  • Performance: B-tree/hash/index concepts, composite indexes, EXPLAIN/query plans, partitioning and avoiding scans
  • AI data workflows: dataset construction, feature extraction, labeling, deduplication, temporal splits and reproducible snapshots
2 · HANDS-ON PRACTICE
  • Solve analytical problems using joins + windows rather than procedural code
  • Take a slow query, inspect EXPLAIN, form a hypothesis, change the query/index and benchmark it
  • Build a training dataset query with point-in-time correctness and leakage prevention
  • Write queries for monitoring model quality, drift and production usage
  • Practice SQL under interview time limits with messy schemas and ambiguous requirements
3 · CAPABILITY EXIT STANDARD
  • Predict query cardinality before running it
  • Explain why an index helps or does not help
  • Prevent leakage and duplicate rows in dataset-building SQL
  • Optimize a query using evidence from an execution plan
  • Write readable SQL another engineer can safely modify
what exactly to cover
  1. Querying: SELECT, filtering, aggregation, CASE, NULL semantics and date/time operations.
  2. Joins: inner/left/right/full/cross joins, join cardinality and avoiding accidental row multiplication.
  3. Advanced SQL: CTEs, subqueries, correlated queries, window functions and recursive queries.
  4. Database fundamentals: primary/foreign keys, constraints, normalization and transaction basics.
  5. Performance: indexes, composite indexes, EXPLAIN/query plans, partitioning and avoiding expensive scans.
  6. AI data work: feature extraction, dataset construction, analytics, labeling queries and reproducible data snapshots.
learn via
Work through window-function and query-optimization exercises, not just SELECT/WHERE basics.
project to prove it
Write the analytics queries behind a dashboard, including a query you had to optimize for performance.

Transformers & Attention
core
why it matters
The dominant architecture across text, vision, and increasingly audio — you cannot reason about modern models without this.
subtopics
Self-attention & scaled dot-productMulti-head attentionPositional encodingsLayer norm & residual connectionsEncoder/decoder architecturesKV cachingTokenization (BPE, WordPiece)
CAPABILITY CURRICULUM — WHAT YOU MUST ACTUALLY COVER
1 · THEORY / CONCEPTS
  • Tokenization and embeddings; BPE/WordPiece/SentencePiece concepts and vocabulary tradeoffs
  • Scaled dot-product attention: Q/K/V, masking, softmax, temperature and dimensions
  • Multi-head attention, residual streams, normalization and feed-forward/MLP blocks
  • Encoder-only, decoder-only and encoder-decoder architectures; causal vs bidirectional attention
  • Positional information: absolute, learned, sinusoidal and rotary/relative-position concepts
  • LLM internals: logits, sampling, temperature/top-k/top-p, KV cache and prefill/decode
  • Efficiency: attention complexity, FlashAttention concepts, MQA/GQA and memory/compute tradeoffs
  • Training: next-token prediction, batching, masking, loss calculation, initialization and checkpointing
2 · HANDS-ON PRACTICE
  • Implement a tokenizer or use a minimal tokenizer and inspect tokenization failures
  • Implement single-head and multi-head attention from raw tensors
  • Build a tiny decoder-only transformer and train it on a small corpus
  • Instrument the model to print tensor shapes, parameter counts, activation memory and attention behavior
  • Change one architectural component at a time and evaluate the effect
  • Implement or profile KV caching during autoregressive generation
3 · CAPABILITY EXIT STANDARD
  • Trace one input token through embedding → attention → MLP → logits
  • Derive attention equations without notes
  • Explain compute/memory complexity and the main inference bottlenecks
  • Debug masking, shape and numerical errors
  • Produce a trained miniature model plus an architecture and experiment report
what exactly to cover
  1. Architecture: token embeddings, positional information, self-attention, cross-attention and feed-forward blocks.
  2. Attention math: Q/K/V projections, scaled dot-product attention, masking and multi-head attention.
  3. Transformer variants: encoder-only, decoder-only and encoder-decoder architectures.
  4. LLM internals: residual streams, normalization, MLP blocks, logits, sampling and KV cache concepts.
  5. Efficiency: causal masking, FlashAttention concepts, grouped/multi-query attention and memory/compute tradeoffs.
  6. Hands-on: implement a tiny transformer, train it, inspect attention shapes and trace a token through the forward pass.
learn via
"Attention Is All You Need" plus Karpathy's from-scratch GPT walkthroughs.
project to prove it
A GPT-style model trained from scratch on a small corpus, with your own tokenizer.

  • Measure freshness and update behavior after source documents change
3 · CAPABILITY EXIT STANDARD
  • Explain why each retrieval component exists
  • Diagnose whether failure comes from parsing, chunking, retrieval, reranking, context assembly or generation
  • Produce retrieval metrics before and after each change
  • Demonstrate security boundaries and reproducible ingestion
  • Know when SQL/metadata/graph retrieval beats vector search
what exactly to cover
  1. Ingestion: document parsing, OCR, metadata extraction, cleaning, deduplication and versioning.
  2. Chunking: fixed/semantic/structure-aware chunking, overlap, parent-child retrieval and chunk-quality evaluation.
  3. Embeddings: embedding models, normalization, similarity metrics, dimensionality and embedding drift.
  4. Retrieval: dense search, BM25/sparse search, hybrid retrieval, filters, top-k and query rewriting.
  5. Ranking: rerankers, reciprocal-rank fusion, score calibration and retrieval failure analysis.

L2
Fine-tuning: LoRA / QLoRA / PEFT
applied-genai
why it matters
Lets you specialize a large model on limited compute — the practical alternative to full pretraining for most teams.
subtopics
Low-rank decompositionAdapter layersQuantization (4-bit/8-bit)Full fine-tune vs. PEFT tradeoffsCatastrophic forgetting mitigationMerging/unmerging adapters
CAPABILITY CURRICULUM — WHAT YOU MUST ACTUALLY COVER
1 · THEORY / CONCEPTS
  • When to fine-tune vs prompt/context engineering vs RAG vs tool use
  • Dataset construction: task format, instruction quality, diversity, deduplication, contamination and train/validation/test splits
  • SFT: objective, masking, batching, sequence packing, learning-rate/epoch choices and overfitting
  • LoRA: low-rank adapters, target modules, rank/alpha/dropout and parameter counts
  • QLoRA: 4-bit quantization concepts, NF4, double quantization and compute dtype tradeoffs
  • Evaluation: task metrics, regression suites, held-out behavior, catastrophic forgetting and qualitative error analysis
  • Training engineering: checkpoints, seeds, experiment tracking, gradient accumulation, mixed precision and reproducibility
  • Deployment: adapter loading/merging, versioning, rollback and inference-cost implications
2 · HANDS-ON PRACTICE
  • Build a clean baseline before fine-tuning
  • Create and audit a dataset with explicit inclusion/exclusion rules
  • Run a small SFT experiment with at least one ablation over learning rate, rank or data size
  • Compare base vs fine-tuned model on both target and non-target capabilities
  • Measure parameter count, memory use, training cost and inference impact
  • Test for overfitting, contamination and catastrophic forgetting
3 · CAPABILITY EXIT STANDARD
  • Justify why fine-tuning was necessary
  • Show a baseline and statistically/operationally meaningful delta
  • Explain every major training hyperparameter
  • Reproduce the run from a configuration file
  • Document failure cases and rollback strategy
  • Know when the correct answer is: do not fine-tune
what exactly to cover
  1. Data: instruction formatting, quality filtering, deduplication, contamination checks and train/eval splits.
  2. SFT: objective, batching, masking, sequence packing, learning-rate selection and checkpointing.
  3. PEFT: LoRA rank/alpha/dropout, target modules, adapters and when full fine-tuning is justified.
  4. QLoRA: 4-bit quantization concepts, NF4, double quantization and compute dtype tradeoffs.
  5. Evaluation: task metrics, regression tests, held-out behavior, catastrophic forgetting and qualitative error analysis.
  6. Engineering: reproducible configs, experiment tracking, model merging, adapter serving and deployment rollback.
learn via
The LoRA and QLoRA papers directly, then Hugging Face's PEFT library documentation.
project to prove it
Fine-tune an open-weight model on a custom dataset and document the eval delta versus the base model.

How the AI industry actually works

A map of the terrain before you pick a path through it. The roles, the money, and the hiring bar all sit downstream of a few structural facts about who builds AI and why.

The four kinds of employer

Frontier labs

Train and ship foundation models (language, vision, multimodal). Hire the fewest people, at the highest research bar — strong math, publications or equivalent independent research, and systems fluency at scale. Compensation is the highest but roles are narrow and brutally competitive.

Product companies

Big tech and established software companies embedding AI into existing products (search, ads, productivity, cloud). Value shipping velocity, strong software engineering fundamentals, and the ability to work inside huge existing codebases and infra.

AI-native startups

Building a product where the model is the product, or where AI is the primary differentiator. Want generalists who can do data engineering, model work, and product instincts in one person. Highest variance in outcome, highest learning velocity.

Enterprise adopters

Non-tech companies (finance, healthcare, manufacturing, retail) applying existing AI tooling to their domain. Value domain knowledge plus applied ML more than research depth. Often the most accessible entry point and the least glamorous.

Research vs. product vs. infrastructure

Almost every AI role falls into one of three tracks, and confusing them is the most common early-career mistake:

  • Research track — advances what models can do. Needs mathematical depth, experiment design, and the patience for work that mostly fails. Publications, open-source research artifacts, or a strong independent research portfolio substitute for a PhD in some hiring pipelines, but not most.
  • Product / applied engineering track — makes existing model capability useful and reliable in a real system. Needs strong software engineering, evaluation discipline, and product judgment. This is where the largest number of jobs actually are.
  • Infrastructure track — makes training and inference fast, cheap, and reliable at scale. Needs systems programming, distributed computing, and hardware-aware thinking (GPUs, networking, memory). Smaller headcount, very high leverage, historically under-supplied relative to demand.

Employment models beyond full-time

Remote-first roles

Increasingly common at AI-native companies with distributed teams; usually demand more written communication and self-direction since there's less ambient context-sharing than in an office.

Freelance / consulting

Short applied-ML or MLOps engagements for companies without in-house AI teams. Requires a track record you can show before anyone will hire you without an interview loop.

Founding / building

Starting a company around a model capability or workflow. The hiring bar becomes irrelevant — the bar becomes whether the product survives contact with users.

Open-source-first

Some engineers build reputation entirely through public repositories and research artifacts, which then substitutes for a conventional resume in hiring conversations.

On numbers: salary bands, headcount growth, and "hot" sub-fields move fast enough that any specific figure printed here would be stale within a year. Treat every quantitative claim about the market as directional, and re-verify anything decision-relevant close to when you act on it.

Where growth is concentrated right now

As of 2026, hiring demand is disproportionately weighted toward roles that make existing model capability reliable and cheap to run rather than roles that push raw capability forward: applied/agentic AI engineering, evaluation and observability, inference and serving infrastructure, and domain-specific applied ML (healthcare, finance, robotics). Loop Engineer
agentic · new discipline
overview
Designs and hardens the core think-act-observe control loop an agent runs on: how it plans a step, executes it, reads the result, and decides whether to continue, retry, or stop. As agents got longer-horizon in 2025–2026, the loop itself became something teams hire specifically to own, separate from the model or the tools it calls.
daily work
Tuning planning/execution/reflection cycles, designing retry and backoff behavior on tool failure, setting termination and budget conditions (token/time/step limits), preventing infinite or thrashing loops, instrumenting the loop for debuggability.
core skills
Strong Python/systems engineering, state-machine thinking, agent frameworks internals (not just API usage), debugging non-deterministic multi-step systems.
math floor
Low to moderate; this is closer to distributed-systems reasoning than to ML theory.
interview shape
Design an agent loop with explicit termination/retry logic; debug a transcript of a loop that got stuck or looped forever.
portfolio signal
An agent loop you built with documented, tested termination conditions and a failure-mode log showing how you caught and fixed stuck/thrashing behavior.
related roles
Harness Engineer, Graph Engineer, LLM/GenAI Engineer, Agent Engineer

overview

daily work

core skills

math floor
Graph theory basics (DAGs, cycles, topological ordering) more than statistical math.
interview shape

portfolio signal
A multi-node agent graph with conditional branching and a visualized/debuggable execution trace, not just a linear chain relabeled as a "graph."
related roles
Loop Engineer, Harness Engineer, LLM/GenAI Engineer, Agent Engineer

What each kind of employer actually expects

The bar isn't uniform. Calibrate your prep to the archetype you're targeting.

Frontier labs

  • Publications, strong reproductions, or equivalent research artifacts
  • Deep math + ability to modify framework internals
  • Research presentation / paper-discussion interview
  • Extremely low acceptance rate; multiple loops common

Big tech / product companies

  • Strong DSA coding bar (LeetCode-medium/hard fluency)
  • ML system design round
  • Behavioral interview weighted heavily
  • Take-home or onsite case study on applied ML

AI-native startups

  • Portfolio and shipped projects matter more than credentials
  • Practical take-home reflecting real work
  • Culture/generalist-fit conversation
  • Speed of learning is explicitly evaluated

Enterprise / consultancies

  • Domain knowledge and communication skills weighted highly
  • Cloud certifications often explicitly valued
  • Client-scenario or case-study interviews
  • Lower bar on cutting-edge research fluency

Remote-first companies

  • Written communication assessed directly (async work samples)
  • Self-direction and ownership signals matter more than pedigree
  • Trial-project or paid work-trial common

Open-source-first hiring

  • Your public commit history functions as the resume
  • Code review quality and issue triage visible to reviewers
  • Often skips a formal coding round entirely if history is strong
Universal signal: across every archetype, the single most consistent differentiator is a small number of deep, working, evaluated projects — not a long list of tutorials completed.

Open source, step by step

The workflow that matters, plus the structured programs that give beginners a lower-friction entry point.

The mechanics

  • Fork & clone — your own copy of the repo to work in.
  • Branch — one feature or fix per branch, never work on main.
  • Commit — small, well-described commits are a review signal in themselves.
  • Pull request — explain what and why, link the issue it resolves.
  • Code review — expect back-and-forth; how you respond to critique is itself evaluated.

First-contribution roadmap

  • Start with documentation fixes or "good first issue" labels to learn the maintainers' workflow with low stakes.
  • Move to small bug fixes with a reproducible test case attached.
  • Graduate to a feature contribution once you understand the codebase's conventions.
  • Stay consistent — one meaningful contribution a month beats a ten-PR burst followed by silence.

Structured entry programs

Google Summer of Code

Paid summer program pairing contributors with open-source orgs on a defined project.

Outreachy

Paid remote internships in open source, with a focus on groups underrepresented in tech.

Hacktoberfest

Annual month-long event encouraging beginner-friendly contributions across participating repos.

LFX Mentorship

Linux Foundation program mentoring contributors into specific open-source projects, including several ML-infra ones.

MLH Fellowship

Structured fellowship pairing early-career engineers with open-source or industry projects.

Coding

Standard DSA (arrays, trees, graphs, DP) plus numpy/pandas manipulation exercises specific to ML interviews.

ML theory

Bias-variance tradeoff, regularization, loss function choices, why specific architectures make specific tradeoffs.

Statistics

Hypothesis testing, confidence intervals, experiment design — often tested via a case study, not definitions.

ML system design

Design a recommendation system / fraud detector / RAG pipeline end to end: data, training, serving, monitoring, failure modes.

LLM-specific design

Design an agent, an eval harness, or a fine-tuning pipeline — increasingly its own interview category in 2026.

Behavioral

Concrete stories with real tradeoffs and outcomes — vague "I'm a team player" answers fail here more often than technical gaps do.

Research presentation

For research-track roles: present a paper or project clearly, defend methodology choices under questioning.

Take-homes

Treat the write-up as seriously as the code — clarity about tradeoffs you made is often weighted as heavily as the result.

Glossary

Use the search box in the sidebar — it filters this list live.

Attention mechanism
A way for a model to weigh how much each element of its input should influence each output, the core operation inside transformers.
Backpropagation
The algorithm that computes gradients of a loss with respect to every parameter in a network by applying the chain rule backward through the computation graph.
Batch normalization
A technique that normalizes layer inputs across a mini-batch to stabilize and speed up training.
Bias-variance tradeoff
The tension between a model being too simple to capture the pattern (high bias) and too sensitive to noise in training data (high variance).
Chain-of-thought prompting
Prompting a model to produce intermediate reasoning steps before a final answer, often improving accuracy on multi-step problems.
Checkpoint
A saved snapshot of a model's weights at a point in training, used for resuming, evaluation, or deployment.
Context window
The maximum number of tokens a model can attend to at once, bounding how much input/history it can use.
CUDA
NVIDIA's parallel computing platform and API for writing code that runs directly on GPUs.
Data parallelism
A distributed training strategy that splits a batch of data across multiple devices, each holding a full copy of the model.
Diffusion model
A generative model that learns to reverse a gradual noising process, used heavily in image and audio generation.
Distillation
Training a smaller "student" model to mimic a larger "teacher" model's outputs, trading some quality for efficiency.
DPO (Direct Preference Optimization)
A method for aligning a model to human preferences directly from comparison data, without a separate reward model.
Embedding
A dense vector representation of an input (word, sentence, image) that captures semantic meaning in a form models can compute over.
Epoch
One complete pass through the entire training dataset.
Evaluation harness
The tooling and test sets used to systematically measure a model or system's quality against defined criteria.
Feature store
A centralized system for storing, versioning, and serving features used in ML training and inference.
Few-shot learning
Giving a model a handful of examples within the prompt to steer its behavior, without updating its weights.
Fine-tuning
Continuing training of a pretrained model on a smaller, task-specific dataset.
Gradient descent
The core optimization algorithm that updates parameters in the direction that reduces the loss.
Hallucination
A model generating output that is fluent but factually incorrect or unsupported by its input/training.
Inference
Running a trained model to produce outputs on new inputs, as opposed to training it.
Interpretability
The study of understanding what's happening inside a trained model — which features, circuits, or representations drive its outputs.
Knowledge graph
A structured representation of entities and their relationships, used to ground or augment model reasoning.
KV cache
Cached key/value tensors from previous tokens during autoregressive generation, avoiding recomputation and speeding up inference.
Latency
The time between a request and a system's response — a primary constraint in production inference systems.
LoRA (Low-Rank Adaptation)
A fine-tuning method that trains small low-rank matrices instead of all model weights, drastically reducing compute needed.
LLMOps
The practices and tooling for deploying, monitoring, and maintaining LLM-based systems in production.
Mixture of experts (MoE)
An architecture where only a subset of a model's parameters ("experts") are activated per input, increasing capacity without proportional compute cost.
Model parallelism
Splitting a single model's layers or parameters across multiple devices when it's too large to fit on one.
Overfitting
A model learning patterns specific to its training data that don't generalize to new data.
PEFT (Parameter-Efficient Fine-Tuning)
An umbrella term for fine-tuning methods (like LoRA, adapters) that update only a small fraction of a model's parameters.
Perplexity
A measure of how well a language model predicts a sample, with lower values indicating better predictive fit.
Prompt injection
An attack where malicious instructions embedded in input data cause a model to deviate from its intended behavior.
Quantization
Reducing the numerical precision of a model's weights (e.g. from 32-bit to 4-bit) to shrink its size and speed up inference.
RAG (Retrieval-Augmented Generation)
Grounding a language model's output by retrieving relevant documents at inference time and including them in its context.
Reranker
A model that reorders an initial set of retrieved candidates by relevance, used to improve RAG retrieval quality.
RLHF (Reinforcement Learning from Human Feedback)
Training a model to align with human preferences by using human comparisons to train a reward signal.
Sparse autoencoder (SAE)
An interpretability tool that decomposes a model's internal activations into a larger set of sparse, more interpretable features.
Synthetic data
Artificially generated training data, often produced by another model, used to augment or replace scarce real data.
Token
The basic unit (often a word-piece) that a language model processes and generates.
Tokenization
The process of splitting text into tokens before feeding it into a model.
Transfer learning
Reusing a model trained on one task as the starting point for a related task, rather than training from scratch.
Transformer
A neural network architecture built around self-attention, the foundation of nearly all modern large language and vision models.
Vector database
A database optimized for storing and searching high-dimensional embeddings by similarity, core infrastructure for RAG.
Vision-language model (VLM)
A model trained to jointly process and reason over both images and text.
Weight decay
A regularization technique that penalizes large parameter values during training to reduce overfitting.
Zero-shot learning
A model performing a task it was never explicitly trained or shown examples for, relying on generalization alone.
Activation function
A non-linear function applied at each layer that lets neural networks model non-linear relationships.
Adapter
A small module inserted into a pretrained model and trained in place of the full model, another parameter-efficient fine-tuning approach.
Autoregressive model
A model that generates outputs one token at a time, each conditioned on all previous tokens.
Benchmark
A standardized dataset and task used to compare model performance, only as meaningful as its construction is rigorous.
Catastrophic forgetting
A model losing previously learned capabilities while being fine-tuned on new data.
Circuit (interpretability)
A specific subgraph of a model's components identified as jointly responsible for a particular behavior.
Cross-validation
A technique for estimating model performance by training and testing on multiple different data splits.
Feature engineering
Manually constructing input features from raw data to improve a model's ability to learn a task.
Gradient checkpointing
A memory-saving technique that recomputes some activations during backpropagation instead of storing them all.
Latent space
The internal, compressed representation space a model learns to encode its inputs into.
Multi-head attention
Running several attention operations in parallel so a model can attend to different types of relationships simultaneously.
Positional encoding
Information injected into a transformer's input so it can distinguish token order, since attention alone is order-agnostic.
Speculative decoding
An inference speedup technique where a small model drafts multiple tokens that a larger model verifies in parallel.
Throughput
The number of requests or tokens a system can process per unit time, a key metric alongside latency for serving systems.

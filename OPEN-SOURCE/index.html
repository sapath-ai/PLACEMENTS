What Is Open Source, Really?

Foundations ~2h ▶

The core idea

Open Source means the source code of a program is publicly available under a license that lets anyone read it, run it, modify it, and redistribute it. That's the legal definition. The cultural definition is bigger: Open Source is a production model — a way of building software where the "company" is a loosely coordinated network of strangers, and the product ships continuously in public, in the open, with the entire history of every decision visible in the commit log.

Almost nobody pays to use Linux, PostgreSQL, React, PyTorch, or Kubernetes — yet these projects collectively underpin trillion-dollar industries. Understanding why that works is the real prerequisite to contributing well.

A short history

1983 — GNU Project

Richard Stallman starts GNU to build a free (as in freedom) Unix-like OS, and writes the GPL — the first copyleft license, which says: if you distribute a modified version, you must share the source too.

1991 — Linux

Linus Torvalds releases the Linux kernel. Combined with GNU tools, it becomes the dominant free OS for servers, and eventually phones (Android) and cloud infrastructure.

1998 — "Open Source" coined

The term is created deliberately to be more business-friendly than "free software" — emphasizing practical development benefits (faster bug-fixing, peer review) over the moral framing.

2005 — Git

Torvalds writes Git to manage Linux kernel development after a licensing dispute with the previous tool. Git's distributed model makes large-scale collaborative development tractable.

2008 — GitHub launches

Turns Git from a command-line tool into a social network for code: forks, pull requests, issues, and profiles turn contribution into something visible and reputational.

2014–2020 — Corporate OSS

TensorFlow (Google), React (Meta), Kubernetes (Google→CNCF), VS Code (Microsoft): large companies open-source core infrastructure as a talent and ecosystem strategy, not charity.

2019–2023 — the AI/ML explosion

PyTorch overtakes TensorFlow in research; Hugging Face turns model + dataset sharing into a GitHub-like social layer; open-weight LLMs (Llama, Mistral, Qwen, DeepSeek) make "open source AI" its own fast-moving category.

2023–2026 — agentic & inference-layer OSS

The center of gravity moves toward inference/serving (vLLM, Ollama, llama.cpp), orchestration (LangChain, LangGraph, LlamaIndex), and protocol-level projects (Model Context Protocol) — exactly where a contributor entering now has the most leverage.

Free Software vs. Open Source: two philosophies, same license text

Free Software (FSF)Open Source (OSI)
Core argumentEthical: users deserve the freedom to run, study, modify, share softwarePragmatic: open development produces better software faster
Typical licensesGPL, AGPL (copyleft — derivatives must stay open)MIT, Apache-2.0, BSD (permissive — derivatives can go closed)

In practice, most AI/ML repositories you'll contribute to use permissive licenses (Apache-2.0, MIT) because companies want adoption without giving up the right to build closed products on top.

Reading a license in 30 seconds

MIT

Do almost anything, including closed-source use, as long as you keep the copyright notice. The simplest, most permissive common license.

Apache-2.0

Like MIT, plus an explicit patent grant — contributors can't later sue users for patent infringement on their own contributions. Preferred by many corporate-backed AI projects.

GPL-3.0 / AGPL-3.0

Copyleft: if you distribute a modified version (AGPL: even as a network service), you must release your source under the same license. Common in infrastructure tools where the authors want to prevent proprietary forks.

Why companies pour billions into something "free"

  • Recruiting funnel. A great OSS project is a permanent, self-selecting interview pipeline — companies hire top contributors they've already watched work for months.
  • Commoditizing the complement. Giving away the framework (PyTorch, Kubernetes) increases demand for the paid layer above it (cloud compute, managed services, support contracts).
  • De facto standards. Whoever's framework becomes the default gets outsized influence over how an entire industry builds — see how much AI research is described in "PyTorch-shaped" terms.
  • Distributed QA. Thousands of unpaid eyes finding bugs and edge cases is a testing budget no single company could otherwise afford.
  • Trust and auditability. Especially in security and AI safety-adjacent tooling, "you can read the code" is itself the product's credibility.

Why individual developers contribute for free

  • Scratching their own itch — fixing a bug that's actually blocking their own work.
  • Learning by reading world-class codebases and getting free code review from senior engineers.
  • Reputation — a public, verifiable, hard-to-fake portfolio (this is the lever this roadmap is built around).
  • Access to programs with stipends (GSoC, LFX, Outreachy — covered in Module 13).
  • Employer sponsorship — many senior engineers contribute to OSS as their job, paid by a company that depends on the project.

How Modern Software Is Built

Foundations ~3h ▶

Before touching Git specifically, internalize the machinery around it — the concepts every serious repository assumes you already understand.

TermWhat it actually is
RepositoryA directory whose full history is tracked — every saved snapshot, forever, by default.

Semantic Versioning (SemVer) — the number that isn't just marketing

MAJOR . MINOR . PATCH e.g. 2.4.1 MAJOR — incremented on breaking changes (your code may need updates) MINOR — incremented on new, backward-compatible features PATCH — incremented on backward-compatible bug fixes only

Reading a CHANGELOG.md and the version diff before upgrading a dependency is a habit that separates professionals from people who get paged at 3am.

Package managers you'll actually touch in AI/ML work

pip / PyPI

Python's default — requirements.txt or pyproject.toml.

conda / mamba

Handles non-Python binary deps (CUDA, MKL) that pip can't — common in ML environments.

uv / poetry

Modern, fast, lockfile-based Python dependency managers gaining ground across 2025–2026 AI repos.

npm / pnpm

JavaScript — you'll meet these in the frontend of tools like LangGraph Studio or model playgrounds.

The full lifecycle of a change, end to end

1. Issue filed

A bug, feature request, or discussion is opened and triaged (labeled, prioritized, sometimes assigned).

2. Branch created

A contributor forks/branches off the latest main to work in isolation.

3. Commits made

Small, logical, well-described snapshots — ideally each one could stand alone in a revert.

4. Tests + docs updated

A change without a test is treated as unfinished in most serious projects.

5. Pull Request opened

CI runs automatically; the diff becomes visible for human review.

6. Code review

Maintainers request changes, discuss tradeoffs, approve.

7. Merge

The change lands on main, often squashed into one clean commit.

8. Release

Eventually bundled into a tagged, versioned release with changelog entry.

Git & GitHub Mastery

Core Skill ~6h ▶

Setup, once

git config --global user.name "Your Name" git config --global user.email "you@example.com" git config --global init.defaultBranch main git config --global pull.rebase false # SSH key (preferred over HTTPS + password for daily work) ssh-keygen -t ed25519 -C "you@example.com" cat ~/.ssh/id_ed25519.pub # paste into GitHub → Settings → SSH Keys

HTTPS vs SSH: HTTPS is simpler to start with and works everywhere including corporate firewalls that block SSH port 22. SSH avoids typing a token every push once configured. Most contributors end up on SSH for daily work.

The fork → clone → branch loop (the shape of almost every contribution)

1. Fork the-project/repo → you/repo (on GitHub, one click) 2. Clone git clone git@github.com:you/repo.git 3. Remote git remote add upstream git@github.com:the-project/repo.git 4. Sync git fetch upstream && git merge upstream/main 5. Branch git checkout -b fix/broken-link-in-readme 6. Work ... edit, commit ... 7. Push git push origin fix/broken-link-in-readme 8. PR open a Pull Request from you:fix/broken-link-in-readme → project:main

origin = your fork (where you push). upstream = the original project (where you pull the latest changes from, but never push directly, since you don't have write access).

Commands worth actually being fluent in

Everyday

  • git status / git diff
  • git add -p — stage hunks selectively
  • git commit -m "..."
  • git log --oneline --graph
  • git stash / git stash pop

History surgery

  • git rebase -i HEAD~3 — squash/reorder commits
  • git rebase upstream/main — replay your branch on latest main
  • git cherry-pick <sha> — grab one commit onto another branch
  • git commit --amend — fix the last commit
  • git reset --soft HEAD~1 — undo a commit, keep changes staged

Merge vs. Rebase — the debate every new contributor walks into

MergeRebase
What happensCreates a new "merge commit" joining two historiesReplays your commits on top of the target branch, one by one
History shapePreserves exactly what happened, including branchingProduces a clean, linear history
DangerNoisy history on long-lived branchesRewrites commit hashes — never rebase a branch others have already pulled
Where you'll see it requiredSome large projects (Kubernetes) prefer merge commits for traceabilityMany projects (React, most Rust/Go repos) require a rebased, linear PR before merge

Rule that prevents 90% of Git disasters: only rebase branches that are yours alone and haven't been shared. Once someone else has pulled your branch, merge instead.

Resolving a merge conflict without panicking

$ git merge upstream/main Auto-merging src/utils.py CONFLICT (content): Merge conflict in src/utils.py <<<<<<< HEAD def normalize(x): return x / x.max() ======= def normalize(x, eps=1e-8): return x / (x.max() + eps) >>>>>>> upstream/main # pick / merge the correct version by hand, then: git add src/utils.py git commit

.gitignore — keeping noise out of history

Ignore build artifacts, dependency folders, secrets, and OS files (__pycache__/, node_modules/, .env, .DS_Store). Most languages have a canonical starter template — never write one from scratch when GitHub's gitignore templates already exist.

The GitHub platform beyond the code

Actions

YAML-defined CI/CD pipelines that run tests, build docs, publish packages on every push/PR — the backbone of the contribution workflow.

Projects

Kanban-style boards that map issues/PRs to a roadmap — where maintainers plan releases.

Discussions

Forum-style Q&A separate from issues — for "how do I…" questions that aren't bugs.

Wiki

Longer-form community-editable documentation, less common now that docs sites (MkDocs, Docusaurus) dominate.

Releases

Tagged snapshots with changelogs and downloadable build artifacts.

Stars / Watch / Fork

Star = bookmark of approval. Watch = notification subscription. Fork = your own copy to modify freely.

Reading order for an unfamiliar repository

1. README first

Get the elevator pitch and the "quickstart" running locally before reading a line of source.

2. CONTRIBUTING.md

This overrides your generic Git knowledge — it tells you the project's actual required workflow (branch naming, commit style, test commands).

3. Directory structure

Look for src/, tests/, docs/, examples/ — orient yourself before diving into any one file.

4. The test suite

Tests are often the most honest, up-to-date documentation of how the code actually behaves.

5. Open issues labeled "good first issue"

Real, scoped problems maintainers have pre-vetted as approachable — the fastest path to your first contribution (Module 8).

Contribution Workflow, Step by Step

Core Skill ~2h ▶
1. Find the issue

Filter by good first issue / help wanted. Prefer issues with a maintainer comment clarifying scope over vague ones.

2. Claim it, don't ghost it

Comment "I'd like to work on this" and wait for an assignment or acknowledgement — prevents duplicate work and shows professionalism.

3. Understand before you code

Read the surrounding module, trace how the function is called elsewhere, check for existing tests covering it.

4. Reproduce locally

Get the project running, and reproduce the bug or the missing behavior yourself before writing a fix.

5. Make the minimal correct change

Resist the urge to refactor everything around it — scope creep is the #1 reason first PRs stall in review.

6. Add or update a test

A bug fix without a regression test can silently reappear. Most maintainers will request this if you skip it.

7. Lint and format

Run the project's exact linter/formatter (ruff, black, eslint) — CI will fail otherwise, and it's an easy, avoidable round-trip.

8. Write real commit messages

Imperative mood, explain why: fix: prevent divide-by-zero in normalize() when max()==0, not fix bug.

9. Open the PR

Fill the template. Link the issue (Closes #482). Describe what changed and why, and how you tested it.

10. Handle review

Treat requested changes as normal, not personal. Push follow-up commits; don't force-push over a reviewer's in-progress comments unless asked.

11. Merge and move on

Once merged, your fix ships in the next release. Delete your branch. Go find the next issue.

A commit message that will get merged vs. one that won't

✗ "fixed stuff" ✗ "Update utils.py" ✓ "fix(tokenizer): handle empty string input in encode() encode("") previously raised IndexError because the token list was empty before the padding step. Added an early return + regression test. Closes #214"

GitHub Etiquette: How Not To Get Ignored

Soft Skills ~1h ▶

Writing an issue that gets answered

  • One issue = one problem. Never bundle three unrelated bugs.
  • Include: what you expected, what happened, exact steps to reproduce, version numbers, and a minimal code sample.
  • Search existing issues first — duplicates cost maintainer time and read as not having done homework.

Writing a PR description that gets reviewed quickly

  • Lead with what and why, not a play-by-play of every line changed — the diff already shows that.
  • State how you tested it, and screenshot/output for anything visual.
  • Keep the PR small. A 40-line PR gets reviewed same day; a 2,000-line PR gets ignored for weeks.
  • Mark draft PRs as Draft — signals "not ready for full review yet, but visible for early feedback."

Reviewing someone else's code well

  • Comment on the code, never the person: "this could leak memory on the error path" not "you always forget error handling."
  • Distinguish blocking issues from nitpicks explicitly — prefix nits with nit: so authors know what's optional.
  • Approve with minor comments rather than blocking on style preferences.

Receiving criticism without it stalling your PR

Requested changes are the default outcome for a first PR to any serious project, not a rejection. The fastest contributors treat every review round as free senior-engineer mentorship and respond within a day or two — momentum matters as much as correctness; stale PRs get closed by bots.

The unwritten rules that keep you from getting ignored

Do

  • Read CONTRIBUTING.md before your first PR to any project
  • Ask clarifying questions on the issue before starting big work
  • Keep PRs scoped to one logical change
  • Say thank you when a maintainer reviews your work — they're volunteering time

Don't

  • Open a giant unsolicited refactor PR with no prior discussion
  • Ping maintainers repeatedly within 24 hours
  • Argue with a maintainer's design decision in your first interaction — ask "why" instead of asserting "this is wrong"
  • Submit AI-generated PRs without understanding or testing the code yourself — maintainers can tell, and it burns trust fast

Preparing for Your First Contribution

Milestone ~4h ▶

Choosing the right first repository

Your first PR should be boringly easy and to a healthy project — not an exciting deep contribution to a project that will teach you nothing about the process because it's abandoned or hostile.

Signs of a healthy project

  • Commits in the last 2–4 weeks
  • Issues get triaged/labeled within days
  • PRs get first review within ~1–2 weeks
  • Active CONTRIBUTING.md and CI badges passing
  • Multiple maintainers, not a single bus-factor-1 owner

Signs of an abandoned project

  • No commits in 6+ months
  • Dozens of open PRs with zero comments
  • Last release years old, unresolved security issues
  • Sole maintainer inactive on every recent issue

"Good First Issue" vs. "Help Wanted" — they are not the same

LabelActually means
good first issueScoped, low-context-required, safe for a newcomer to attempt without deep project knowledge
help wantedMaintainers want outside help, but it may need real project context — read the thread before assuming it's beginner-friendly
documentationOften the fastest legitimate path to a first merged PR, and genuinely valuable — don't treat it as lesser

Judging project health before you invest time

  • Check the Insights → Pulse and Contributors tabs for recent activity trends.
  • Skim the last 10 closed PRs — were they merged in days or ignored for months?
  • Read 2–3 recent issue threads to gauge maintainer tone — respectful and constructive, or curt and overwhelmed?

Environment setup: the part everyone underestimates

1. Read the "Development" section of CONTRIBUTING.md

It usually gives the exact setup commands — don't improvise.

2. Use an isolated environment

A fresh virtualenv/conda env or devcontainer, so you're not fighting your global Python install.

3. Run the existing test suite untouched, first

If tests fail before you've changed anything, that's a setup problem — fix that before writing code.

4. Find a beginner bug yourself, if none are labeled

Try an edge case (empty input, huge input, wrong type) the README's examples don't cover — you'll often surface a real small bug.

First, the fear itself — why you genuinely cannot "break" a real codebase

This is the part almost nobody explains clearly to beginners, and it's the actual reason to stop being scared:

  • You never touch the real project. Forking makes a private copy under your account. Every edit you make happens there — the original repository is physically untouched until a maintainer chooses to pull your changes in.
  • A Pull Request is a request, not an action. Opening one just says "here's a suggested change, please review it." Nothing merges, deploys, or runs anywhere until a human with write access explicitly clicks "Merge."
  • Almost every serious repo has branch protection. Non-maintainers structurally cannot push straight to the main branch even if they wanted to — GitHub blocks it at the permissions level.
  • CI catches mistakes before a human even looks. If your change breaks tests, the PR is flagged red automatically, before it can be merged (Module 2).
  • Nothing in Git is ever truly gone. Every commit is a permanent snapshot. Even a bad merge can be reverted with one command, restoring the exact prior state.
  • The absolute worst realistic outcome is a maintainer says "not quite, try this instead" — which is just a code review comment, not a consequence. Every contributor currently working at a top AI lab has a closed or rejected PR somewhere in their history. It's normal, not embarrassing.

The single safest possible first move: a repo built specifically for this fear

AI Domain Contribution Roadmaps

AI Focus ongoing ▶

Pick one domain to go deep in for your first 10–15 contributions rather than spreading thin — depth reads as expertise to recruiters; breadth without depth reads as dabbling.

Machine Learning & Classical ML

Learning order: scikit-learn → pandas → XGBoost/LightGBM. Beginner: fix a docstring example that no longer runs. Intermediate: add a missing parameter validation or a new estimator test. Advanced: implement a new algorithm variant with benchmark against the paper. Skills gained: estimator API design, numerical correctness testing. Demand: steady baseline requirement for most ML Engineer roles; companies: every company doing tabular ML, fintech, ad-tech.

Deep Learning Frameworks

Learning order: PyTorch → JAX. Beginner: fix an operator's docstring or add a missing type hint. AI Evaluation Engineering: Measure Before You Ship

Core AI Skill ~8h + ongoing ▶

Why this module exists

Evaluation is not a final QA step. For modern LLM, RAG, and agent systems, it is part of the engineering loop: define the behavior you want, build a representative test set, measure the system, change one thing, re-run the evals, inspect failures, and promote only when quality, latency, cost, and safety remain inside your acceptance criteria.

Rule: never describe an AI system as “working” because a few examples looked good. Produce evidence.

The evaluation stack

1. Dataset

Representative inputs, expected behavior, references where available, adversarial cases, edge cases, and regression cases. Version it like code.

2. Metrics

Choose metrics that correspond to failure modes: correctness, relevance, groundedness, retrieval quality, tool-call accuracy, task success, safety, latency, and cost.

3. Decision gate

Define pass/fail thresholds, acceptable regressions, and release criteria before looking at the results. A score without a decision rule is just a number.

LLM evaluation

Evaluate the model/application at the task level, not just the raw model. Separate reference-based checks (exact match, structured assertions, factual correctness) from reference-free or rubric-based checks (relevance, style, safety, completeness). Use an LLM judge when the property is difficult to express as a deterministic rule, but calibrate it against human judgments and test for judge instability and bias.

Core techniques

  • Golden/reference datasets
  • Exact match, structured assertions, unit tests
  • Rubric-based scoring
  • LLM-as-judge with explicit criteria
  • Pairwise comparison / A-B testing
  • Human evaluation for calibration and high-risk cases

Failure analysis

  • Slice results by task type, language, difficulty, source, and model
  • Inspect false positives and false negatives
  • Track score distributions, not only averages
  • Keep known failures as regression cases
  • Separate model failures from retrieval/tool/data failures
  • Document evaluator assumptions and limitations

RAG evaluation

Do not collapse RAG quality into one answer score. Evaluate the retriever and the generator separately, then evaluate the end-to-end system. Important retrieval signals include context precision and context recall; important generation signals include faithfulness/groundedness, answer relevance, and factual correctness. Ragas currently exposes these families of metrics along with noise sensitivity and other task-specific metrics. Ragas evaluation metrics

Retrieval

Recall@k, precision@k, context precision, context recall, ranking quality, and retrieval latency.

Generation

Faithfulness, groundedness, factual correctness, answer relevance, completeness, and refusal behavior where appropriate.

End-to-end

Task success, user-facing correctness, citation quality, latency, token usage, cost, and failure rate.

Agent evaluation

An agent is a trajectory, not a single response. Evaluate whether it achieved the goal, selected appropriate tools, supplied valid arguments, recovered from failures, respected constraints, and avoided unnecessary steps. Keep both final outcome and trajectory evidence.

What to measure

  • Task / goal success
  • Tool-call accuracy and argument correctness
  • Trajectory quality and unnecessary-step rate
  • State / memory correctness
  • Recovery after tool or model failure
  • Policy / safety adherence

Test the ugly paths

  • Missing or malformed tool results
  • Conflicting instructions
  • Unavailable services and timeouts
  • Ambiguous user intent
  • Prompt injection / malicious tool output
  • Long-horizon tasks and partial completion

Offline vs. online evaluation

ModeUse it forTypical evidence
OfflineRegression testing before releaseFixed datasets, deterministic assertions, evaluator scores, benchmark runs
OnlineReal production behaviorUser feedback, task completion, latency, cost, error rate, sampled traces
HumanCalibration and high-impact decisionsBlinded ratings, pairwise preferences, rubric agreement, adjudication

Production loop: offline evals catch regressions before deployment; online telemetry reveals failures that the benchmark missed; human review periodically calibrates both the benchmark and automated judges.

Regression datasets and evaluation-driven development

1. Capture a failure

Save the input, relevant context, model output, tool trajectory where applicable, expected behavior, and failure category.

2. Turn it into a test case

Add the example to a versioned regression dataset. Do not rely on memory or a notebook sitting on your laptop.

3. Fix one cause

Change the prompt, retrieval, model, tool policy, code, or data pipeline with a clearly stated hypothesis.

4. Re-run the suite

Check the target metric and watch for regressions in unrelated slices. A local improvement that breaks another task is not a clean win.

5. Promote the case permanently

Keep the failure in the regression suite so the same bug does not quietly return six months later.

The quality / latency / cost frontier

Never optimize quality in isolation. A production AI system is constrained by quality × latency × cost × reliability × safety. Record p50/p95 latency, token or compute cost, throughput, error rate, and the quality metrics that matter for the task. A model that gains 1 point of quality while tripling latency and cost may be a worse production choice.

Quality

Task success, correctness, relevance, groundedness.

Latency

p50/p95 response time, tool latency, queueing.

Cost

Tokens, model calls, embedding/retrieval cost, compute.

Reliability

Error rate, timeout rate, fallback success, stability.

Tooling: learn the concepts first, then the ecosystem

You do not need to memorize every evaluation framework. Be able to design the evaluation system yourself, then use tooling where it accelerates execution. Useful ecosystems include Ragas for RAG/agent metrics, DeepEval for LLM application tests, LangSmith for tracing/evaluation workflows, Arize Phoenix for observability/evaluation, and provider-native evaluation tooling. The transferable skill is the evaluation methodology, not allegiance to one vendor.

Minimum AI Evaluation portfolio artifact

Build one system with a real eval loop

Take one RAG or agent project from your roadmap and ship an evaluation harness containing: 50–200 representative cases, a versioned regression set, deterministic checks where possible, LLM-judge/rubric checks where necessary, retrieval metrics, task-success metrics, failure slices, latency/cost measurements, and a short report comparing at least two system variants.

Interview standard: you should be able to answer “How do you know it works?”, “What does it fail on?”, “How did you prevent regressions?”, and “What did quality cost you in latency and money?” with numbers rather than vibes.

AI Security Engineering: Build Agents That Cannot Freely Betray You

Core AI Skill ~10h + ongoing ▶

Why this module exists

Modern AI systems are no longer isolated text generators. They retrieve untrusted content, call tools, access files, execute code, use credentials, and sometimes act autonomously. Security therefore has to be designed around the entire model → context → tool → identity → runtime → data chain.

Rule: never give an agent a capability merely because the model might need it. Start with the minimum capability, minimum data, minimum privilege, minimum autonomy, and a clear audit trail.

Current security guidance increasingly treats prompt injection, excessive agency, supply-chain compromise, tool poisoning, identity/privilege abuse, unexpected code execution, and agent hijacking as first-class AI-system risks. OWASP's 2025 LLM guidance includes prompt injection, sensitive information disclosure, supply chain, poisoning, improper output handling, excessive agency, vector/embedding weaknesses, and unbounded consumption; its newer agentic guidance extends this to agent goal hijack, tool misuse, identity/privilege abuse, agentic supply-chain vulnerabilities, and unexpected code execution. OWASP GenAI Security

The AI security attack surface

1. Model

Jailbreaks, unsafe outputs, model manipulation, system-prompt leakage, weak refusal behavior.

2. Context

Direct/indirect prompt injection, poisoned documents, malicious web pages, untrusted tool output, cross-context contamination.

3. Tools & protocols

Tool poisoning, confused-deputy behavior, unsafe schemas, command injection, MCP/A2A integration risks, shadow tools and servers.

4. Runtime & identity

Credential theft, privilege escalation, excessive permissions, code execution, data exfiltration, insecure containers and weak auditability.

Core threat classes you must know

Least privilege for agents

Minimum functionality

Expose only the tools required for the task. If an agent only needs read access, do not expose write/delete functions.

Minimum permissions

Use scoped identities and short-lived credentials. Separate read, write, admin and destructive capabilities.

Minimum autonomy

Require approval or human review for high-impact actions. Make the boundary explicit instead of hoping the model behaves.

MCP and agent protocol security

Treat MCP servers, tools and protocol messages as part of the security boundary. OWASP's MCP Top 10 currently highlights token/secret exposure, privilege escalation, tool poisoning, supply-chain attacks, command execution, intent-flow subversion, authentication/authorization failures, missing telemetry, shadow servers and context over-sharing. OWASP MCP Top 10

MCP security checklist

  • Authenticate the client and server appropriately
  • Use scoped, short-lived credentials
  • Validate tool names, schemas and arguments
  • Track tool provenance and version changes
  • Do not trust tool output merely because it came through a protocol
  • Log tool calls, identities, approvals and outcomes

Red flags

  • Long-lived secrets in prompts, logs or memory
  • One token with broad write/admin access
  • Tools that combine read + write + delete unnecessarily
  • Dynamic tools with no provenance or review
  • Agent can execute arbitrary shell commands
  • No way to reconstruct who/what/why caused a consequential action

Sandboxing and runtime containment

If an agent can execute code or manipulate files, assume the model can eventually be induced to make a dangerous call. Contain the blast radius with isolated runtimes, non-root users, read-only filesystems where possible, restricted network egress, CPU/memory/time limits, temporary workspaces, explicit host boundaries and kill switches. OpenAI's public agent-security guidance similarly emphasizes sandboxing and layered protections because prompt injection remains an evolving attack class. OpenAI: Designing AI agents to resist prompt injection

Security testing & red teaming

1. Map trust boundaries

Identify users, models, retrieved content, tools, MCP servers, credentials, databases and external services.

2. Define attacker goals

Examples: exfiltrate a secret, modify a repository, send an unauthorized message, execute code, escalate privileges or cause runaway cost.

3. Build attack cases

Test direct injection, indirect injection, malicious documents, poisoned tool output, compromised dependencies, credential abuse and long-horizon manipulation.

4. Measure the security boundary

Track attack success rate, data exposure, unauthorized tool calls, privilege violations, unsafe code execution and recovery behavior.

5. Fix and regression-test

Every successful attack becomes a permanent security regression case. Re-run it after model, prompt, tool, dependency and infrastructure changes.

Security observability

Identity

Who initiated the task? Which service identity and credentials were used?

Intent

What task was requested, what approvals were given, and what policy applied?

Actions

Which tools, APIs, files, commands and destinations were touched?

Outcome

What changed, what failed, what data moved, and did a security policy trigger?

Minimum AI Security portfolio artifact

Build a deliberately attacked agent

Take one RAG/agent system and produce a security case study: threat model, trust-boundary diagram, least-privilege tool design, credential strategy, sandbox/runtime controls, at least 20 adversarial attack cases, automated security regression tests, telemetry, and a before/after report showing which attacks were blocked and which remained unresolved.

Interview standard: you should be able to explain exactly what happens if an attacker controls retrieved content, a tool result, a dependency, a credential, or an external website — and where the system stops the attack.

The contributor workflow: how experienced agent OSS contributors work

1. Pick one real subsystem

Choose runtime, state/checkpointing, tool execution, transport, provider adapter, tracing, evaluation, security or test infrastructure. Do not start by modifying the whole agent architecture.

2. Read the repository's design before the issue

Inspect CONTRIBUTING, architecture docs, package boundaries, tests, recent merged PRs and the code path named by the issue. Learn how maintainers already solve similar problems.

3. Run the smallest real path

Start one agent, invoke one tool, inspect one trace, trigger one failure and identify where state changes. If you cannot explain the control flow, you are not ready to patch it.

4. Reproduce a real failure

Build a minimal reproduction for a timeout, malformed tool call, duplicate side effect, interrupted stream, stale checkpoint, rate limit or provider failure. Save the reproduction as a test/fixture when the project permits.

5. Define the invariant

Write the behavior that must remain true: no duplicate side effect, bounded retry count, resumable state, valid tool schema, authorized action, deterministic checkpoint restoration or equivalent.

6. Patch the smallest ownership boundary

Fix the layer that owns the invariant. Avoid prompt changes when the real bug is state management; avoid framework rewrites when a transport or retry boundary is broken.

7. Test adversarially

Test malformed tool arguments, repeated delivery, timeout during side effect, cancelled execution, partial state, provider 429/5xx, duplicate messages and recovery after process restart.

8. Measure before/after

Record success rate, recovery rate, duplicate-side-effect rate, latency, token/cost impact and relevant trace evidence. Agent changes need behavioral evidence, not just green unit tests.

9. Submit upstream like a maintainer

Explain the failure, invariant, design choice, tests, compatibility impact and evidence. Keep the PR reviewable. Be ready to revise the implementation after maintainers challenge the abstraction.

Experienced-contributor rules

  • Bound autonomy. Every side effect needs an explicit permission and failure boundary.

Distributed-systems invariants you must learn to defend

Safety

A side effect must not happen more times than the system contract permits. Define what "duplicate" means for the operation.

Liveness

Useful work must eventually progress under stated assumptions. Watch for stuck leases, poisoned tasks and blocked queues.

Boundedness

Queues, retries, memory and concurrency cannot grow without a limit during overload.

Recoverability

After a worker/dependency failure, the system must have a defined path to resume, replay, reconcile or explicitly abandon work.

Experienced OSS contributor playbook

  • Find the invariant before the fix. "Add retries" is not a design; "this operation is safe to retry because..." is.
  • Map side effects. Database writes, payments, emails, model calls and external APIs have different duplication risks.
  • Read failure-path tests first. Mature distributed projects often encode years of operational knowledge in their tests.
  • Inject timing failures. Kill a worker before ack, after ack, during a side effect, and during recovery. Timing changes the semantics.
  • Measure distributions. Queue depth, service time and p95/p99 behavior often matter more than averages during overload.
  • Do not retry everything. Permanent errors, validation failures and authorization failures should not become retry storms.
  • Make resource bounds explicit. Every queue, worker pool, retry loop and buffer needs an intentional limit.
  • Preserve observability. A reliability change without traces, counters or logs can make the next incident harder to diagnose.
  • Prefer small failure reproductions. A deterministic 50-line test is more valuable to maintainers than a vague production story.
  • Do not rewrite concurrency architecture casually. Existing scheduling behavior may encode compatibility assumptions you have not discovered yet.
  • Benchmark recovery, not only throughput. A system that is fast until one dependency fails is not robust.
  • Study recent merged reliability PRs. Learn how the project currently handles backoff, ownership, testing and operational trade-offs.

Experienced OSS contributor playbook

  • Benchmark the whole path. Component speedups can disappear behind network, queueing or synchronization costs.
  • Understand topology before changing parallelism. Tensor/pipeline/data/expert strategies create different communication and memory constraints.
  • Treat GPU memory as a scheduling resource. "One GPU" is not a uniform unit when models, KV caches and workloads have different footprints.
  • Measure tail latency. AI serving systems are often constrained by p95/p99 behavior, not average latency.
  • Separate capacity from availability. A system can have enough theoretical compute but still fail because the right resource is unavailable at the right time.
  • Don't autoscale on the easiest metric. CPU can look healthy while request queues and GPU work are collapsing.
  • Test cold starts. Model loading and GPU initialization can dominate real scale-up behavior.
  • Make state boundaries explicit. KV caches, agent state, retrieval state and workflow checkpoints have different durability/affinity requirements.
  • Expect partial failure. One worker, GPU, node, retrieval shard or model replica can fail while everything else remains alive.
  • Do not optimize utilization at the expense of quality. Larger batches, aggressive routing or compression can alter task success and retrieval/agent behavior.
  • Study recent upstream performance PRs. Mature AI infrastructure projects often contain subtle hardware, scheduler and compatibility constraints.
  • Keep contribution scope narrow. A benchmark, scheduler fix or serving optimization should be reviewable independently before you propose an architecture rewrite.

5B · RAG Evaluation — separate retrieval from generation

Retrieval Recall

Did the evidence required to answer the query appear in the candidate set?

Test: labeled relevant chunks/documents + recall@k.

Ranking Quality

Did the useful evidence appear near the top of the retrieved context?

Test: MRR/NDCG/precision-style ranking analysis.

Context Quality

Was the selected context sufficient, relevant and within the context budget?

Test: context sufficiency + distractor cases.

Grounded Answer

Did the final answer make claims supported by the supplied evidence?

Test: claim→evidence mapping + unsupported-claim rate.

Critical diagnosis: do not hide retrieval failures inside generation scores. If recall is bad, changing the prompt may conceal the problem rather than fix it.

5H · Incident Engineering for AI

  • Capture the trace before changing the system. Preserve enough evidence to reconstruct the failure.
  • Separate symptom from cause. "Bad answer" may be retrieval recall, tool failure, stale state, model behavior or policy enforcement.
  • Turn incidents into eval cases. A production failure that never becomes a regression test is likely to return.
  • Track model/prompt/retrieval versions. Without version correlation, regression analysis becomes guesswork.
  • Use canaries. Release changes to a controlled fraction before exposing the entire workload.
  • Measure quality and infrastructure together. Faster and cheaper is not automatically better.
  • Keep an explicit rollback matrix. Know which layer can be reverted independently.
  • Protect telemetry itself. Observability data can contain prompts, PII, credentials or sensitive retrieved content.
  • Sample intelligently. High-volume traces may require adaptive sampling, but security/quality-critical events should not disappear.
  • Do not worship dashboards. Every metric should answer a diagnostic or operational question.
  • Read incident reports and regression tests in mature OSS projects. They reveal operational knowledge that tutorials rarely teach.
  • Contribute instrumentation/evaluation fixes upstream. Observability and evaluation improvements can be high-leverage OSS contributions because they improve maintainability for everyone.

Experienced OSS contributor playbook

  • Find existing test/eval conventions before adding a new framework. Mature repositories usually have a preferred pattern.
  • Prefer deterministic graders whenever the task permits. Exact-match, schema validation, state assertions and executable outcomes are easier to trust than a judge.
  • Calibrate LLM judges. Compare them against human labels and inspect disagreements instead of treating judge scores as ground truth.
  • Version datasets and evaluators. A score without dataset/evaluator version is weak evidence.
  • Keep a protected regression set. Do not tune directly against every test case until it becomes meaningless.
  • Separate retrieval metrics from answer metrics. Otherwise you cannot identify the actual failure surface.
  • Instrument before optimizing. If you cannot see where latency/cost/quality changes, optimization is guesswork.
  • Use semantic conventions instead of inventing telemetry names. OpenTelemetry's common conventions exist specifically to improve correlation and interoperability. citeturn0search1
  • Protect telemetry content. Prompts and outputs can contain sensitive data; logging everything is not observability maturity. citeturn0search7
  • Turn incidents into tests. Every meaningful production failure should leave a durable artifact.
  • Contribute narrow observability/evaluation improvements. Add instrumentation, missing metrics, regression tests, benchmark coverage or evaluator fixes rather than trying to rewrite an entire evaluation platform.
  • Benchmark trade-offs. Report quality + latency + cost together. A single score hides engineering reality.

6D · Advanced OSS contributor behaviors

Repository Progression: Beginner → FAANG-level

Portfolio ongoing ▶

Jumping straight to a frontier-lab repo is how most beginners bounce off Open Source entirely. Climb this ladder instead — each tier's codebase complexity, review bar, and CI strictness step up deliberately.

Tier 1 — Beginner-friendly, high-volume good-first-issues

Small, well-scoped, extremely welcoming maintainers, huge good first issue backlogs. Purpose: learn the fork→PR→review loop with minimal codebase complexity. Example shape: single-purpose CLI tools, small utility libraries, documentation-heavy projects, first-timers-only labeled repos.

Tier 2 — Intermediate, real users, moderate codebase

Thousands of stars, a small core team, a real test suite and CI gate you must pass. Purpose: learn to work inside someone else's architecture and conventions. Example shape: mid-size Python/JS libraries, a specific integration package inside a larger ecosystem (e.g. one vector-store integration inside LangChain, not LangChain core).

Tier 3 — Advanced, high-traffic, strict review culture

Tens of thousands of stars, dozens of maintainers, RFC-style discussion required before large changes, multiple rounds of review as the norm. Purpose: learn to propose, defend, and land non-trivial design decisions in public. Example shape: Hugging Face Transformers, scikit-learn, FastAPI core.

Tier 4 — Production-grade infrastructure

Code that runs in other companies' production systems. Correctness and backward compatibility are non-negotiable; performance regressions are caught by dedicated benchmark CI. Purpose: learn engineering discipline under real stakes. Example shape: vLLM, Ray, Kubernetes, PostgreSQL extensions.

Tier 5 — Frontier-lab / FAANG-level research repos

PyTorch core, JAX, DeepSpeed, Triton, CUDA-adjacent kernels. Contributors here are frequently paid staff at major labs; outside contributions are welcomed but held to research-grade rigor — benchmarked, reviewed by domain experts, sometimes requiring a CLA (Contributor License Agreement). Purpose: this is where "Open Source contributor" starts reading as "already basically qualified for the team."

Why this order matters

Each tier isn't just "harder code" — it's a different social and process environment. Skipping tiers means learning codebase navigation, Git workflow, and high-stakes design negotiation all at once, which is exactly why so many beginners' first PR attempt is to a repo three tiers too advanced.

Open Source Programs & Mentorships

Opportunity apply annually ▶

These programs turn "I contribute in my spare time" into a structured, mentored, often-paid commitment — and they are one of the strongest resume lines available to someone without industry experience yet. Details (dates, stipends) shift year to year — always verify current specifics on the program's own site before applying.

Google Summer of Code (GSoC) Some prior contribution recommended

What: A ~12-week paid, mentored contribution program where contributors work on a defined project with an accepted open-source org. Eligibility: Open globally to contributors 18+ (no longer student-only since 2022 rule changes — verify current rules each cycle). Process: pick an org, discuss a project idea with mentors, submit a written proposal, get selected, then code for the program duration with milestone check-ins. Selection criteria: quality of proposal, evidence of prior small contributions to that org, clear communication with mentors pre-application. Tip: orgs strongly favor applicants who've already opened a small PR before applying — do that first.

Outreachy Beginner-friendly, equity-focused

What: Paid remote internships (~3 months) in Open Source, explicitly focused on groups underrepresented in tech. Process: an initial "contribution phase" where applicants make a small real contribution to a participating project before final selection — this phase itself is one of the best structured on-ramps into OSS available. Tip: treat the contribution phase as your actual goal even if not selected for the internship — the skills and PR history are the real prize.

LFX Mentorship (Linux Foundation) Some experience recommended

What: Rolling mentorship cohorts (not just once a year) across Linux Foundation projects — including many cloud-native and, increasingly, AI-adjacent projects under LF AI & Data. Process: browse open mentee slots, apply directly with a short proposal/CV, selected by the project's own mentors. Tip: because cohorts run continuously, it's often less competitive per-cycle than GSoC — worth checking year-round.

CNCF Mentorship (LFX under Cloud Native Computing Foundation)

What: Mentored contributions to cloud-native infrastructure projects (Kubernetes-adjacent) — highly relevant to AI Infrastructure/MLOps career tracks given how much AI serving now runs on Kubernetes. Selection: similar to LFX generally — proposal plus evidence of initiative.

MLH Fellowship (Major League Hacking)

What: A paid, cohort-based, ~12-week fellowship with Open Source, AI/ML-focused, and traditional software tracks; includes structured technical curriculum alongside real contribution work. Good for: students and early-career developers wanting more structure/community than a solo GSoC-style commitment.

Google Season of Docs

What: Pairs technical writers with open-source projects for a documentation-focused engagement. Good for: contributors who want to build a portfolio starting from the documentation tier of the contribution ladder (Module 8) into something formally recognized.

Hyperledger Mentorship, Apache Software Foundation Programs, Julia Season of Contributions, Red Hat Open Source Program Office initiatives

Narrower in scope than GSoC/Outreachy but valuable if your target ecosystem overlaps — Apache projects show up heavily in data engineering (Spark, Kafka, Airflow), which intersects with AI data pipelines; Julia is relevant if you're going deep on the scientific-computing/quant side.

University-sponsored initiatives & AI-foundation mentorships

Many universities now run their own OSS clubs or credit-bearing OSS practicum courses; some AI foundations and labs run informal community-contribution programs tied to specific open-weight model releases. These are lower-profile but often lower-competition than the flagship programs above — worth checking your own institution's CS department and any AI lab community Discords.

How Companies Actually Evaluate Open Source Work

Hiring Insight ~1.5h ▶

Quality over quantity — what recruiters and hiring engineers actually look at

  • They open your 3–5 most substantial PRs, not your total commit count.
  • They read the PR description and the review thread — how you responded to feedback tells them more than the code itself.
  • They check whether your contributions were merged, not just opened — an open, stale PR signals unfinished work.
  • They look for a pattern over time, not a single burst right before applying (a wall of commits in the two weeks before your application date is a well-known tell).

The contribution-graph myth

Myth: a fully green GitHub contribution graph gets you hired. Reality: hiring engineers know the graph can be gamed (trivial daily commits, private repo activity counted, bot-assisted commits) and most experienced reviewers weight it near zero. What they weight heavily instead: 2–3 PRs to recognizable, real projects where you handled non-trivial review feedback well.

What "meaningful contribution" means in practice

Weak signalStrong signal
50 typo-fix PRs across random repos3 PRs to the same project showing escalating complexity over months
A huge PR opened and never followed up onA modest PR that went through 3 rounds of review and got merged
Contributions with no testsContributions that include tests and pass CI on the first or second try
Copy-pasted or clearly unreviewed AI-generated PRsA PR description that shows you understand tradeoffs you made

How Open Source strengthens a resume, concretely

  • Replaces "familiar with PyTorch" with a linked, merged PR to PyTorch or an ecosystem library — verifiable, not self-reported.
  • Gives interviewers real code to discuss instead of a take-home exercise — often leads to more substantive technical interviews.
  • Demonstrates async, written communication skill — the single most requested but least-tested soft skill for remote AI roles.
  • Shows you can operate inside someone else's codebase and constraints, which is literally the day-one job of any new hire.

Becoming a Recognized Contributor

Long-term 6-18 months ▶
Choose 1–2 projects to go deep in

Recognition compounds inside a single community far faster than it does spread across dozens of one-off PRs.

Help newcomers on issues/discussions

Answering a "how do I set this up" question is low-effort, high-goodwill, and visible to maintainers watching the community.

Review other contributors' PRs

Most projects allow (and welcome) non-maintainers leaving substantive review comments — this is one of the fastest ways to get on a maintainer's radar.

Fix bugs and ship features consistently

Consistency beats intensity — a steady cadence over months reads as reliability, which is exactly what maintainers are screening for when granting more trust.

Improve documentation proactively

Volunteering to document something you just learned the hard way is one of the highest-goodwill contributions a project can receive.

Get invited as a reviewer, then a triager

Many projects have an informal ladder: contributor → trusted reviewer (can approve, not merge) → committer/maintainer (can merge). This is earned through visible, repeated good judgment, not requested.

Become a maintainer (optional, high-commitment)

The strongest possible resume line, but a real ongoing responsibility — only pursue it for a project you'd genuinely want to steward.

Share what you're learning publicly

A short blog post walking through a bug you fixed, or a conference/meetup lightning talk, compounds your visibility beyond the project's own community.

The compounding loop

Help newcomers → maintainers notice you → they trust you with bigger issues → your PRs get merged faster because reviewers already trust your judgment → you get invited to review → your name starts showing up in release notes and CONTRIBUTORS files → recruiters searching that ecosystem's contributor list find you directly.

Building an Elite GitHub Profile

Portfolio ~4h + ongoing ▶

The profile README

A short, well-written username/username repo README is the first thing a recruiter sees. Keep it to: who you are, what you focus on, 2–4 pinned highlights, and how to reach you. Skip badge walls and animated GIF headers — they read as templated, not impressive.

Pinning strategy

Pin a deliberate mix: one polished original project (shows you can build, not just fix), one or two repos with your best merged contributions highlighted in the README, and one that demonstrates your specific target domain (e.g., a small vLLM benchmark repo if you're targeting AI infra roles).

Repository organization

  • Every public repo should have a real README, even side projects — an unexplained folder of scripts signals unfinished work, not volume.
  • Archive or delete genuinely abandoned tutorial-following repos rather than letting them dilute your profile.
  • Use consistent commit message conventions across your own projects — it's a preview of how you'll work on a team.

PHASE 01 / 08 — COMPLETE

Core Foundations

Networking, OS/concurrency, database internals, and distributed systems theory — the substrate every HLD/LLD decision later gets justified against. Skip this and you'll be pattern-matching diagrams from memory instead of reasoning from first principles, which is exactly what breaks under a hard interviewer's follow-up questions.
Weeks 1 – 8
Load 8–10 hrs/wk
Exit gate 4 checks
WHY THIS PHASE EXISTS Most candidates who "fail" HLD/LLD rounds don't fail because they don't know the name of a pattern — they fail because they can't defend a trade-off when pushed. "Why Kafka and not RabbitMQ here?" "Why B-tree index and not hash index?" "What actually breaks first under partition?" Those answers come from this phase, not from memorizing "design Twitter" solutions. WEEK 01–02

Networking, Down to the Wire

~9 hrs/wk
Topics — in this order
  • OSI vs TCP/IP model only as much as explains real behavior — skip trivia
  • TCP handshake, slow start, congestion control, why TCP is "reliable" and what that costs you
  • UDP and when losing reliability is the correct trade (video, gaming, DNS)
  • HTTP/1.1 vs HTTP/2 (multiplexing, head-of-line blocking) vs HTTP/3 (QUIC over UDP)
  • DNS resolution path end to end — recursive resolver, TTL, caching layers
  • TLS handshake cost, TLS 1.3 vs 1.2, session resumption
  • Connection pooling, keep-alive, why opening a new TCP+TLS connection per request is a silent killer
Resources
  • High Performance Browser Networking — Ilya Grigorik free online — read Parts 1 & 2 fully, this is the single best resource for this week
  • Kurose & Ross, Computer Networking book — Ch. 2–3 only (transport layer), skip the rest for now
  • Wireshark tool — install now, you'll use it in the hands-on below
  • Cloudflare Learning Center — "What happens when..." series free — good for HTTP/2/3 and TLS refreshers
Hands-on build

Write a raw TCP echo server in Python using only the socket module (no frameworks). Then write a minimal HTTP/1.1 server on top of it that parses a real request line and headers by hand. Capture the full exchange in Wireshark — TCP handshake, your HTTP request/response, TCP teardown.

Deliverable: a short written note (half page) stating the measured latency contribution of TCP handshake vs TLS handshake vs actual request/response, using your own captured numbers — not textbook numbers.
WEEK 03–04

Operating Systems & Concurrency

~9 hrs/wk
Topics — in this order
  • Processes vs threads, context-switch cost, why threads aren't free
  • Virtual memory, paging, why "just add more RAM" isn't always the fix
  • Blocking vs non-blocking I/O, buffered vs direct I/O
  • The C10K problem and why thread-per-connection collapses at scale
  • epoll / kqueue / IOCP — the actual mechanism behind "async"
  • Thread pools vs event loops — when each wins
  • Locks, mutexes, race conditions, deadlock conditions (the four Coffman conditions)
Resources
  • OSTEP (Operating Systems: Three Easy Pieces) free online — Concurrency section in full, skip file systems for now
  • "The C10K Problem" — Dan Kegel free essay — old but still the clearest framing
  • "What Color is Your Function?" — Bob Nystrom free essay — best mental model for async you'll ever read
Hands-on build

Build the same simple HTTP server two more ways: (1) thread-pool-per-request, (2) single-threaded event loop using asyncio or raw epoll via selectors. Load-test all three servers (raw socket, thread-pool, event-loop) with wrk or ab at increasing concurrency (10 → 100 → 1000 connections).

Deliverable: one graph (throughput/latency vs concurrency) comparing the three implementations, plus 3–4 sentences explaining why the curves diverge where they do.
WEEK 05–06

Database Internals

~10 hrs/wk
Topics — in this order
  • B-tree indexing — structure, why reads/writes cost what they cost
  • LSM-trees — structure, write amplification vs read amplification, compaction
  • B-tree vs LSM: when each wins (this single trade-off shows up in half of all HLD interviews)
  • Query execution plans, EXPLAIN ANALYZE, index selection by the planner
  • ACID properties — precisely, not the acronym-only version
  • Isolation levels: read uncommitted → serializable, and what anomaly each one prevents
  • Write-ahead logging (WAL), crash recovery
  • Leader-follower replication basics, replication lag, sync vs async replication
Resources
  • Designing Data-Intensive Applications — Martin Kleppmann book — Ch. 1–3 in full; this book is the spine of the entire 18-month plan, buy it now
  • Use The Index, Luke free online — best practical guide to how indexes actually get used
  • "Architecture of a Database System" — Hellerstein, Stonebraker, Hamilton free paper — dense but worth skimming for the mental model
Hands-on build

Install Postgres locally. Load a table with ~1M synthetic rows. Run identical queries with and without an index, capture EXPLAIN ANALYZE output for both. Then set up SQLite and read through its B-tree page format documentation to connect the theory to a real on-disk structure.

Deliverable: annotated EXPLAIN ANALYZE outputs (before/after index) with your own explanation of why the planner's cost estimate changed.
WEEK 07–08

Distributed Systems Theory Primer

~10 hrs/wk
Topics — in this order
  • CAP theorem, rigorously — what "partition" actually means, and why "pick 2 of 3" is a misleading meme
  • PACELC — the extension almost nobody mentions but every hard interviewer expects
  • Consistency models: strong/linearizable vs eventual vs causal — with a concrete example for each
  • Why consensus is hard — the core problem (agreement under failure/asynchrony), not the algorithm yet
  • Failure models: crash-stop vs crash-recovery vs Byzantine — and why almost all interview systems assume the first
  • Logical clocks (Lamport clocks), why wall-clock time lies to you in distributed systems
Resources
  • DDIA — Kleppmann book — Ch. 5 (Replication), Ch. 8 (Trouble with Distributed Systems), Ch. 9 (Consistency & Consensus, first half)
  • MIT 6.824 Distributed Systems — Lectures 1–3 free, YouTube — this course will resurface heavily in Phase 6, start the habit now
  • "Perspectives on the CAP Theorem" — Gilbert & Lynch free paper — the actual proof, worth the discomfort
Hands-on build

Run two Redis instances locally with replication configured. Use tc/network namespaces (or simply kill the link) to simulate a network partition between them. Write to the primary during the partition, observe what the replica shows, then heal the partition and observe convergence behavior.

Deliverable: a one-page write-up explaining, using your own experiment (not the textbook), whether this Redis setup is CP or AP under partition, and why — cite what you actually observed.

PHASE 02 / 08 — ISSUED FOR CONSTRUCTION

LLD I — OOP, SOLID, Design Patterns

This phase builds the discipline layer: writing code that stays clean under changing requirements. LLD interviews are graded almost entirely on whether your design survives the interviewer's "now add feature X" follow-up — that survivability comes from correct OOP and SOLID instincts, not from having memorized 23 GoF patterns. Patterns are taught here as answers to problems you'll first feel the pain of, not as vocabulary to recite.
Weeks 9 – 16
Load 9–10 hrs/wk
Exit gate 4 checks
WHY THIS PHASE EXISTS Almost every LLD rejection has the same root cause: a design that works for the first requirement and collapses the moment the interviewer adds a second one — "now support multiple payment methods," "now the elevator needs a priority mode." That collapse is a SOLID violation, not a "didn't know enough patterns" problem. This phase trains you to feel a violation as it happens, and to reach for the right pattern because it fixes a real symptom you just caused — not because it's next on a checklist.
WEEK 09–10

OOP Foundations, Done Rigorously

~9 hrs/wk
Topics — in this order
  • Encapsulation & abstraction — hiding implementation vs hiding intent most people only learn the first one
  • Inheritance vs composition — why "favor composition over inheritance" is not a slogan, walk through a concrete break case
  • Polymorphism — static dispatch (overloading) vs dynamic dispatch (overriding), and what it costs at runtime
  • Interfaces vs abstract classes — when each is the honest choice, not the habitual one
  • Coupling & cohesion — how to eyeball a class and know it's doing too much
  • Law of Demeter ("don't talk to strangers") — the rule that quietly prevents most tangled designs
Resources
  • Head First Object-Oriented Analysis & Design book — Ch. 1–4; slow but the analogies stick, don't skip it for being "too basic"
  • "Composition over Inheritance" — Refactoring Guru free article — read alongside your own broken example below
  • Clean Code — Robert C. Martin book — Ch. 2–3 (naming, functions) as a side reference while you refactor
Hands-on build

Take a deliberately messy "god class" (write one yourself first — a 300+ line OrderManager that validates, calculates tax, applies discounts, sends email, and logs, all in one class) and refactor it into properly separated, composed classes. Then build a small text-based Parking Lot simulation (just the entities and their interactions — no persistence, no UI) using composition, not inheritance, to model vehicle types.

Deliverable: before/after code for the god-class refactor plus a 4–5 line note on which specific coupling problem each extracted class fixed.
WEEK 11–12

SOLID, Applied Not Memorized

~9 hrs/wk
Topics — in this order
  • Single Responsibility — "one reason to change," and why that's a sharper test than "does one thing"
  • Open/Closed — extend behavior without editing existing, tested code
  • Liskov Substitution — the classic Rectangle/Square trap and why it generalizes
  • Interface Segregation — fat interfaces forcing classes to implement methods they don't need
  • Dependency Inversion — depend on abstractions, and why this is what actually enables unit testing
  • For each principle: what breaks in production 6 months later if you ignore it
Resources
  • Agile Software Development: Principles, Patterns, and Practices — Robert C. Martin book — the SOLID chapters are the origin source, read these over secondary summaries
  • Refactoring Guru — SOLID Principles free, visual — good for quick before/after diagrams
  • Refactoring — Martin Fowler book — Ch. 1 case study, to connect SOLID to the actual mechanics of refactoring
Hands-on build

Write five short code snippets from scratch, each one deliberately violating a different SOLID principle (don't copy examples — write your own so the violation is one you'll recognize later). Refactor each. Then take your Week 9–10 Parking Lot code and audit it against all five principles — fix whatever you find.

Deliverable: 5 before/after pairs plus the audited Parking Lot code with a short log of what SOLID violations you found in your own earlier work.
WEEK 13–14

Design Patterns I — Creational & Structural

~10 hrs/wk
Topics — in this order
  • Singleton — the pattern, and the honest case for why it's overused and often a design smell
  • Factory Method & Abstract Factory — deferring object creation, and the difference between the two
  • Builder — for objects with many optional parameters or multi-step construction
  • Prototype — cloning over re-constructing, when object creation is expensive
  • Adapter — bridging incompatible interfaces without touching either side
  • Decorator — adding behavior without subclass explosion
  • Facade — simplifying a complex subsystem's entry point
  • Composite & Proxy — tree structures treated uniformly, and controlled access to an object
Resources
  • Refactoring Guru — Creational & Structural Patterns free, visual — primary resource this week, the diagrams are unusually clear
  • Head First Design Patterns book — Ch. 1, 4, 6 (Strategy intro, Factory, Singleton) — the narrative style helps the "why," pair with Refactoring Guru for precision
  • Design Patterns (GoF) — Gamma, Helm, Johnson, Vlissides book, reference only — don't read cover to cover, look up each pattern here after you've already used it once
Hands-on build

Build a small notification system that must support multiple channels (email, SMS, push) and multiple notification "types" that can be layered (e.g., urgent + logged + retried). Do not pre-plan which patterns to use — build the naive version first, feel where it breaks when you add a second channel, then refactor in Factory (for channel creation) and Decorator (for layered behavior). No toy textbook examples — this must be your own working code.

Deliverable: working notification system code plus a short note on the exact moment each pattern became necessary, not just "I added it."

Design Patterns II — Behavioral, and UML for Communication

Deliverable: working code + 2 UML diagrams (class + sequence), each produced within the 10-minute time box.

Load 9–11 hrs/wk
Exit gate 5 checks
WHY THIS PHASE EXISTS Phase 2 taught the vocabulary. That is not enough. WEEK 17

LLD Interview Protocol — Requirements → Model → Contracts

~9 hrs/wk
Topics — in this order
  • Requirement extraction: functional vs non-functional requirements, scope control, assumptions
  • Actors, use cases, domain entities, value objects, services, repositories, policies
  • Invariants: what must never become false, and where that rule should live
  • Public contracts: method signatures, preconditions, postconditions, error semantics

Take a deliberately vague prompt: "Design a library lending system." Spend 10 minutes clarifying scope, then produce a domain model, public interfaces, one main sequence, five invariants, and ten test cases. Deliverable: two one-page design sheets showing requirements, assumptions, domain model, contracts, invariants, sequence flow, and tests.

PHASE 04 / 08 — ISSUED FOR CONSTRUCTION

HLD Building Blocks

The transition from object-level design to system-level engineering. This phase teaches the primitives that make large systems work: service boundaries, API contracts, storage selection, partitioning, replication, caching, messaging, reliability patterns, capacity planning, observability, and scaling. You do not learn "system design answers" here; you learn the mechanisms those answers are assembled from.
Weeks 25 – 34
Load 9–11 hrs/wk
Exit gate 7 checks
WHY THIS PHASE EXISTS HLD becomes bullshit when someone can draw boxes but cannot explain what happens inside them. A "cache" is not an architectural decision until you can explain invalidation, staleness, eviction, hot keys and failure behavior.

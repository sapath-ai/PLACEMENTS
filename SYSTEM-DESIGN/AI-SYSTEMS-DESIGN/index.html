01 // Four Architectural Planes

Use these planes to locate every system component.

  • Application plane: user-facing AI capability and workflow.
  • Model plane: training, fine-tuning, evaluation, registry and deployment.
  • Data plane: datasets, retrieval, features, context and knowledge.
  • Compute plane: GPUs, CPUs, clusters, networking, storage and scheduling.

02 // Control Plane vs Data Plane

Separate what controls the system from what carries workload traffic.

  • Control: deployment, policy, routing, quotas, access, configuration and governance.
  • Data: inference requests, tokens, embeddings, retrieved context, tool calls and outputs.
  • Ask this distinction repeatedly throughout every later phase.

03 // Online, Nearline, Offline

Classify the workload before designing the infrastructure.

  • Online: latency and availability dominate.
  • Nearline: freshness matters, but asynchronous processing is acceptable.
  • Offline: throughput, reproducibility and batch efficiency dominate.

04 // AI System Lifecycle

Production AI is a feedback loop, not train-once/deploy-once.

  • Problem → Data → Model → Evaluation → Deployment → Inference
  • Monitoring → Feedback → Improvement → Re-evaluation → Redeployment
  • For agents: Task → Context → Action → Tool → Observation → State → Next action.

05 // The Constraint Triangle

Architecture is tradeoff management. Start with the dominant constraint instead of starting with a technology.

  • Quality: model capability, accuracy, groundedness, task success.
  • Latency: TTFT, inter-token latency, end-to-end response time, freshness.
  • Cost: compute, tokens, storage, network, human review and operational overhead.
  • Then add reliability, security, privacy, scalability and maintainability as hard constraints where required.

Method

Framework: How to Answer Any AI System Design Question

A universal 7-step structure, applied throughout as an example to: "Design a real-time recommendation system."

01

Clarify requirements & constraints

Pin down functional requirements and non-functional numbers: expected QPS, latency SLO, consistency needs, cost ceiling, and scale (users, items, data volume).

Applied to "real-time recommendation system": “Are we optimizing for engagement or watch-time? What's the acceptable staleness for a user's feed — seconds or minutes? How many candidate items exist?”

02

Define core entities & data flow

Name the entities (users, items, events, features) and sketch how data moves between them — this grounds everything that follows in concrete objects.

Applied to "real-time recommendation system": Entities: users, videos, watch-events, engagement features. Flow: watch-events → feature pipeline → feature store → ranking model.

03

High-level architecture sketch

Draw the major components and their interactions before drilling into any one of them — candidate generation, ranking, feature store, serving layer.

Applied to "real-time recommendation system": Candidate generation (two-tower retrieval) → lightweight first-pass ranker → heavy second-pass ranker → re-ranking for diversity → serving.

04

Deep-dive the hardest sub-problem

Identify the 1–2 sub-problems the interviewer actually cares about and go deep — this is where signal is generated, not in the boxes-and-arrows.

Applied to "real-time recommendation system": Deep-dive: how the two-tower retrieval model is trained and served with approximate nearest-neighbor search at low latency.

05

Back-of-envelope scale math

Compute concrete numbers live: QPS, storage footprint, network bandwidth, and how they change the design.

Applied to "real-time recommendation system": 500M DAU × 20 sessions/day / 86,400s ≈ 115K QPS sustained — this rules out any single-node ranking service.

06

Reliability & failure modes

State what breaks (model staleness, feature-store outage, cold start) and the corresponding fallback or degradation path.

Applied to "real-time recommendation system": If the ranking model times out, fall back to a cached popularity-based ranking rather than failing the request.

07

Tradeoffs & alternatives

Name at least one alternative you rejected and why — this signals judgment, not just knowledge of a pattern.

Applied to "real-time recommendation system": Rejected a pure collaborative-filtering approach because it can't handle new-item cold start at the required freshness.

Common Failure Modes

The ten mistakes that separate a strong system-design answer from a mediocre one — and the one-line fix for each.

01
MISTAKEJumping to architecture before clarifying requirements
FIXSpend the first 5 minutes only on clarifying questions and numbers.
02
MISTAKEIgnoring non-functional requirements (latency/cost/consistency)
FIXState explicit SLOs before proposing any design.
03
MISTAKEOver-engineering with unnecessary complexity
FIXMatch architectural complexity to the actual scale given in the prompt.

MISTAKETreating ML system design like generic backend design

CAPABILITY BUILD MODEL
These are not 36 disconnected skills. They are capability builds. Each capability combines knowledge → implementation → measurement → failure testing → optimization → deployment → evidence. A capability is not considered built because you studied the topic; it is built when the artifact proves you can operate it under realistic constraints.
CAPABILITY GATE
Gate every capability through the same loop: LEARN → BUILD → MEASURE → BREAK → OPTIMIZE → DEPLOY → DOCUMENT. If you cannot produce evidence from the loop, the capability remains in progress.

Programming & LeetCode Beginner

System Design (AI-flavoured) Intermediate
Elite move: Take a real published LLM-serving outage post-mortem, reconstruct the failure, and redesign the system to prevent it. Then build a GPU + cost simulator: feed it QPS, model size, and context length — get back GPU count and monthly dollar cost, validated against live cloud pricing.
You attach failure modes and dollar figures to your designs. A working cost simulator reframes you from "can code" to "can own a budget."
AI-Native Software Engineering Intermediate
Elite move: Build a repository-level AI engineering benchmark that compares your baseline workflow with an agent-assisted workflow. Then independently verify every accepted patch and measure time-to-correct-change, regression rate, test quality, review effort, and intervention rate. Repeat across unfamiliar repositories and progressively harder tasks.
The durable capability is AI-augmented engineering with verification, not memorising a coding-agent product. You learn when to delegate, how to constrain the agent, how to detect plausible-but-wrong patches, and how to preserve engineering ownership.

The production eval is no longer just a benchmark score. It is a release gate plus an observable execution trace that lets you explain why a stochastic system succeeded, failed, or became too expensive.

THE DISTINCTION
A roadmap tells you what to learn. This playbook tells you how to turn it into capability. The unit of progress is therefore not a completed topic; it is a demonstrated capability with an artifact, measurements, failure evidence, and a deployable result.
FINAL EVIDENCE STANDARD
EVIDENCE LADDER
L1Can explain the concept and reproduce a known result.
L2Can implement it, benchmark it, and diagnose failure.
L3Can deploy it with observability, security and operating constraints.
L4Can extend it, publish the evidence, and defend the engineering trade-offs.
Every major capability should leave evidence another engineer can inspect. At minimum: working artifact, repository, evaluation method, measured result, failure analysis, documentation, and a clear statement of what you would change next. For research, add reproducibility and experimental provenance. For production, add observability, SLOs, cost, security assumptions, and rollback. For open source, add tests, contribution hygiene, and a usable README. Your final portfolio is therefore a body of evidence, not a list of technologies.

    Update 01 // Benchmark Contract

    AI/ML From Scratch — Operating Rules

    This file is a practical implementation benchmark, not a conventional course. The objective is to reconstruct algorithms from mathematical understanding and programming ability, while preserving the original guided exercises exactly as written.

    Allowed

    • Your own notebook, notes, and previously earned code primitives.
    • A programming language and its normal runtime/compiler.
    • Basic numerical/array primitives at the permitted abstraction level.
    • Mathematical references when you genuinely need to verify a definition or equation.

    Forbidden

    • AI coding or answer assistants: ChatGPT, Claude, Gemini, Copilot, etc.
    • Copied implementations, tutorials, Stack Overflow answers, or repository code.
    • Using scikit-learn, PyTorch, TensorFlow, or another library's implementation as the algorithm itself.
    • Hidden library calls that bypass the mechanism you are being tested on.

    Core Standard

    • Derive the mechanism before coding it.
    • Implement the core logic yourself.
    • Validate correctness numerically or against a known behavior.
    • Reuse only primitives that you have already independently earned.

    What Counts as “Done”

    • The implementation runs and produces the intended behavior.
    • You can explain the mathematics and important assumptions.
    • You can diagnose obvious numerical, shape, or convergence failures.
    • You understand what your implementation is doing rather than merely reproducing syntax.

    Integrity rule: the existing algorithm cards remain the canonical guided curriculum. This contract adds assessment discipline; it does not replace, rewrite, or weaken the original exercises.

    UPDATE 06 // Debugging Challenges

    Implementation mastery is not only writing the algorithm correctly. It is also diagnosing why a mathematically plausible implementation fails.

    NUMERICAL FAILURE
    Find overflow, underflow, NaNs, unstable exponentials, or singular matrices without replacing the algorithm with a library call.
    GRADIENT FAILURE
    Locate sign, transpose, broadcasting, chain-rule, or missing-factor errors using numerical gradient checking.
    SHAPE FAILURE
    Diagnose tensor-dimension and broadcasting errors in convolution, recurrent networks, attention, and Transformers.
    LEARNING FAILURE
    Diagnose divergence, vanishing/exploding gradients, bad initialization, poor learning rates, and stalled convergence.
    DATA FAILURE
    Detect leakage, invalid splits, malformed labels, scaling mistakes, and train/test distribution problems.
    LOGIC FAILURE
    Find an implementation that runs and produces plausible outputs but violates the algorithm's actual mathematical procedure.

    UPDATE 07 // Numerical Stability Checkpoints

    Numerical correctness is part of algorithm correctness. For relevant implementations, explicitly test failure modes before accepting the result.

    EXP / SOFTMAX
    Test large positive and negative logits. Use a stable formulation and verify probabilities remain finite and normalized.
    LOG-DOMAIN COMPUTATION
    Test products and probabilities that underflow. Use log-space calculations where appropriate and compare against safe reference cases.
    MATRIX OPERATIONS
    Test singular or ill-conditioned matrices, covariance estimates, inverses/solves, and regularization behavior.
    OPTIMIZATION
    Test exploding updates, stalled convergence, NaNs, learning-rate sensitivity, and gradient clipping where relevant.
    PROBABILISTIC MODELS
    Test zero probabilities, tiny variances, degenerate clusters, and normalization errors in models such as GMM and Naive Bayes.
    DEEP NETWORKS
    Test activation saturation, exploding/vanishing gradients, normalization edge cases, and unstable attention scores.
    CHECKPOINT: an implementation is not considered robust until its relevant numerical failure modes have been deliberately exercised.

    UPDATE 08 // Mandatory Gradient Checking

    Whenever an algorithm contains a differentiable computation implemented by hand, verify the analytical gradient numerically before trusting training behavior.

    01 // ANALYTICAL
    Derive and implement the gradient implied by the algorithm.
    02 // NUMERICAL
    Estimate derivatives with finite differences on small, deterministic inputs.
    03 // COMPARE
    Measure absolute and relative error and define a tolerance appropriate to the scale.
    04 // DIAGNOSE
    If the check fails, isolate the operation before proceeding to model-level training.
    CHECK: analytical gradient ≈ finite-difference gradient. A failing check is a blocker, not something to ignore because the model eventually trains.

    UPDATE 09 // Complexity Analysis

    Correctness is only the first target. For every implementation, understand what scales, what becomes the bottleneck, and whether a materially better implementation is possible.

    TIME COMPLEXITY
    Record dominant training and inference cost in the relevant input dimensions.Time: O( ... )
    SPACE COMPLEXITY
    Account for parameters, intermediate state, caches, temporary matrices, and stored data.Space: O( ... )
    SCALING BOTTLENECK
    Identify the operation that dominates as data, dimensions, sequence length, clusters, or model size grows.
    NAIVE → OPTIMIZED
    Where a meaningful optimization exists, implement the straightforward version first, then improve it and explain the trade-off.
    CHECKPOINT: predict scaling before benchmarking, then use measurements to validate or challenge the analysis.

    UPDATE 10 // Benchmark + Optimization Challenges

    After achieving a correct implementation, measure it. Optimize only when the bottleneck is understood, then verify that the optimization preserves correctness.

    01 // BASELINE
    Record runtime, memory where practical, convergence behavior, and output quality.
    02 // PROFILE
    Identify the actual hot operation instead of optimizing from intuition alone.
    03 // OPTIMIZE
    Vectorize, cache, reduce redundant work, improve data movement, or use a better formulation where justified.
    04 // RE-MEASURE
    Run the same benchmark conditions again and report the measured improvement.
    05 // REGRESSION CHECK
    Compare optimized outputs against the known-correct implementation on deterministic and edge cases.
    06 // EXPLAIN
    Document why the optimized version is faster or smaller and what trade-offs it introduces.
    RULE: “optimized” means measured improvement without sacrificing algorithmic correctness.

    UPDATE 11 // Equivalent-Formulation Challenges

    When an algorithm has multiple mathematically valid formulations, implement the important alternatives and verify that they agree on controlled cases. The goal is to understand the equivalence, not merely memorize one implementation.

    PCA
    Compare covariance-matrix eigendecomposition with SVD. Verify equivalent principal subspaces up to numerical tolerance.
    OPTIMIZATION
    Where appropriate, compare batch and mini-batch formulations and explain when their update behavior differs despite optimizing the same objective.
    ATTENTION
    Compare a straightforward attention implementation with a vectorized formulation and verify identical outputs on deterministic inputs.
    SAMPLING
    Where the curriculum provides alternative samplers or parameterizations, implement both and compare the resulting behavior under matched conditions.
    CHECKPOINT: explain why the formulations are equivalent, where floating-point differences arise, and what practical trade-offs distinguish them.

    UPDATE 12 // Reusable Primitive Library

    Once a primitive has been independently implemented and verified, later algorithms may reuse it. This turns the roadmap into a progressively constructed personal ML toolkit rather than a collection of disconnected scripts.

    LINEAR ALGEBRA
    Matrix/vector operations, decompositions, reductions, norms, and numerical shape checks.
    NUMERICAL UTILITIES
    Stable softmax, log-sum-exp, finite differences, tolerance checks, random seeds, and safe normalization.
    LOSSES + ACTIVATIONS
    Reusable loss functions, activation functions, derivatives, and validation tests.
    OPTIMIZERS
    SGD, momentum, RMSProp, Adam, schedules, and optimizer-state handling.
    GRADIENT TOOLING
    Numerical gradient checker, computational-graph primitives, and gradient diagnostics.
    DATA UTILITIES
    Splitting, batching, shuffling, normalization, dataset iteration, and deterministic test fixtures.
    DISTANCE + SIMILARITY
    Euclidean, Manhattan, cosine, kernel/similarity functions, and reusable neighborhood calculations.
    SAMPLING + INITIALIZATION
    Random initialization, sampling utilities, reproducibility controls, and distribution checks.
    TENSOR / NN UTILITIES
    Shape transformations, padding, batching, masking, normalization, and reusable neural-network components.
    RULE: reuse is earned. A primitive should be independently implemented, numerically checked, and understood before becoming a dependency for later challenges.

    UPDATE 13 // Modern Algorithm Additions

    A deliberately small extension to the modern end of the benchmark. These are mechanism-level exercises, not a shift into production AI engineering.

    BPE TOKENIZER
    Implement byte/character-level pair merging, vocabulary construction, encoding, decoding, and deterministic round-trip tests.
    ROPE
    Implement rotary positional embeddings, verify the rotation structure, and test sequence-position behavior on small deterministic tensors.
    KV CACHE
    Implement cached key/value reuse for autoregressive attention and verify identical outputs against uncached decoding.
    CROSS-ATTENTION
    Implement attention where queries and key/value sequences come from different representations and verify shapes and masking behavior.
    DDIM
    Implement the deterministic diffusion sampling formulation and compare quality/step-count behavior against the existing DDPM sampler.
    CONTRASTIVE OBJECTIVE
    Implement a temperature-scaled contrastive learning objective, positive/negative pairing, and a small synthetic sanity test.
    CLIP-STYLE OBJECTIVE
    Implement symmetric image-text contrastive loss on a tiny paired dataset and verify the similarity matrix and temperature behavior.
    QLORA MECHANICS
    Reproduce the conceptual low-rank adapter path together with quantized base-weight handling at toy scale; focus on mechanism rather than a production quantizer.
    SCOPE RULE: these additions strengthen the modern algorithmic benchmark without turning this file into an MLOps, cloud, or agent-engineering roadmap.

    UPDATE 14 // Final Black-Box Exam

    The final assessment removes the roadmap's scaffolding. Select or randomly draw a set of algorithms across the tiers and receive only the algorithm name, input/output contract, dataset, and constraints.

    01 // SELECTION
    Choose 10–15 algorithms spanning multiple tiers. Do not select only the algorithms you are comfortable with.
    02 // BLANK PAGE
    No equations, checklist, implementation tutorial, library source, AI assistant, or copied reference implementation.
    03 // SPECIFICATION
    For each challenge, provide only the algorithm identity, input/output contract, dataset, and explicit constraints.
    04 // BUILD
    Implement from first principles. Reuse only primitives already earned under Update 12.
    05 // VERIFY
    Run correctness tests, numerical checks, edge cases, complexity analysis, and benchmarks appropriate to the algorithm.
    06 // DEFEND
    Explain the mathematics, assumptions, failure modes, complexity, and implementation trade-offs without reopening the guided card.
    SCORING
    Correctness — 30%  |  Mathematical fidelity — 20%  |  Numerical stability — 15%  |  Edge cases — 10%  |  Complexity — 10%  |  Code quality — 10%  |  Debugging — 5%
    PASSING PRINCIPLE: the goal is not to recognize an algorithm. The goal is to reconstruct it correctly when the scaffolding disappears.

    UPDATE 15 // First-Principles / Oral Defense

    Implementation is not complete mastery until you can defend the algorithm without reopening the implementation guide.

    01 // WHY DOES IT WORK?
    Explain the mathematical or statistical mechanism that makes the algorithm solve its stated problem.
    02 // ASSUMPTIONS
    State the assumptions the algorithm relies on and describe what happens when those assumptions are violated.
    03 // DERIVATION
    Derive the key objective, update rule, recurrence, or transformation from first principles rather than reciting code.
    04 // FAILURE MODES
    Identify numerical, statistical, optimization, data, or architectural conditions that can make the implementation fail.
    05 // COMPLEXITY
    Give the relevant time and space complexity and identify the operation that controls scaling.
    06 // TRADE-OFFS
    Explain why you would choose this algorithm over a related alternative and what you give up by doing so.
    DEFENSE STANDARD: if you cannot explain the mechanism, derive the critical step, and diagnose a failure without the card, the implementation is not yet fully owned.
